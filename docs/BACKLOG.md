**いま無いもの：** 支払いの仕組み、契約状態の持ち方、解約・返金の扱い。

#### 先に決めること

| 論点 | なぜ決めないと進めないか |
| --- | --- |
| **課金の単位** | 人ごとか、リストごとか。2-3 の容量拡張が「誰の容量か」に直結する |
| **支払いの手段** | Stripe などの外部サービスを使う前提でよいか。手数料と入金サイクルが変わる |

| **解約したらどうなるか** | **ここが一番危ない。** 容量を増やした人が解約したとき、上限を超えている分をどうするか（消す・凍結する・据え置く）を決めておかないと、事故が起きてから考えることになる |
| **法令の表示** | 特定商取引法に基づく表記、利用規約、適格請求書（インボイス）の要否 |

- **契約状態をクライアントに持たせない。** いまサイト管理者の判定を

- **外部サービスからの通知（Webhook）を受ける口が要る。** 決済の成否は

### 2. プレミアム限定の機能

#### 2-1. オフラインでも使えるダウンロード機能

**いまの作り：** 音源は Cloud Storage にあり、再生のたびに URL を取り
直して鳴らしている（8.1）。**端末には何も残していない。**

先に決めること。

- **どこまで持つか。** 曲 1 つずつか、リストまるごとか
- **いつ消すか。** 端末の空き容量は有限で、消す規則が無いと溜まり続ける
- **リストから抜けた人・除外された人の端末に残ったものをどうするか。**
  **技術的には消せません。** 一度端末に降りたものを、こちらから
  取り上げる手段は無い。これを承知のうえで配る、と決める必要がある
- **著作権の扱い。** 「共有の範囲で聴く」と「手元に残す」は意味が違う。
  録音した本人以外の音源も入るアプリなので、**規約で触れておくこと**

技術的には、Web では Service Worker と端末側の保存領域を使うことになる。
**いまは Service Worker を実質使っていない**ので、そこから作ることになる。

#### 2-2. 申請なしでリストを作れる（上限つき）

**いまの作り：** リスト作成はサイト管理者の承認が要る（5.1）。
これは「無制限に作られると管理できない」ためであって、
**承認そのものが目的ではない。** 上限があるなら、外す余地はある。

先に決めること。

- **上限は何個か。** 人ごとか、契約の種類ごとか
- **上限に達したらどうなるか。** 作れないだけか、申請に切り替わるか
- **既存のリストを消したら枠は戻るか。** 削除しては作り直す使い方を
  許すかどうか
- **サイト管理者から見えるか。** 承認を通らないリストが増えるので、
  一覧で把握できないと管理不能になる（11.1）

**リスト名の重複判定（13.3 の名前予約）は承認の流れに組み込まれている。**
承認を飛ばす経路を作るなら、そこも通るようにすること。

#### 2-3. 容量の拡張（初期 2GB、10GB まで自動拡張）

**いまの作り：** 容量はリストごと、初期値 1GB。増やせるのはサイト管理者
だけ（7.2 / 11.1）。

先に決めること。

- **誰の容量か。** いまは**リストごと**。「プレミアムユーザーの容量」と
  すると、**持ち方が根本から変わる**（1 人が複数のリストに参加している）。
  ここが 1 の「課金の単位」と繋がる
- **自動拡張の条件。** 何割を超えたら、いくつ増やすか。
  いまは 80%／90% で通知しているので（7.3）、そこに繋げられる
- **10GB に達したらどうなるか。** 止めるのか、申請にするのか
- **解約したときどうするか**（1 の「解約したらどうなるか」と同じ論点）

**費用が自動で増える仕組みになる点に注意してください。**
Cloud Storage の料金は保存量に比例します。自動拡張は、
**人手を介さずに請求額が増える経路**を作ることになります。
仕様 12.1 で自動停止は実装しない方針なので、**予算アラートの設定は
この機能より先に済ませてください。**

### 3. 外部サービスに置いたままリンクする（Google ドライブ・OneDrive など）

**やりたいこと：** 本体は外部サービスに置いたまま、リンクだけを登録し、
聴くときは外部から直接鳴らす。

**いまの作りとの距離。** URL を登録する仕組みはすでにあります（6.2 の
`kind: 'url'`）。**足りないのは「その URL から音を鳴らす」ところ**で、
再生は Cloud Storage のファイルにしか繋がっていません（8.1）。

先に確かめること（**どれも未確認です。憶測で設計しないこと**）。

| 確かめること | なぜ |
| --- | --- |
| **共有リンクから、音として直接鳴らせるか** | サービスによっては、共有リンクを開くと閲覧用の画面が返り、音そのものは返らないことがあります。**まず 1 曲、実際に鳴らして確かめてください** |
| **他サイトからの再生が許可されているか（CORS）** | 許可されていないと、ブラウザが再生を拒みます |
| **非公開のファイルをどう扱うか** | 本人しか開けないファイルは、アプリから鳴らすのに**その人のアカウント連携（OAuth）が要ります**。連携を作るかどうかは大きな判断です |

決めること。

- **リンク切れをどう扱うか。** 外部で消された・移動された・共有を止めた
  ときに、こちらからは何も分かりません。**再生できなくなったことを
  どう伝えるか**を決めておく（「失敗しました」で終わらせないこと）
- **容量の計算に入れるか。** 本体は外部にあるので、こちらの使用量は
  増えません。**プレミアムの容量拡張（2-3）と、どう見せ分けるか**
- **公開範囲。** リンクを知っている人なら誰でも聴ける状態のまま
  登録されることがあります。リストの中だけに留まらない点を、
  登録する人に伝えるかどうか

**最初にやるべきは、実装ではなく「1 曲で試すこと」です。**
鳴らないと分かれば、そこから先の設計は要りません。

### 最初の表示までの待ち時間をさらに縮める（フォントの扱い）

取りに行き、それが遮断された環境で文字が出なくなるためです（`lib/app.dart`）。
**この前提は維持したうえで**、選べる手は次の 3 つです。

| 手 | 減る量 | 引き換えに失うもの |
| --- | --- | --- |
| **太字（700）を同梱しない** | 約 1.4MB | 太字が合成になる。日本語では線が太るだけで、字形は保たれる |
| **字を絞った版を作る**（常用漢字＋かな＋英数など） | 1MB 前後 | **絞った範囲外の字が豆腐（□）になる。** 表示名や曲名に珍しい漢字が入ると出ない |
| そのまま | 0 | — |

**推奨は「太字を同梱しない」です。** 失うものが見た目だけで、
文字が出なくなる危険がありません。

字を絞る手は効果も大きいのですが、**このアプリは利用者が自分で決めた
表示名や曲名を出します。** 名前の漢字が豆腐になるのは避けたいところです。
やるなら、どの範囲まで含めるかを決めてから着手してください。

**依頼者に選んでもらう論点として残しています。**

### 最初の表示までの待ち時間（残り。2026-08-08 の依頼者確認より）

**「早くはなったが、まだ数秒かかる」**（依頼者の実測）。
同日の対応（フォントを起動から外す／太字を廃止／Firebase SDK の先読み）で
縮んだが、まだ残っている。

いま起動時に必ず要るものは、これだけである。

| 取りに行くもの | 圧縮後 | 減らせるか |
| --- | --- | --- |
| CanvasKit（描画部） | 約 2.2MB | **ここが最大。** 下記参照 |
| `main.dart.js`（アプリ本体） | 約 0.85MB | 分割は Flutter Web では難しい |
| Firebase SDK 5 本 | 計 数百 KB | 先読み済み。**初期化を待つ構造自体**は残る |

**手として考えられるもの（未検討・未実測）。**

1. **`runApp` を Firebase の初期化より前にする。**
   いまは `await Firebase.initializeApp()` を終えてから `runApp` している
   （`lib/main.dart`）。先に画面を出し、初期化の完了を待つ間だけ
   読み込み表示にすれば、**SDK の到着を待たずに枠が出る**。
   ただし初期化前に Firebase を触るコードが 1 つでもあると落ちるので、
   触る場所を全部数えてからでないと着手できない。
2. **CanvasKit を減らす。** Flutter が用意する `skwasm` 等の選択肢を
   実測して比べる。**版によって前提が変わるので、まず実測すること。**
3. **Service Worker で 2 回目以降を速くする。**
   初回は変わらないが、2 回目以降は体感が大きく変わる。

**測り方を先に決めること。** 開発機のブラウザ枠では描画時刻を測れず、
今回は転送量と読み込み順で判断した。依頼者の開発者ツールでの実測が
唯一の当てになる数字だった。**「速くなったはず」で終わらせない。**

### 読み込み中に □（豆腐）が一瞬見える

**2026-08-08 の依頼者確認で判明。** 日本語フォントを最初の描画の
待ち時間から外した副作用。読み終わるまでの一瞬、端末側のフォントに
無い字が □ で描かれることがある。

**表示が壊れるわけではなく、フォントが届いた時点で直る。**
待ち時間を縮める効果のほうが大きいと判断して、いまは受け入れている。

消したい場合の手：

- **読み込み中は文字を出さない。** フォントが届くまでアプリ全体を
  読み込み表示にする。**それでは元に戻る**（待ち時間が復活する）ので、
  最初の 1 画面だけに限るなどの工夫が要る
- **よく使う字だけの小さなフォントを先に読む。** 全体を待たずに
  かなと常用漢字だけ先に当てる。ただし**範囲外の字は □ のままになる**
  ので、表示名や曲名に珍しい漢字が入ると直らない
- 端末のフォントを明示的に指定する（`fontFamilyFallback`）。
  □ が出るのは端末に字が無いときなので、効くかどうかは環境による

**どれも「一瞬の見た目」と「数秒の待ち時間」の取引になる。**
どちらを取るかは依頼者の判断。

### 定期実行の関数の確認（`purgeDeletedFiles`）

**自動テストの対象外です。** 89 件の統合テストは定期実行の関数を
一度も呼びません。**元から確かめる項目が無かった**ものであり、
2026-08-08 に減らしたわけではありません。

このため `functions/run-integration.mjs` は **Pub/Sub エミュレータを

確かめる価値は小さくありません。**消したファイルは戻せない**からです。
やるなら次の 2 つを見ます。

- 猶予期間（既定 30 日）を過ぎた項目のファイルだけが消えること
- 孤児ファイル（既定 24 時間）の判定が、生きているファイルを巻き込まないこと

`functions/src/domain/paths.ts` の判定自体は `npm test` の 85 件で
守られています。足りないのは**通しで動かしたときの確認**です。

### ~~users ドキュメントが、ログイン済みなら誰にでも読める~~ — 2026-08-11 に対応済み
