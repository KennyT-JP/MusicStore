# ゼロベース監査 追加確認項目（本プロジェクト固有）

社内共有版の「ゼロベース監査 手順書」に**追加して**使ってください。
手順書の 6 観点はそのまま実施し、各観点でここに挙げた項目も見ます。

追加のきっかけは、**その回の監査で見つけられなかった欠陥**です。
見つけられた欠陥は手順書がすでに拾えているので、ここには載せません。

---

## 観点 1・3 共通：クライアントとサーバーで「同じ制約」に触れていないか

> **1 回目（2026-08-06）で最も痛かった見落とし。**
> サーバー側の誤りは指摘できたのに、**クライアント側のまったく同じ誤りは
> 「動いているはず」と仮定して素通りした**。結果、リストを作ってもホームに
> 出ない状態が配信後まで残った。

- [ ] 同じ種類の問い合わせが、クライアントとサーバーの両方にないか探す
- [ ] 片方で問題が見つかったら、**もう片方を必ず実際に動かして確かめる**
- [ ] 言語やライブラリが違っても、**基盤の制約は共通**であることを疑う

**やり方：** 片方の誤りを見つけたら、その API 名（今回なら `collectionGroup`
`documentId`）でリポジトリ全体を検索し、**ヒットした箇所を 1 件ずつ実行して確かめる。**
読んで「正しそう」で済ませない。

## 観点 1・3 共通：コメントとルールが食い違っていないか

> **2 回目に見つかった。** セキュリティルールに
> 「連番はトランザクション、容量は Functions が更新する」とコメントしながら、
> その下は `allow write: if false` だった。**項目の追加が一度も成功しない**
> 状態が配信後まで残った。

- [ ] ルールのコメントが説明している動作を、**そのルールが実際に許しているか**確かめる
- [ ] 「クライアントが書く」と書かれた項目に、書き込みの許可があるか
- [ ] 全面禁止（`if false`）の隣に、例外を述べたコメントが無いか

**やり方：** ルールのコメントは「意図」であって「実装」ではない。
両者が食い違っていても誰も気づかない。**コメントを読んだら、その動作を
テストで再現する。**

## 観点 2：「一度も成功していない経路」を洗い出す

> テストが無い経路は、**壊れたのではなく最初から動いていない**可能性がある。
> 「以前は動いていた」という前提を置かない。

- [ ] テストが 0 件の経路を列挙する
- [ ] そのうち**利用者が最初に通る経路**（ログイン直後の画面など）を優先して実行する
- [ ] 画面を開いて「空です」と出たとき、**本当に空なのか、取得に失敗しているのか**を切り分ける

**やり方：** 空の表示は「データが無い」と「取れなかった」の区別がつかない。
取得そのものを、実データを入れた状態で 1 度は動かす。

- [ ] エミュレータと本番で**挙動が違う機能**を把握しているか
- [ ] 「エミュレータでは検証できない」と書かれた箇所は、**まず実際に試す**

> **「〜できない」と書かれた箇所こそ、まず試すこと。**

- [ ] 無ければ、実際に動いている実装がどこかを探し、そちらのテストの有無を見る

## 観点 4：前提が崩れると自動的に通る項目が無いか

> **2 回目に見つかった。** 統合テストでエミュレータのプロジェクト ID が
> 噛み合っておらず 24 件が FAIL した。そのとき「本人には届かない」

> 通知が 1 件も作られていないのだから、当然通る。

- [ ] 「〜が起きないこと」「〜が無いこと」を確かめる項目を数える
- [ ] その項目は、**前提が全部壊れていても通ってしまわないか**を考える
- [ ] 通ってしまうなら、前提そのものを確かめる項目が別にあるか

**やり方：** 否定を確かめる項目は、単独では意味を持たない。
「起きるはずの側」が同じ実行の中で確かめられていて初めて意味が出る。
前提の確認は最初にまとめて行い、崩れていればその場で止める。

## 観点 6：「名前が変わらない」を「中身が変わらない」と読み替えない

> **2 回の監査がどちらも見つけられなかった。** 配信の設定
> （`firebase.json`）でフォントを `immutable`（1 年、取り直さない）に
> していた。ところが Flutter はアイコン用の
> `MaterialIcons-Regular.otf` を、**そのビルドで使うアイコンだけに
> 削り込んで作り直す。** 名前は変わらないのに中身が変わるファイルである。
>
> 結果、**新しい画面が古いフォントで描かれ**、増やしたアイコンだけが
> 出なかった。ボタンは場所を取るが絵柄が無い、という出方をする。
> 強制リロードでも直らない。

- [ ] キャッシュを長く効かせている資産を列挙する
- [ ] そのうち、**ビルドのたびに作り直されるもの**が混ざっていないか
      （生成物・削り込まれるフォント・結合されたファイル）
- [ ] 「変わらない」と判断した根拠は、**ファイル名**か、**中身**か

**やり方：** 2 回続けて配信し、**同じ名前のファイルの中身が変わっているか**を
実際に比べる。名前だけを見て判断しない。
中身が変わりうるものに `immutable` を付けてはいけない。
`must-revalidate` なら、同じ内容のときは 304 が返るだけで転送量はほとんど変わらない。

**もう一つの教訓：** この不具合は**配信して初めて出る**。
ローカルでも、テストでも、ビルド成果物を調べても正常だった。
**「手元では動くのに配信先で動かない」ときは、アプリの外側**
（配信の設定・キャッシュ・ヘッダ）**を疑う層に入れること。**

## 観点 6：症状の原因を、アプリの中だけで探さない

> **2026-08-07 に 3 件続けて起きた。どれもアプリのコードは正常だった。**

> | 症状 | 原因のあった場所 |

- [ ] 当てはまるなら、**アプリの外側の層**を順に挙げる
      （ビルドの生成物・配信の設定・キャッシュ・クラウド側の権限）
- [ ] 層ごとに、**機械的に確かめる方法**があるか

**やり方：** 層を挙げてから、上から潰す。
今回効いたのは、生成されたフォントの中身を直接読む・
ビルドした成果物をヘッドレスブラウザで動かす、といった
**推測を挟まない確認**だった。スクリーンショットの目測は当たらない。

## 観点 2：例外を握りつぶすことは、欠陥そのものとして扱う

- [ ] 絞れないなら、詳細を読める導線があるか

**やり方：** 「失敗しました」とだけ出す作りは、**直す機会そのものを奪う。**
利用者向けの文言はやさしいままでよいが、
技術的な内容へ辿り着ける道を必ず残す。

## 観点 2：テストの中の「除外」が、環境によって効かなくなっていないか

- [ ] テストの中に「この範囲は除く」という判定はあるか
- [ ] その判定は、**実行する環境が変わっても同じ意味になるか**
      （パス区切り・改行・大文字小文字）
- [ ] 除外が効かなくなったとき、そのテストは**落ちるか、通るか**
      通るなら、それは前提が崩れると自動的に通る形である

**やり方：** 除外を書いたら、**除外が効かない場合を 1 度作って**
テストが落ちることを確かめる。パスは `test/support/repo_files.dart` の

## 観点 3：作り直したのに、前の作りの「選ばせる場所」が残っていないか

> **2026-08-08。** 招待 URL を共有リンクに作り直したとき、
> 「無期限・何度でも・複数人」は直したのに、
> **発行する側が相手の役割を選ぶ**という前の作りだけ残していた。
> 依頼は「単純にリンクで送る」だったので、依頼者から作り直しを指摘された。
>
> テストは全件緑だった。**残していた場所そのものを固定するテストを
> 書いていた**ためである（「付与できる役割は Super User と
> Read Only だけ」）。消すべきものを守るテストは、消し忘れを隠す。
>
> 入口が 3 か所あり、そのうち曲の詳細だけ Read Only 固定になっていた。
> **入口ごとに結果が違う**のは、作りが 1 つに決まっていない印である。

- [ ] 作り直した機能に、**利用者が選ぶ場所**はいくつ残っているか
- [ ] その選択は、**選ぶ人がその答えを知っている**か
      （配る側は、相手が参加するかどうかも知らない）
- [ ] 同じ機能の入口が複数あるとき、**どれを使っても結果は同じ**か
- [ ] その選択肢を固定しているテストは、**残すべきものを守っているか**
      作り直しで消す予定のものを守っていないか

**やり方：** 依頼に「単純に」「そのまま」と書かれていたら、
実装後に**押すまでに何回選ばせているか**を数える。
0 回にできないか、まず疑う。

**さらに（2026-08-08）。** 選択肢を消したあと、
**その判断がどこへ行ったかを見ること。**
このときは、画面から消した代わりに同じ判断を
リンクのドキュメントへ書き込んでいた。
利用者から見れば選ぶ操作は消えているので、直ったように見える。

- [ ] 消した選択肢の判断は、**本当に無くなったか**。別の場所へ移しただけではないか
- [ ] 移した先が**人に渡るもの**（URL・ファイル・QR・共有 ID）なら、
      それを渡すこと自体が権限を配る行為になっていないか
- [ ] そこに書いた値は、**転送されても困らないか**

## 観点 2：手順書に「窓を 2 つ開く」と書いてあるものは、実行されていないと疑う

> **2026-08-08。** 統合テスト 61 件は「1 枚目で `npm run serve`、
> 2 枚目で `npm run test:integration`」という手順だった。
> **一度も実行されていなかった。** 期待値が古いまま赤く、
> **そのまま本番まで配信されていた。**
>
> しかも件数は、実行せずに手で 58 → 61 と書き換えられていた。
> 実際は 60 だった。**数が合わないことに誰も気づけない。**
>
> `rules-test` は最初から自分でエミュレータを起動して落とす形
> （`emulators:exec`）だったので、124 件は毎回そのまま走っていた。
> **同じリポジトリの中に、実行される形と実行されない形が並んでいた。**

- [ ] 手順が「窓を 2 つ」「別のターミナルで」を要求していないか
- [ ] そのテストは、**最後にいつ実行されたか**が分かるか
- [ ] 書いてある件数は、**実行して数えたもの**か
- [ ] 同じリポジトリに、自動で完結している実行役が別にないか。あるなら揃える

**やり方：** 人が 2 つの窓を並べる前提の手順は、**書いてあっても実行されない**。
`emulators:exec` のように、起動から後片付けまでを 1 つのコマンドに収める。

## 観点 2：環境が変わったら、「できない」と書いた申し送りを疑い直す

> **2026-08-08。** 申し送りには「作業用コンテナでは `rules-test` が
> 8 件スキップされる」「統合テストは実行できない」「配信はできない」と

>
> 実際に動かしたところ、rules-test は **124 件すべて通り**、
> 統合テストも通り、**配信もできた**。
>
> 1 回目の申し送りは「**『〜できない』と書かれた箇所こそ、まず試すこと**」。
> **同じことを、環境が変わった側からも言う必要がある。**

- [ ] 申し送りの「できない」に、**そのときの環境**が書かれているか
- [ ] いまの環境は、そのときと同じか
- [ ] 違うなら、**先に試してから**申し送りを引き継ぐ

**やり方：** 制約を書くときは「**この環境では**」を必ず添える。
添えられていない制約は、環境が変わった瞬間に嘘になる。

## 観点 6：道具が要求する版は、道具が変わると上がる

> **2026-08-08。** `docs/SETUP.md` には「Java 11 以上」と書いてあった。
> ところが `firebase-tools` 15.24 は **Java 21 以上**を要求する。
> 17 を入れても `Please install a JDK at version 21 or above` で止まる。
>
> さらに、17 と 21 が両方入っている環境で、実行役が**先に見つけた 17 を
> 掴んで**失敗した。「入っているか」だけを見ると古いほうを選ぶ。

- [ ] 手順書に書いた版の要件は、**いまの道具**の要件と一致しているか
- [ ] 複数の版が入りうるもの（JDK・Node・Python）を探す処理は、
      **版まで見て選んでいるか**。「見つかった最初のもの」で済ませていないか

## 観点 1・6：設定を生成する道具が、別の設定を壊していないか

> **2026-08-08 に原因が判明。** 申し送りには
> 「`firebase.json` が勝手に書き換わる事象が **2 回**起きた。
> どちらも 100 行前後が 1 行に潰れていた。原因は不明」とあった。

> **犯人は `flutterfire configure`** だった。接続設定を生成すると、
> ついでに `firebase.json` を読み書きして整形し直す。
> このとき**キャッシュ指定（アイコンが出ない不具合の修正）が丸ごと消える。**
>
> 生成する道具は、**頼んだファイル以外にも触る。**

- [ ] 設定を生成する道具を動かしたら、**その直後に `git status` を見る**
- [ ] 想定していないファイルが変わっていないか
- [ ] 変わってよいファイルと、捨てるファイルを手順書に書いてあるか

**やり方：** 「このファイルを作る道具」と言われても、それだけを触るとは限らない。
実行の前後で作業ツリーの差分を比べる。
