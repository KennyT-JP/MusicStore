## 3. 主な発見と対処

### 3.1 【高】ユーザー削除が、本番では一度も成功しない形だった

`deleteSiteUser` は削除対象の曲を `collectionGroup('items').where('createdBy', ==, uid)`
で引くが、**コレクショングループ範囲の単一フィールド索引が宣言されていなかった**。
Firestore が自動で作るのはコレクション範囲だけなので、クラウドでは
FAILED_PRECONDITION になり、ユーザー削除は必ず失敗する。

**エミュレータは索引を強制しないため、統合テスト 75 件は緑のまま**だった。
第 3 回申し送りの「手元では動くのに配信先で動かない」の型そのもの。
観点 1 と観点 6 が独立に同じ箇所を指した。

さらに `leaveAllLists` の `collectionGroup('viewers')` も同じ欠落で、こちらは
`.catch(() => [])` が失敗を握り潰すため、**無効化・削除・退会のたびに閲覧者の
掃除が黙って空振りし続ける**形だった（「例外を握りつぶすことは欠陥そのもの」
—— 第 3 回で自分たちが書いた観点に、また引っかかった）。

対処: fieldOverrides に items.createdBy / viewers.uid を追加。握り潰しを廃止。

### 3.2 【中】ログイン可能なサイト管理者が 0 人になる経路があった

「最後の 1 人のサイト管理者は降格・退会・削除できない」の人数計算
（scanSiteAdmins / countSiteAdmins）が **`user.disabled` を除外していなかった**。
管理者 A・B のうち B を無効化しても B は数に入り続けるため、その後 A を
降格・削除すると、ログインできる管理者がいなくなる。

対処: 無効化済みを人数から除外。統合テストに「無効化後は残る 1 人が最後の
1 人として守られる」ケースを追加。

### 3.3 【中】削除済みコメントを、本人が黙って復活できた

comments の update ルールは createdBy の不変しか課しておらず、**status を
制約していなかった**。項目side には「復元はリスト管理者のみ」（restoreIsAllowed）が
あるのに、コメント側に相当物が無い。API を直接叩けば、リスト管理者が削除した
コメントを投稿者本人が active に戻せる。

対処: deleted→active はリスト管理者のみ、をルールに追加。ルールテストに
肯定・否定の対で追加し、ルールを一時的に戻す対照実験で赤くなることを確認。

### 3.4 【中】サイト管理者を削除しても、内部の管理者一覧に残り続けた

`deleteSiteUser` がサイト管理者を消したとき `syncSiteAdminCount` を呼んでおらず、
siteConfig の siteAdminUids に消えた uid が残る。以後、**存在しないユーザーの
notifications へ通知が書き込まれ続ける**。withdrawAccount も同様の未同期
（こちらは isWithdrawn が通知を止めるため実害は人数のみ）。あわせて
withdrawAccount は members しか外しておらず、退会者が閲覧者一覧に残っていた。

対処: 両関数で同期を呼ぶ。viewers も外す。

### 3.5 【高】統合テストは、接続が一瞬切れただけで全体が死んでいた

5 本並列の検証（check.mjs）が監査当日 2 回中 2 回赤くなり、1 回目の原因は
統合テストの **fetch が接続リセットで未捕捉例外**になったことだった（単独では
緑 = 一過性）。時間切れには 180 秒の余裕を持たせてあったが、**接続リセットは
その歯止めの外**にあった。「遅いだけで落とさない」方針の残っていた穴。

対処: 接続系エラーに限って短いリトライを追加。

### 3.6 【高】見張りのテストに、実験で実証できた抜け道が 6 つあった

第 2 回・第 3 回で足してきた見張り（watchdog）そのものを今回初めて対照実験に
かけた。**6 つの見張りすべてに、検出をすり抜ける実証済みの穴があった。**

| 見張り | 抜け道（実験で実証） |
| --- | --- |
| no_dead_code_test.dart | **コメントに名前を書くだけ**で「呼び出しあり」に数えられる。入れ子ジェネリクス（`Future<List<X>>`）の関数はそもそも走査対象外 |
| no_dead_code.test.ts | 自ファイル内で自己参照する export は検出されない。index.ts のコメントに載った名前は無条件免除 |
| discipline.test.js | `import { assertSucceeds as sneak }` の**別名 import で素通し**。対象が直下 *.test.js のみで、vitest が実行する *.spec.js 等は見張りの外 |
| web_startup_test.dart | **HTML コメントの中でも contains が真**。modulepreload 5 本を全部コメントアウトしても 23 件緑のまま |
| setup_doc.test.ts | `export const X =`（改行）`onCall` と書くと一覧から漏れる |
| signup_locale_test.dart | 規則テストが**テスト内の写し**を検証しており、本番の fallback を壊しても 5 件緑のまま |

見張りは「置いた」ことで安心し、**見張り自体を試すことを 2 回の監査で
一度もしていなかった**。今回の最大の教訓。

対処: 6 件すべて修正（コメント除去してから数える・import 自体を禁止する・
実行範囲と見張り範囲を一致させる・写しをやめて本物を検証する、等）。

### 3.7 【高】「テストは緑・本番は別のコード」が、また出た（4 回連続）

| 回 | 内容 |
| --- | --- |
| 第 1 回 | 連番と招待 URL のロジックが本番から 0 参照 |
| 第 2 回 | Permissions の 6 メソッドが本番から 0 参照 |
| 第 3 回 | canWrite / isMember（TS）が本番から 0 参照 |
| **第 4 回** | **QuotaPolicy の通知境界 3 メソッドと SequencePolicy（Dart）が本番から 0 参照** |

毎回見張りを足しているのに再発するのは、**見張りの粒度が荒い**からだった
（モジュール単位で見るため、同じファイルに 1 つでも使用中の関数があると
死蔵メソッドが素通しになる）。3.6 の粒度拡張とあわせて対処。
本番で効いているのはサーバー側（functions/src/domain/quota.ts）なので、
Dart 側の写しはテストごと削除し「サーバーが正」の方式に揃えた。

### 3.8 【中】配信の Cache-Control は「後に書いたブロックが勝つ」

firebase.json の headers で、no-cache 指定の**後ろ**に `**/*.@(js|json)` の
1 時間キャッシュが書かれていたため、flutter_service_worker.js /
flutter_bootstrap.js / version.json の no-cache が**上書きされて無効**だった
（本番の実ヘッダで確認）。さらに `/` や深いパス（rewrite で index.html が
返る）はどのブロックにも一致せず、既定の 1 時間キャッシュになっていた。
「must-revalidate で毎回確認」というコメントも誤解で、max-age の間は
一切問い合わせない。ビルドのたびに中身が変わる MaterialIcons の混在事故
（第 3 回）は、実は 1 時間の窓で今も起こり得た。

対処: 「後勝ち」を前提に headers を並べ直し（包括 no-cache → 資産の長期
キャッシュ → 最後に index.html・SW・MaterialIcons の no-cache）、
hosting_cache_test.dart を実効ヘッダの検証に強化。

## 5. 今回分かったこと（次回への申し送り）

1. **見張りを置いたら、見張り自体を壊してみること。** 6 つの見張り全部に
   実証可能な抜け道があった。「見張りがある」は「守られている」ではない。
   見張りを足すときは、すり抜ける書き方を 1 つ以上試してから置く。
2. **エミュレータは索引を強制しない。** collectionGroup クエリを足したら、
   firestore.indexes.json への宣言を必ず対にする。統合テストの緑は
   索引の正しさを何も保証しない。
3. **「後に書いたものが勝つ」設定は、順序が仕様。** firebase.json の headers は
   追記した場所によって既存の指定を黙って無効化する。追記のたびに、
   実際に配信されたヘッダを見る（今回は本番の実ヘッダで裏取りした）。
4. **人数を数える処理は、数える対象の定義から疑う。**「サイト管理者の数」に
   無効化済みが入っていた。数を守るテストは、境界（無効化・退会・削除）を
   またいだ直後の数を見ること。
5. 環境が変わって「できない」が消えた（統合・ルールテストとも監査環境で
   実行できた）。第 3 回の申し送りどおり、制約は環境ごとに疑い直す。
