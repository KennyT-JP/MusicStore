## 1. 概要・目的

メンバーが個々に録音した音源や、YouTube 等で見つけた楽曲を、1 つのリストに集約して共有するためのアプリです。Web 版を先に開発し配信済み。**Android / iOS ネイティブは土台を実装済み**（APK / ipa がビルドでき、ipa は App Store Connect まで上がっている）で、**実機確認とストア審査が残る**（`MOBILE-APP-DESIGN.md`）。リストは複数作成でき、管理者がメンバーのアクセスを承認・管理します。

## 3. アカウント・認証

### 3.1 ログイン方法
- Google アカウント連携
- メールアドレス＋パスワード
- **iOS では Sign in with Apple も**。判定は `AuthRepository.isAppleSignInAvailable`（規則は `lib/domain/apple_sign_in.dart` の `AppleSignInPolicy`）で、**iOS ネイティブのときだけ**ボタンを出す。Web と Android には出さない（Apple 側に Services ID と戻り先 URL の登録が別途要るため。詳細は `MOBILE-APP-DESIGN.md`）。
- **ログイン状態を保持**する（次回以降、自動でログインした状態を維持）
- メール＋パスワード登録者向けに、**パスワード再設定機能**（登録メールにリセット用リンクを送付）を用意

#### メールアドレスの確認（本人確認）

- **メール＋パスワードで登録した場合、メールアドレスの確認を必須**とする。
  - 登録すると確認メールが送られ、**リンクを押すまでアプリを利用できない**（ログインはできるが、「確認メールを送りました」の案内画面で止まる）。
  - 確認メールの再送ができるようにする。
  - **確認メールは、送る人がいま画面に出している言語で送る**（2 章）。
    指定しないと Firebase の既定（英語）で届き、日本語の画面なのに英語のメールが来る。
  - **リンクを開いたら、待っている側の画面も自動で先へ進む。**
    リンクは別のタブ（別の端末のこともある）で開かれるため、
    アプリ側は数秒ごとに確認を取り直す。押して進める操作も残す。
- **Google アカウント連携での登録は確認不要**（Google 側で確認済みのため）。
- 未確認のまま共有リンクを受け取った場合も、**確認を済ませてから選ぶ**（3.3）。

### 3.1.1 未ログイン状態で URL を開いた場合

- 共有 URL（`/lists/…`）・共有リンク（`/s/…`）のいずれも、**未ログインでは内容を一切表示しない**（リスト名も出さない）。まずログイン／サインアップ画面を表示し、**完了後（メール確認を挟む場合も含めて）に元の URL へ自動的に戻す**。戻った先で、共有 URL ならリスト名と参加申請ボタン（5.3）、共有リンクなら「メンバーになる／ならずに見る」の選択（3.3）が出る。
- 「メンバーにならずに見る」ほうもログインは要る（誰が見ているか分からない状態にしないため）。
- **ログイン済みの人は、開いた URL の画面が直接出る。** 起動時はログイン状態の復元が終わるまで画面遷移の判定を待つ（復元前に「未ログイン」と誤判定すると、ログイン済みの人にログイン画面が見えてしまうため）。
- URL を偶然拾っただけの第三者に、リスト名が漏れないようにするための扱い。

### 3.2 アカウント取得の 2 経路（両方対応）
1. **自己登録**：誰でも Google／メールでサインアップ可能。その後、リスト作成やリスト参加を申請できる。
2. **共有リンク経由**：サイト管理者・リスト管理者が共有リンクを発行して渡す（3.3）。

### 3.3 共有リンクの仕様

**2026-08-07 に作り直しました。** 以前は「ワンタイム・24 時間で期限切れ」の
招待 URL でした。渡した相手が期限内に開けないと配り直しになり、
複数人に配ることもできませんでした。

- 共有の操作を行うと、**共有リンク**が発行される。
- **有効期限は無い。何人でも、何度でも使える。**
- 管理者が任意の手段（メール等）でその URL を相手に伝える。
- **リンクは 1 種類だけ。役割という概念を持たない。**
  発行時に指定するのは**対象リスト**（と、曲を指すなら**その曲**）だけ。
  **URL は「どのリスト（どの曲）か」以外の意味を持ってはいけない。**
  リンクに役割を載せると、その URL を渡すこと自体が書き込み権限を
  配ることになる。渡された人が転送すれば、そのまま広がる。
- **選ぶのは受け取った人だけ。** 配る側にも、サーバーにも、
  「この人をどう扱うか」を決める場所を置かない。
- 発行できる人：**サイト管理者は誰に対しても**発行可／
  **リスト管理者は自分のリストへのリンクのみ**発行可。
- **発行の入口は 3 か所。どれも押すと同じ 1 本のリンクができる。**
  - ホームのリスト行の「リンクをコピー」（押すとその場で URL がクリップボードへ入る）
  - メンバー管理画面（発行した URL を画面に出す。取り消しもここから）
  - **曲の詳細**（その曲を指すリンク。開くとその曲が出る）
- URL を渡すときは、**期限が無く何度でも使えること**を必ず添える。
  配ったあとも生き続けるので、渡す相手を選ぶ判断がそこで要る。

#### 受け取った人が選ぶ

**リンクを開いた人は、その場で 2 つから選ぶ。**

| 選択肢 | 何が起きるか |
| --- | --- |
| **リストのメンバーになる** | メンバーになる。**曲やコメントを追加できる**（Super User）。メンバー一覧に名前が出て、曲が追加されると通知が届く |
| **リストのメンバーにならずに見る** | メンバーにならない。曲の一覧を見て、音を聴くことはできる。メンバー一覧には出ず、通知も届かず、書き込みもできない |

（文言は 2026-08-08 の指示で「参加する／参加せずに見る」から変更。
英語表示は "Become a list member" / "View without becoming a member"）

- **押す前に、それぞれ何が起きるかを画面に書く。** 押したあとで
  「そういうことだったのか」となる作りにしない。
- **どちらを選んでもログインとメール確認は必要。**
  誰が中身を見ているか分からない状態にしないため。
- 「メンバーにならずに見る」を選んだあとでメンバーになりたくなったら、
  **同じリンクをもう一度開けばよい**。その旨も画面に書く。
- 参加せずに見ている人は `lists/{listId}/viewers` に入る（13.3）。
  **メンバーの人数にも通知の宛先にも入らない。**
  誰が見ているかは、メンバー管理画面でリスト管理者に見える。
- **閲覧者は、そのままリストの中身へ入れる**（v1.5）。
  共有リンクを開いた時点で受け入れが済んでいるので、**参加申請は要らない。**
  画面側も閲覧者を「見られる人」として扱う（`ListAccess.isViewer`）。
  ここを落とすと、見る権利を持っているのに参加申請の画面へ送られる。
- **見られることと、書けることは別。** 閲覧者に役割は与えない。
  項目やコメントの追加、メンバー管理、共有リンクの発行はいずれも不可。
- **参加した人は Super User で入る**（`domain/roles.ts` の
  `INITIAL_JOIN_ROLE`）。**リンクが役割を決めるのではない。**
  役割を決めるのはサーバー側のこの 1 か所だけで、リンクの中身は見ない。
  リンクを配るのは相手を招いた人なので、招かれた側は曲を足せる。
  見るだけでよい人のために「メンバーにならずに見る」があり、
  **参加を選んでも書けないままでは、2 つの選択肢が同じ意味になる。**
  URL が広まったと分かったときは、**リンクを取り消す**（この節の「取り消し」）。
- **v1.2 では Read Only にしていた（v1.9 で戻した）。** 2026-08-08 の
  「URL は単なるリンクでしかなく、それ以上の意味を持たせてはいけない」
  というご指示に対し、リンクから役割を外すのと同時に、**指示されていない
  初期役割まで引き下げていた**（依頼者の承認なし）。
  **リンクが役割を運ばないことと、参加した人がどの役割になるかは別の話。**
- **書けるようにするかどうかは、リスト管理者が後から決める**（5.4）。
  メンバー管理から役割を上げる。リンクからリスト管理者にはならない。

#### リンクを受け取ってから中に入るまでの流れ

アカウントを持っているかどうかで分岐せず、**どちらの場合も URL を
1 回開くだけで済む**ようにする。

| 状態 | 流れ |
| --- | --- |
| ログイン済み | URL を開く → 選ぶ → 完了 |
| ログアウト中（アカウントあり） | URL を開く → ログイン → **元の URL へ自動で戻る** → 選ぶ → 完了 |
| アカウント未取得 | URL を開く → サインアップ → （メール登録の場合はメール確認／3.1）→ **完了と同時に元の URL へ戻る** → 選ぶ |

#### 止める手段は取り消しだけ

**期限が無いということは、一度配ったリンクを止める手段が
取り消ししか無いということでもある。** 以前は期限切れが事実上の
歯止めになっていた。

- 取り消すと、そのリンクからは参加も閲覧もできなくなる。
- **すでに参加した人・閲覧中の人はそのまま残る。**
  外すのはメンバー管理から行う。
- 取り消し済みと「リンクが違う」は**別の文言**で伝える。
  受け取った人が次に取る行動が違うため
  （取り消し → 新しいリンクを依頼／見つからない → URL を確かめる）。
- リンクの ID は推測できない長さにする（13.3）。
  **期限が無いぶん、ID の推測されにくさがそのまま守りになる。**

### 3.4 表示名
- 初期値は次の順で決める。

  1. 登録画面で入力された名前
  2. Google 連携で得られた表示名
  3. メールアドレスの `@` より前
  4. 「ユーザー」

- **1 を必ず先に見ること。** Firebase の `updateDisplayName` はサーバー側を更新するだけで、手元のユーザー情報の表示名は取り直すまで空のままになる。2 を先に見ると、入力された名前があるのに 3 が採用される（実際にそうなっていた／`domain/display_name.dart` の `initial` と回帰テストで固定している）。
- ユーザーが後から自由に変更可能。

### 3.5 退会（アカウント削除）
- ユーザーは自分のアカウントを自分で削除（退会）できる。
- 退会後も、その人が登録した項目・コメント等の**投稿・履歴は残す**。表示名は「**退会したユーザー**」と表示（元の名前は出さない）。
- **例外**：自分が**最後のサイト管理者**である場合は退会できない（4.4 参照）。

## 4. 権限・役割

### 4.1 権限階層
```
サイト管理者 ＞ リスト管理者 ＞ Super User ＞ Read Only
```
- 上位の役割は、下位の役割の権限を**すべて包含**する。
- 役割は**リストごとに個別**に決まる（例：あるユーザーがリスト A では Super User、リスト B では Read Only、も可能）。

### 4.2 各役割の主な権限
| 役割 | 主な権限 |
| --- | --- |
| サイト管理者 | サイト全体の全権限。全リストの項目・コメントの編集・削除、全リストの削除、権限変更、リスト作成申請の承認、各種サイト設定 |
| リスト管理者 | 自分が管理するリスト内の全権限（項目・コメントの編集・削除、リスト削除、メンバー招待・承認・役割割当・除外、容量把握 等） |
| Super User | リストへの項目追加・アップロード、コメント・返信 |
| Read Only | 閲覧のみ（全項目・全コメントの閲覧、音源再生・URL アクセス可）。追加・コメントは一切不可 |

### 4.3 権限の管理
- 各ユーザーの役割変更は、**サイト管理者・リスト管理者**が行う。
- 管理者自身もアップロード・コメントができる（上位は下位の権限を包含するため）。

### 4.4 サイト管理者の初期設定
- 最初のサイト管理者は、**システムを立ち上げた人**を初期サイト管理者として登録する。
- 以後、サイト管理者は他の人をサイト管理者に昇格できる。

### 4.5 サイト管理者が 0 人になることの防止

サイト管理者が 0 人になると、リスト作成申請の承認も権限変更もできなくなり、**アプリ内からは誰も復旧できない**。これを構造的に防ぐ。

- **サイト管理者が 1 人しかいない場合、その人は自分を降格できず、退会もできない**。
- 該当する操作をしようとした場合は、次のように案内してブロックする。
  > 「あなたは現在ただ 1 人のサイト管理者です。先に別の方をサイト管理者に指名してください。」
- 判定はサーバー側（Cloud Functions）で行う。画面上でボタンを無効化するだけでは、他の経路からの操作を防げないため。
- サイト管理者の人数は `siteConfig/global` に保持し、昇格・降格・退会のたびに更新する（13.3）。

> **補足**：リスト管理者については、0 人（管理者不在）になることを許容し、サイト管理者が後から指名する運用としている（5.6）。サイト管理者だけは上位の救済先が存在しないため、扱いを分けている。

## 5. リスト管理

### 5.1 リスト作成（申請制）
- 新規リストは**サイト管理者への申請制**。
- 申請に必要な情報：
  - **リスト名**（申請時に、既存の全リストと**重複チェック**を行う）
  - 概算の**登録曲数**
  - **使用者数**
  - **作成目的**
- サイト管理者が申請を確認して承認する。
- 承認されると、**申請者がそのリストのリスト管理者**になる。
- 申請は**初期ユーザーを含め、誰でも**可能。

### 5.2 既存リストへの参加（2 経路）
1. **共有リンク経由**（3.3 参照）。
2. **参加申請**：リストの共有 URL から参加を申請する。
   - 申請者は役割を選べない（**アクセス申請のみ**）。
   - **リスト管理者が承認時に役割（Super User / Read Only）を決定**する。

### 5.2.1 申請の状態確認と却下後の扱い（リスト作成申請・参加申請の共通ルール）

- ユーザーは**自分が出した申請の一覧と状態**（申請中／承認／却下）を、いつでも画面で確認できる。
- **却下されても通知は送らない**（10.2 のとおり）。ただし申請一覧を見に行けば「却下」と分かる。
- **却下された後は、同じ申請をやり直せる**。回数の制限は設けない。
- 却下理由は入力させない（管理者の負担と気まずさを避けるため）。

> **意図**：通知を送らないのは「わざわざ知らせない」ためであり、「隠す」ためではない。申請者が永遠に待ち続ける状態や、管理者への問い合わせが発生する状態を避ける。

### 5.3 リストの見え方・発見方法
- 全リストの一覧を公開する画面は**作らない**。
- リストは、**既存参加者から共有 URL をもらって**発見・申請する。
- 未参加者が共有 URL を開いた場合：**リスト名など最低限の情報＋「参加申請」ボタンのみ**を表示。中身（曲・コメント）は承認されるまで見えない。

### 5.4 メンバーの除外・離脱
- **リスト管理者（以上）**は、メンバーをそのリストから外す（アクセス権を取り消す）ことができる。
- **メンバー自身**も、自分からリストを抜けることができる。
  - 導線は**リスト詳細のメニュー**に置く。役割を問わず、そのリストのメンバー全員に出す。
    以前はメンバー管理画面にしか無く、その画面はリスト管理者以上にしか導線が無かったため、
    **Super User と Read Only は抜ける手段が無かった**（監査 第2回）。
- 外された／抜けた後も、その人の投稿・履歴は残す。表示名は「**退会したユーザー**」と表示。
- **除外・離脱した人は、あらためて参加申請できる**（5.2）。除外された人と自分で抜けた人を区別せず、どちらも同じ扱いとする。
  - 入れ直すかどうかはリスト管理者がその都度判断する。ブロックリストのような仕組みは設けない。
  - 誤って外してしまった場合も、共有リンクを渡すか申請を承認すればすぐ戻せる。
- **リスト管理者自身が抜ける場合**、そのリストのリスト管理者が自分ひとりであれば、抜けた時点で**管理者不在のリスト**になる（5.6）。サイト管理者が別の人を指名するまでその状態が続く。

### 5.5 リスト削除
- **リスト管理者**は自分のリストを削除できる。
- **サイト管理者**は全リストに対して全権限を持つ（どのリストでも削除可）。
- リストを削除すると、そのリストのファイル・コメントも**すべて削除**される。

### 5.6 管理者不在時の扱い
- リスト管理者が 1 人だけの状態でその人が退会した場合、そのリストは**管理者不在のまま保持**する。
- **サイト管理者が新しいリスト管理者を指名する**まで、その状態を維持する。
- サイト管理画面で「管理者不在のリスト」を確認・指名できるようにする。

### 5.7 サイト管理者がメンバーに加える

- **サイト管理画面のユーザー一覧**から、その人をリストのメンバーに加えられる。
  一覧の各行のメニュー →「リストに追加」→ リストを選ぶ → **役割を選ぶ**。
- **なぜ要るか。** これまで人がリストに入る道は3つで、いずれも**入る側か、
  そのリストの管理者の操作**を要した——参加申請（5.2）・共有リンク（3.3）・
  管理者不在時の指名（5.6）。**運営が「この人をこのリストに入れておく」
  ことができなかった。**
- **付けられる役割は Super User と Read Only のみ。** リスト管理者にはできない
  ——それは 5.6 の指名の仕事で、意味も条件も違う。
- **役割は必ず選ばせる**（既定を決め打ちにしない）。加える人が曲を足せるのか
  見るだけなのかは、加える側が知っていることで、システムが推測してよいもの
  ではない。承認（5.2）と同じ考え方。
- **すでにメンバーなら断る。** 役割の上げ下げはリスト管理者の仕事（5.4）で、
  ここで黙って書き換えると、**リスト管理者が決めた役割をサイト管理者が
  知らずに巻き戻す**ことになる。
- 退会した人・無効にされた人は加えられない（画面にも項目を出さない）。

## 6. リスト項目

### 6.1 項目の単位
- 1 項目 ＝ **音源ファイル 1 つ**、または **URL 1 つ**（両方の混在・複数登録は不可）。

### 6.2 項目が持つ情報
| 項目 | 内容 |
| --- | --- |
| 連番 | リストごとに 1 から採番。**振り直しなし**。削除時は欠番を残し、リスト上に「**削除されました**」と表示（ソフト削除） |
| 日付 | 録音日を想定（ただし厳密な意味は持たせない）。初期値は当日、**自由に変更可**。**時刻もタイムゾーンも持たない「年月日」だけの値**（下記） |
| ファイル または URL | 音源ファイル、または URL のいずれか |
| 曲名 | **任意** |
| アーティスト名 | **任意** |
| 登録者 | **ログインユーザーを自動記録** |
| コメント | **任意**（追加・アップロード時に記入できる） |

#### 日付の扱い（タイムゾーン）

- 項目の「日付」は、**時刻もタイムゾーンも持たない年月日の値**として保存する（`2026-08-04` のような文字列相当）。
- **どの国・どの端末から見ても、登録した人が入力したとおりの日付が表示される**。時差による 1 日のずれは発生しない。
- 初期値の「当日」は、**入力する人の端末のローカル日付**を用いる。
- これはユーザーが意味を持たせる日付（録音日）に限った扱い。**投稿日時・更新日時などのシステムが記録する日時は、通常のタイムスタンプとして保存し、見る人の現地時刻で表示**する。

### 6.3 編集・削除

- 項目の**全フィールドを編集可能**。**ファイルの差し替えも実装済み**（13.4 参照）。編集画面でファイルを選び直すと差し替わる——クライアントが新しいファイルを**別名で**アップロードしてから、サーバーの `replaceItemFile`（`functions/src/callable/items.ts` → `functions_repository.dart` → `item_form_screen.dart`）が項目の指す先を移す。差し替えても**連番は振り直さない**（6.2）。URL の差し替え、ファイル ↔ URL の切り替えも通る。
- 編集・削除できる人：**登録した本人**、および自リストのリスト管理者、サイト管理者（4.2 参照）。
- **削除には猶予期間がある**。削除した項目は一覧上「削除されました」と表示されるが、ファイル本体は**一定期間（初期値 30 日）Storage に保持**され、その間はリスト管理者以上が**復元できる**。猶予期間を過ぎるとファイルは完全に削除され、使用容量が減る（詳細は 13.4）。
- **ファイルを差し替えた場合も、旧ファイルは同じ猶予期間だけ保持**される。`replaceItemFile` が旧 `file` を `previousFiles` に積み（`purgeAt` 付き）、猶予を過ぎたら定期実行の掃除が実体を消す（13.4）。
- 猶予期間中は**容量を消費し続ける**ため、上限に近いリストでは削除してもすぐには空きが増えない点に注意（7.2）。

#### 同時編集の扱い

2 人が同じ項目（またはコメント）を同時に編集していた場合、**後から保存した人が、先に保存された内容を知らないまま上書きしてしまう**ことがある。バックアップを持たない方針（12.3）のため、これを防ぐ。

- 編集画面を開いた時点の更新日時を保持しておき、**保存時に「開いてから他の人が更新していないか」を確認**する。
- 更新されていた場合は**保存を中止**し、次のように表示する。
  > 「ほかの方がこの項目を更新しました。最新の内容を読み込み直してください。」
- ユーザーは最新内容を読み込み直したうえで、編集をやり直す。
- **編集中のロックは行わない**（ブラウザを閉じられたときにロックが残るため）。
- この確認はサーバー側（Firestore のトランザクション）で行い、画面上のチェックだけに頼らない。

### 6.4 表示・並び替え・検索
- **並び替え**：連番／日付／登録者 で並び替え可能。
- **検索**：曲名・アーティスト名で検索。曲名・アーティスト名が未記入の項目は、**ファイル名で検索**できるようにする。
- リスト上は、URL やファイル名を**そのまま表示**する。
  - **音として鳴らせるファイルは、一覧の左の再生ボタンからその場で鳴らせる**（8.1）。
  - **URL を開く・ダウンロード・音源以外のファイルを開く操作は、一覧の各行の右に専用ボタンで置く**
    （`ItemExternalAction`／`lib/ui/widgets/item_external_action.dart`・`list_detail_screen.dart`）。
    文字そのものにはリンクを付けない（行を押すと詳細へ行くため、押す場所で違う動きが起きるのを避ける）。
    項目詳細からも同じ操作ができる（8.2）。
    - なお、**Web からは音源ファイルのダウンロードを外す**方針（Android の一般公開が引き金。
      音源以外のファイル（楽譜 PDF 等）と URL は従来どおり開ける。詳細と現状は `DOWNLOAD-DESIGN.md` 7）。

#### 削除済み項目の見え方

- **既定では削除済み項目も一覧に表示**し、欠番の位置に「削除されました」と出す。連番が飛んでいる理由が誰にでも分かる状態にする。
- 一覧上の**切り替えで、削除済み項目を非表示にできる**。削除が積み上がっても一覧が見づらくならないようにするため。
  - 切り替えは全メンバー（Read Only 含む）が使える。
  - **切り替えの状態は端末に保存する**（`shared_preferences`／`lib/data/local_preferences.dart`）。
    次に画面を開いても、選んだ状態が続く。**アプリ全体で 1 つの設定**として持つ（リストごとには覚えない）。
    保存先が使えない端末では、その場の切り替えは効くが記憶されず既定（表示する）に戻る。
- **削除済み項目は検索の対象に含めない**。検索は「今ある曲を探す」ための機能と位置づける。
- 削除済み項目には、曲名・アーティスト名・ファイル名・URL を表示しない（「削除されました」とだけ表示する）。**復元操作はリスト管理者以上のみ**が行える（6.3）。

## 7. ファイル・容量

### 7.1 アップロード対象
- 主に mp3・mp4 を想定するが、**ファイル種別は制限しない**（他形式も可）。
- ファイル本体は **Firebase Storage** に保存し、Firestore には「どのファイルがどこにあるか」等のメタ情報のみを持たせる。

### 7.2 容量上限（クォータ）
- **リスト単位の合計容量に上限**を設ける。
- 初期値 **1GB**。**サイト管理者がリストごとに個別**に上限を設定できる（サイト管理画面）。
- **ファイル単位の上限は設けない**。

### 7.3 容量に関する通知・挙動
- 使用量が **80% を超えたら「Notice」**、**90% を超えたら「警告」**を、**リスト管理者**へ通知する。
- 上限を超えた状態でアップロードしようとした場合：「**上限を超えました。リスト管理者にご連絡ください**」と表示し、アップロードをブロックする。

### 7.4 使用量の可視化
- **サイト管理画面**：全リストの容量使用量を表示。
- **リスト管理者**：自分のリストの容量使用量を把握できる。

### 7.5 アップロードの手順と、失敗・中断時の扱い

**基本方針：ファイルのアップロードが完全に終わってから、項目を作成する。**

#### 手順

1. ユーザーがファイルを選び、曲名・日付などを入力して「追加」を実行する。
2. **先に Storage へファイルをアップロード**する。この間、進捗を表示し、**キャンセルできる**ようにする。
3. アップロードが完了したら、**項目を作成する**（このときに連番が採番される／13.3）。
4. 項目の作成まで終わって、はじめて一覧に表示される。

#### 失敗・中断したとき

- 通信が切れた／ブラウザを閉じた／キャンセルした場合、**項目は作成されない**。
  - 一覧に中途半端な項目が残らない。
  - **連番も消費しない**（欠番が無駄に増えない）。
- Storage 側に**行き場を失ったファイル**が残ることがある。これは**定期実行（1 日 1 回）で自動削除**する（13.4）。
  - 判定条件：Storage 上にあるが、**対応する項目が存在せず、かつアップロードから 24 時間以上経過**しているファイル。
  - 削除に連動して使用容量も戻る。
- ユーザーには「アップロードに失敗しました。もう一度お試しください」と表示し、**やり直しを促す**。中断したところからの再開機能は設けない。

#### 容量チェックのタイミング

- **アップロードを始める前**に、そのファイルのサイズを加えても上限を超えないかを確認する。超える場合は 7.3 のメッセージを表示し、**アップロード自体を開始しない**（無駄な通信と課金を避けるため）。
- 同時アップロードなどで、開始時のチェックをすり抜けて上限を超えることがあり得る。その場合も**アップロード済みのファイルは削除せず受け入れ**、以後のアップロードをブロックする。
- ただし、**上限を超えている状態から始まったアップロードは、サーバー側で取り消す**。画面を経由しない呼び出し（Storage の SDK を直接叩く等）で上限を無視できてしまうため。
  - すり抜け（このファイルで初めて超えた）＝**受け入れる**
  - 無視（足す前からすでに超えていた）＝**取り消す**
  - 判定は `functions/src/domain/quota.ts` の `shouldRejectUpload`。

## 8. 再生・リンクの挙動

### 8.1 一覧からその場で再生する

**リストの一覧で、各行の左に再生の操作を置く。**

| いまの状況 | 出すボタン |
| --- | --- |
| 止まっている | 再生 |
| 鳴っている | 一時停止・停止 |
| 一時停止している | 再生・停止 |

- **停止**：止めて**先頭へ戻す**。次に再生すると頭から始まる。
- **一時停止**：**その位置で止める**。次に再生するとその位置から続く。
- 一時停止中も停止を出す。出さないと、途中で止めたものを頭に戻す手段がなくなる。
- 別の曲の再生を押すと、鳴っていたほうは止まる。**2 曲が同時に鳴ることはない**。
- 最後まで鳴り終わったら、停止したのと同じ状態に戻る。

**対象は音として鳴らせるファイルだけ。**

- **URL の項目**（YouTube 等）：外部のページなので、ここでは鳴らせない。8.2 の開き方による。
- **音ではないファイル**（画像・書類・動画）：ファイルの種類は登録時に制限していない（7.1）ため、
  音源以外も登録できる。押しても鳴らないものに再生ボタンを出さない。
  判断は `contentType` が `audio/` で始まるかどうか。種類が記録されていない古い項目は
  拡張子（mp3 / m4a / wav / flac / ogg / aac）で判断する。

再生の状態と移り変わりは `lib/domain/playback.dart` に切り出してあり、
端末の音を鳴らさずに確かめられる（12.6）。

### 8.2 その他の開き方

- **アップロードされた音源・動画**：項目詳細から、**別のアプリで開く**／**ダウンロードする**を選べる。
- **URL（YouTube 等）**：リンクをタップすると**外部サイトへ遷移**する。

## 10. 通知

### 10.1 通知チャネル
- **アプリ内通知**（ベルアイコンに通知が溜まる形）
- **プッシュ通知**（FCM。モバイル版向け。**初期リリースでは未対応**で、モバイルの配信に合わせて対応する／12.7）

### 10.2 通知イベントと受信者
| イベント | 受信者 |
| --- | --- |
| リストに項目（曲）が追加された | 該当リストの**メンバー全員**（役割は問わない。リスト管理者を含む） |
| コメントが付いた | 該当リストの**リスト管理者**／**サイト管理者（全リスト）**／自分の投稿・コメントにコメントが付いた**本人** |
| 容量が 80% 超（Notice）／90% 超（警告） | 該当リストの**リスト管理者** |
| リスト作成の申請があった | **サイト管理者** |
| リストへの参加申請があった | 該当リストの**リスト管理者** |
| 申請が**承認**された | **申請した本人**（※**却下時は通知しない**） |

いずれの場合も、**きっかけを作った本人には送らない**。自分の操作の通知が
自分に届いても雑音にしかならないため。

**曲の追加だけは「役割」ではなく「参加しているかどうか」で決める。**
曲が増えたことは、そのリストにいる人みんなにとっての知らせなので、
閲覧のみ（Read Only）の人にも届く。逆に、サイト管理者であっても
参加していないリストの曲は通知しない。全リストの曲が流れ込むと、
本当に見るべき通知が埋もれてしまうため。サイト管理者がそのリストの
様子を知りたい場合は、リスト管理者を兼任してメンバーになる（4.1）。

### 10.3 通知設定（On/Off）
- 上記の**すべての通知種別を個別に On/Off** できる。
- 各種別について、**アプリ内通知／プッシュ通知**をそれぞれ個別に切り替えられる。
- さらに、**全体を一括で On/Off** するマスタースイッチを用意する。
- **初期状態は全てオン**（新規ユーザーは最初すべての通知がオン）。
- 設定画面では、種別の名前だけでなく**どんなときに届くか**も併記する。
  名前だけでは「自分に届く通知なのか」が判断できず、切り替えようがないため。

## 11. 管理画面（機能まとめ）

### 11.1 サイト管理画面（サイト管理者）
- リスト作成申請の確認・承認
- 各リストの容量使用量の表示
- リストごとの容量上限の設定（初期値 1GB）
- ~~招待 URL の有効期限の設定~~（**廃止**。共有リンクに期限は無い／3.3）
- 管理者不在リストの確認・リスト管理者の指名
- サイト管理者への昇格
- ユーザーの権限変更
- **ユーザーの追加・無効化・削除**（下記／v1.6）
- **クーポンの発行・一覧・上限変更・停止・使用者確認**（プレミアム／15.2）
- **利用者のプレミアム期限の延長・容量上限の個別調整**（`extendPremium` / `setUserQuota`／15.1）

#### ユーザーの追加

サイト管理者が、メールアドレス・表示名・**パスワード**を入力して作る
（2026-08-09 の依頼者指示）。決めた本人がパスワードを知っている状態に
なるため、**渡したあとで本人に変えてもらう**旨を画面に書く。

**メール確認は済んだ扱いにする。** サイト管理者が宛先を承知のうえで
作るためで、こうしないと本人は確認メールを待つ画面から先へ進めない
（3.1）。自己登録の経路では、従来どおり確認を求める。

#### 無効と削除

**無効は戻せる。削除は戻せない。** 迷ったら無効にする。

| | 無効 | 削除 |
| --- | --- | --- |
| ログイン | できない | できない（アカウントが無い） |
| 認証のアカウント | **残す**。有効に戻せる | 消す |
| `users` ドキュメント | **残す** | 消す |
| 参加中のリスト・閲覧中のリスト | 外す | 外す |
| 登録した曲・音源ファイル | **残す** | **消す** |
| 書いたコメント | 残す | **残す**（表示名は「退会したユーザー」／3.5） |

- **コメントを残すのは、会話が文脈だから。** 1 つ抜けると前後が読めなくなる。
- **曲は本当に消す。** ソフト削除（6.2）は「あとで戻せるように」する
  仕組みで、物理削除の求めに対しては答えになっていない。
- **有効に戻しても、参加していたリストには戻らない。** 外した記録しか
  残っていないため、どこに戻すべきかを機械的に決められない。改めて案内する。

#### 誰に対して行えるか

- **自分自身には行えない。** 無効化すれば自分が締め出され、削除すれば
  アカウントごと消える。どちらも「やり直す手段」を自分から奪う操作で、
  サイト管理者が 0 人になる道でもある。自分をやめるときは退会を使う（3.5）。
- **最後のサイト管理者は止められない**（4.5）。誰も承認できなくなり、
  リストが 1 つも作れなくなる。

### 11.2 リスト管理者の機能
- 自リストの容量使用量の把握
- メンバーの招待、参加申請の承認、役割の割当、メンバーの除外
- 自リスト内の項目・コメントの編集・削除
- 自リストの削除

## 12. 運用・非機能に関する方針

### 12.1 Firebase の料金プラン

- **Blaze プラン（従量課金）を採用**する。Cloud Functions・Storage・FCM を本格利用するため、無料の Spark プランでは要件を満たせない。
- ただし、**Google Cloud の予算アラートを必ず設定**し、想定月額を超えた場合はメール通知が届くようにする。
  - 予算アラートのしきい値は、想定月額に対して **50% / 90% / 100%** の 3 段階で設定する。
  - 通知先はサイト管理者のメールアドレス。
- Blaze プランには各サービスの無料枠がそのまま適用されるため、**小規模利用のうちは実質無償**で運用できる見込み。無料枠を超えた分のみ課金される。
- **予算超過時の自動停止（課金の自動無効化）は実装しない**。サービスが止まる影響のほうが大きいため、アラートによる検知と手動対応で運用する。

#### 無料枠の地域制約（費用に直結する）

**Cloud Storage の無料枠は米国の 3 リージョンにしか適用されない。**

| サービス | 無料枠 | 地域の制約 |
| --- | --- | --- |
| Cloud Storage | 5GB 保存／月 100GB ダウンロード／アップロード 5 千回・ダウンロード 5 万回 | **`us-central1` / `us-west1` / `us-east1` のみ** |
| Cloud Firestore | 1GiB／読み取り 5 万・書き込み 2 万・削除 2 万（日）／月 10GiB 転送 | なし（東京でも適用される） |
| Cloud Functions | 月 200 万回の呼び出し | なし |

**費用を決めるのは保存量ではなくダウンロード量。** 音源は Storage から直接配信されるため、再生された回数がそのまま請求額になる。月 100GB の無料枠は、10 人程度が数十曲を聴く使い方であればまず超えない。

小規模（音源 5GB・月間ダウンロード 20GB）での概算：

| | 米国 | 東京 |
| --- | --- | --- |
| 合計 | 0 円 | 約 400 円/月 |

**判断：検証環境は Storage を `us-east1` に置く。** 無料枠の恩恵が大きく、開発中の遅延は問題にならないため。本番環境の配置は利用規模を見て決める（東京にすると画面表示は速くなるが、Storage の無料枠を失う）。

- 想定利用量に応じた概算見積もりは別途整理する。

### 12.2 デプロイ・ホスティング・環境構成

- Web 版は **Firebase Hosting** にデプロイする。
- **本番環境と検証（ステージング）環境を、別々の Firebase プロジェクトとして分離**する。

| 環境 | 用途 | Firebase プロジェクト |
| --- | --- | --- |
| 本番（production） | 実際の利用者が使う環境 | 本番用プロジェクト |
| 検証（staging） | 新機能の動作確認・リハーサル | 検証用プロジェクト |

- 環境を分ける理由：Firestore のデータ・Storage のファイル・認証ユーザーがプロジェクト単位で完全に独立するため、**検証作業が本番データを壊す事故を構造的に防げる**。
- Flutter 側は **ビルド時に接続先の Firebase 設定を切り替える**構成にする（環境ごとの設定ファイルを用意し、ビルドフレーバー／`--dart-define` 等で切り替え）。
- 予算アラート（12.1）は**本番・検証の両プロジェクトに設定**する。検証環境の想定額は本番より低く設定する。
- 公開 URL は当面 Firebase Hosting の既定ドメイン（`*.web.app` / `*.firebaseapp.com`）を使用し、独自ドメインの割り当ては将来の検討事項とする。

#### 実際のプロジェクト

| 環境 | 表示名 | プロジェクト ID | 公開 URL |
| --- | --- | --- | --- |
| 本番 | `Music-Storage` | `music-storage-d79b2` | <https://music-storage-d79b2.web.app> |
| 検証 | `Music-Storage-dev` | `music-storage-dev` | <https://music-storage-dev.web.app> |

本番のプロジェクト ID が表示名と一致しないのは、`music-storage` が既に使われており、末尾にランダムな文字列が付いたため。

#### ロケーションとリージョン

| 対象 | 検証環境 | 理由 |
| --- | --- | --- |
| Cloud Firestore | `asia-northeast1`（東京） | 画面表示の速さは Firestore との往復回数が支配的。無料枠に地域の制約がないため東京にできる |
| Cloud Storage | `us-east1`（米国東部） | 無料枠がこの地域にしか適用されない（12.1） |
| Cloud Functions（既定） | `asia-northeast1` | Firestore と揃える |
| Cloud Functions（Storage トリガー） | `us-east1` | **トリガーは対象と同じリージョンでしか動かせない** |

- **ロケーションはあとから変更できない。** Firestore も Cloud Storage も、作成後の移動手段はなくプロジェクトの作り直しになる。作成時に決めきること。
- リージョンはコードに直書きせず、`functions/.env.<プロジェクト ID>` の `FUNCTIONS_REGION` / `STORAGE_REGION` で環境ごとに上書きできるようにする。本番と検証でロケーションが違っても、同じコードをそのまま配信するため。
- **この値は `defineString`（パラメータ）で受け取ること。** Firebase CLI は、どの関数をどこに配置するかを決める解析の段階では、子プロセスに一部の環境変数しか渡さない。`process.env` で読むと解析時には常に未設定になり、指定しても効かない。

#### 呼び出し可能関数の公開設定

`onCall` の関数は、**Cloud Run のレベルでは誰でも呼べる状態にしておく必要がある。** Firebase のログイン情報は `Authorization` ヘッダに載るが、Google のアクセストークンではないため Cloud Run には読めないため。**利用者の確認は関数の中で `request.auth` を見て行う**（未ログインなら `unauthenticated` を返す）。

Firebase CLI はこの設定を関数の**新規作成時**に行う。初回デプロイが途中で失敗すると設定だけが飛ばされ、以後の配信は更新扱いになるため直らない。その場合は関数を削除してから配信し直す（手順は SETUP.md）。

### 12.3 バックアップ・エクスポート方針

- **定期自動バックアップは組まない**。バックアップ保管にかかるストレージ課金を抑えることを優先する。
- 必要が生じたときに、**サイト管理者が手動でエクスポート**する運用とする。
  - Firestore：`gcloud firestore export` によるデータのエクスポート。
  - Storage：`gsutil` / `gcloud storage` によるファイルの一括ダウンロードまたは別バケットへのコピー。
- **アプリ側にバックアップ／エクスポート用の画面は作らない**（初期リリースでは対象外）。
- 手動エクスポートの具体的な手順は、**運用手順書として別途整備**する。

> **留意事項（リスクの明示）**
> 定期バックアップを持たないため、**誤操作や不具合でデータが失われた場合、直前の状態には戻せない**。特に以下の操作は復旧手段がないことを前提に扱う。
> - リストの削除（5.5：ファイル・コメントもすべて削除される）
> - 項目のファイル／URL の差し替え（6.3：元のファイルは残らない）
>
> 実運用の負荷が見えてきた段階で、定期自動バックアップの導入を改めて検討する。

### 12.5 UI デザインの方針

- **Flutter 標準の Material Design をそのまま使う**。独自のデザインシステム・テーマは作らない。実用性とスピードを優先する。
- **レスポンシブ対応は初期リリースから行う**。PC ブラウザとスマートフォンのブラウザの両方で、破綻せず使えることを最低ラインとする。
  - 画面幅に応じてレイアウトを切り替える（広い幅＝表形式に近い一覧、狭い幅＝1 行ずつのカード／リスト表示）。
- リスト項目の一覧は、**行形式のシンプルな表示**とする（連番・日付・曲名／ファイル名・登録者が一目で分かる並び）。
- 詳細なレイアウトは実装しながら詰める方針とし、**事前のモックアップ作成やデザイントーンの決定は行わない**。
- 多言語対応（2 章）に伴い、**文言は日本語・英語で長さが変わる**ため、テキストが固定幅で溢れない作りにする。

#### 配色

- **寒色系で統一する。** 音源を落ち着いて扱う道具なので、視覚的な刺激を抑える。
- 基準色は青（`#1B5E9E`）。3 番目の色は青緑（`#0E7C86`）。
- **エラーの赤だけは寒色にしない。** 危険の伝わり方が弱くなるため。

> **Material 3 は基準色 1 つから配色を自動で作るが、`tertiary` は色相を回して作られる。**
> 青を指定しても桃色系になり、実際に検証環境のバナーが桃色になっていた。
> `tertiary` の一群は別の基準色から作り直して差し替える（`lib/app.dart` の `appColorScheme`）。

- **最小の大きさが組みごとに違う。** 横一列は高さ 28px 以上、
  横組み 2 段は幅 120px 以上、アイコン単体は 16px 以上。
  下回ると英字やワードマークが潰れる。
- **暗い側の横一列は、タイルなし（`-notile`）を使う。** アイコンの
  角丸タイルは濃紺なので、暗い地色だと背景に溶けて四角い影に見える。
- SVG ではなく PNG を積んでいる。理由は 2 つ。
  1. SVG を描くには依存を 1 つ増やすことになり、足した部品が
     組み込まれないまま配信される事故を過去に起こしている（`docs/DEVLOG.md`）
  2. **ロックアップの SVG は文字をテキスト要素のまま持っている。**
     Noto Sans JP が無い環境では別のフォントで組み直された見た目になる
     （`brand/README.md`「フォントについて」）。ラスタ版なら崩れない

#### 広告（v1.9 で置き場所を変えた）

**広告はアプリの画面に出さない。読み物のページにだけ出す。**

| ページ | 広告 | 理由 |
| --- | --- | --- |
| アプリの画面（`web/index.html`） | **出さない** | CanvasKit は画面を canvas に描くので、**HTML に読める文字が 1 つも残らない** |
| 使い方（`web/help/{ja,en}/*.html` の章ページ） | 出す | 読み物。**1 ページ 1,600 字以上**を保つ |
| 使い方の目次・プライバシーポリシー | 出さない | 目次は薄く、法務のページは読ませる文書 |

**v1.8 では画面の最上部に枠を置き、アプリ側にスクリプトを入れていた。
それが審査に落ちる形だった。** AdSense の 2 大指摘「コンテンツを含まない
画面における広告」「有用性の低いコンテンツ」は、たいてい同じ事実から
出る——**広告のあるページに読めるテキストが無く、テキストのあるページに
広告が無い**（別プロジェクトで実際に受けた指摘。共有ドキュメント
`ナレッジベース.md` S-7、`アンチパターン集.md` AP-43）。

Googlebot は JS を実行するので「実行されないから空」ではない。
**実行しても文字が増えない**のが canvas 固有の問題で、
サーバー側で HTML を返してからアプリを起動する対処（プリレンダリング）も
効かない（描画後の DOM がまた canvas に戻る）。

- **読み物は 6 ページに束ねてある。** 原本は `docs/manual/{ja,en}.html`
  （1 枚もの）で、`scripts/build-manual.mjs` が章を束ねて生成する。
  **章を 1 つずつページにすると全部が薄くなる**（日本語の本文は約
  12,000 字しかない）。薄いページの量産は同じ指摘に戻る。
- **原本は `web/` の外に置く。** 中に置くと 1 枚ものと分割ページの両方が
  配信され、同じ文章が 2 か所に出る（重複コンテンツ）。
- 所有者証明の `ads.txt` は同じパブリッシャー ID で置いてある。
  **片方だけでは審査に通らない。**
- **枠（`ins` 要素）は置かず、自動広告に任せる。** 手動のユニットには
  コンソールで作った枠の ID が要り、審査前は発行できない。
- **robots.txt でアプリの画面を隠さない。** 隠して誤魔化すのは違反で、
  広告が「中身の無い画面」に出ている事実は変わらない。
- **プレミアムには広告を出さない**という想定は、アプリの画面に広告が
  無くなったことで**そのまま満たされた**（v1.8 で用意していた
  切り替えの入口は撤去した）。

> **この配置は `test/domain/ads_placement_test.dart` が見張っている。**
> 広告のスクリプトは 1 行なので、戻すのも一瞬で、戻したことに誰も
> 気づかない。**コメントではなく、落ちるテストで守る。**
> 「寒色で統一」は目視でしか確かめられないと思われがちだが、色相は数値なので
> `test/ui/theme_test.dart` で機械的に固定している。

### 12.6 テスト・品質保証の方針

**方針：壊れると影響が大きいロジックは自動テストで守り、画面操作はステージング環境での手動確認でカバーする。**

#### 自動テストを書く対象（必須）

| 対象 | 理由 |
| --- | --- |
| 権限判定ロジック（4 章） | 役割ごとの可否を間違えると、見えてはいけない情報が見えてしまう |
| Firestore セキュリティルール | クライアントを信用しない最後の防波堤。ルール単体で検証する必要がある |
| 容量上限の判定（7.2・7.3） | 80%／90% の通知境界、上限超過時のアップロードブロック |
| 連番の採番（6.1・6.2） | 振り直しなし・欠番維持という仕様が崩れると復旧できない |
| 共有リンクの検証 | 取り消しの判定（`functions/src/domain/share_link.ts`） |

- Firestore セキュリティルールは **Firebase Emulator Suite** 上でテストする（本番・検証プロジェクトに触れずに検証できる）。
- ロジックのテストは Flutter の単体テスト（`flutter test`）で記述する。

#### テストの書き方で守ること（監査 第2回）

2 回の監査で、**テストが緑でも守られていない**状態が繰り返し見つかった。
次を守る。

| 決めごと | 理由 |
| --- | --- |
| **テストする関数は、本番から呼ばれていること** | 連番・招待・権限判定は、テストが手厚いのに本番から 0 参照だった。実際に動いていたのは別の場所のインライン実装で、そちらは無テストだった。`test/domain/no_dead_code_test.dart` が機械的に確かめる |
| **「〜できない」を確かめる項目には、「できる」側の対を同じ実行に置くこと** | 否定だけの項目は、前提が全部壊れていても通る。土台が崩れているほど緑が増える |
| **前提が崩れたら、その場で理由を出して止めること** | 常に赤いテストがあると、本物の後退が混ざっても出力が変わらない |
| **同じ規則を 2 か所に持つときは、対応表を両方に置くこと** | 「揃っていること」を確かめるテストが、揃う入力しか渡しておらず食い違いを隠していた |
| **権限を変えたら、その資源に対する操作をすべて並べて確かめること** | 「作れる」だけを見て「読める」を見ておらず、新規登録が壊れた |

#### 手動確認でカバーする対象

- 画面のレイアウト・レスポンシブ表示（PC／スマートフォン）
- 認証フロー（Google 連携・メール＋パスワード・パスワード再設定）
- ファイルのアップロード／ダウンロード／外部アプリでの再生
- 通知の到達（アプリ内通知・プッシュ通知）
- 日本語・英語の表示切り替え

- 手動確認は**検証（ステージング）環境**で行う（12.2）。確認する項目は
  **[TEST-CASES.md](TEST-CASES.md) の台帳**にまとめてある（2026-08-11 に整備）。
  **自動テストで守れるものは載せない**——同じものを 2 か所に置くと、数だけ増えて片方が古くなる。載せるのは「人の目や耳が要る」「実物のメールや外部サービスが要る」「配信先でしか起きない」「時間がかかる」のいずれかに当たるものだけ。

#### 今回は行わないこと

- **E2E テスト（自動）は作らない**。作成・維持のコストが見合わないため、上記の手動確認で代替する。
- **CI（GitHub Actions 等）での自動実行は初期リリースでは組まない**。テストはローカルで実行する。開発が続き手動実行の負担が増えてきた段階で、改めて導入を検討する。

### 12.7 通知の実装範囲（10 章の細部）

- **初期リリースでは、アプリ内通知（ベルアイコン）のみを実装する。**
- **プッシュ通知（FCM）は未実装**とし、モバイル版の配信に合わせてまとめて対応する。モバイルのアプリ自体は土台を実装済みだが（2 章／`MOBILE-APP-DESIGN.md`）、**通知基盤（`firebase_messaging`・APNs 鍵・通知許可の取得）はまだ入れていない**。Web プッシュはブラウザごとの差が大きく、通知許可の取得も必要になるため、Web 単独での先行実装は行わない。
- **まとめ通知（集約表示）は行わない**。通知は 1 件ずつ、発生の都度リアルタイムに積む。
- **メールでの通知は行わない**（12.1 の予算アラートは Google Cloud 側の機能であり、これとは別）。

#### 通知設定への影響（10.3 の補足）

- 通知設定画面には、**種別ごとのアプリ内通知の On/Off と、全体のマスタースイッチ**を用意する。
- **プッシュ通知の On/Off 項目は、初期リリースでは画面に表示しない**。ただし将来の追加を見越し、**データ構造としてはプッシュ通知の設定値を最初から保持できる形**にしておく（既定値はオン）。

#### アプリ内通知の扱い

- 未読／既読の状態を持ち、ベルアイコンに**未読件数**を表示する。
- 通知をタップすると、対象のリスト・項目・コメントへ遷移する。
- 通知の保持期間・上限件数は、運用しながら決める（初期は無制限に保持し、問題が出たら見直す）。

## 13. データモデル（Firestore / Storage）

### 13.1 設計の基本方針

| 方針 | 内容 |
| --- | --- |
| 入れ子構成 | `lists/{listId}` の配下に項目・メンバー・コメントをぶら下げる。セキュリティルールをパス単位で書けるため、未参加者に中身を見せない要件（5.3）を構造で担保できる |
| メンバー情報は一元管理 | 役割は `lists/{listId}/members/{uid}` の 1 か所のみに持つ。ユーザー側へのミラーは行わない |
| コメントはフラット | 無制限の入れ子（9 章）を、親 ID とパス配列で表現する |
| 表示名は参照で解決 | 項目・コメントには uid のみを持ち、名前は表示時に `users` から引く |
| サーバー側で守る値 | 連番・使用容量など、狂うと困る値はトランザクションまたは Cloud Functions で更新し、クライアントからは書けないようにする |

### 13.2 コレクション全体像

```
users/{uid}                          ← 公開可能な情報のみ（表示名・写真・退会）
  ├ private/state                    ← 本人だけが読める私的情報（メール・言語・通知設定・プレミアム・容量／13.3）
  └ notifications/{notificationId}

lists/{listId}                       ← 公開可能な最小情報のみ
  ├ meta/stats                       ← 容量・連番などの内部情報（メンバーのみ）
  ├ members/{uid}
  ├ joinRequests/{uid}
  ├ viewers/{uid}                    ← 参加せずに見るだけの人（3.3）
  └ items/{itemId}
      └ comments/{commentId}

listNames/{nameLower}                ← リスト名の重複チェック用
listRequests/{requestId}             ← リスト作成申請
shareLinks/{linkId}                  ← 共有リンク（3.3）
coupons/{couponId}                   ← プレミアムのクーポン（15 章。管理者のみ／ルールで全面禁止）
  └ redemptions/{uid}                ← 誰がいつ使ったか
siteConfig/global                    ← サイト全体の設定
```

#### `lists/{listId}` を 2 段に分けている理由

Firestore の読み取り権限は**ドキュメント単位**で、「このフィールドだけ見せる」ということができない。5.3 で「未参加者が共有 URL を開いたらリスト名など最低限の情報だけ見える」と決めているため、**公開してよい情報**と**メンバーにしか見せたくない情報**を別ドキュメントに分ける必要がある。

- `lists/{listId}` … リスト名・作成日時など。ログイン済みユーザーなら誰でも読める。
- `lists/{listId}/meta/stats` … 使用容量・連番カウンタなど。そのリストのメンバーのみ読める。

### 13.3 各ドキュメントの構造

#### `users/{uid}` — ユーザー（公開可能な情報のみ）

`users/{uid}` は**表示名の解決のためログイン済みなら誰でも読める**（Firestore のルールに項目単位の読み取り制限が無い）。そのため、**本人だけに見せたい情報は `users/{uid}/private/state` へ分けてある**（下記／プライバシー目的。`lib/data/firestore_paths.dart` の `userPrivate`）。

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `displayName` | string | 表示名（3.4）。初期値は Google の表示名またはメール名 |
| `photoURL` | string? | アイコン画像 |
| `isWithdrawn` | bool | 退会済みかどうか（3.5） |
| `withdrawnAt` | timestamp? | 退会日時 |
| `createdAt` / `updatedAt` | timestamp | |

- **退会時は `users/{uid}` を削除せず、`isWithdrawn` を true にする**。過去の投稿は uid 参照のままなので、この 1 か所を変えるだけで全投稿の表示が「退会したユーザー」に切り替わる。

#### `users/{uid}/private/state` — 本人だけが読める私的情報

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `email` | string | メールアドレス（Auth 側が正本。Functions が写す） |
| `locale` | string | 表示言語（`ja` / `en`） |
| `notificationSettings` | map | 通知設定（10.3）。下記参照 |
| `premium` | map? | プレミアムの状態（15 章）。`until` だけで表す。**サーバーだけが書く** |
| `storage` | map? | 人ごとの合計容量（15 章）。**サーバーだけが書く** |

- **本人だけが読める**（サイト管理者も直接は読めない。必要な情報はサーバー経由で取る）。`email` を `users/{uid}` の直下に置くと、表示名の解決のために誰にでも見えてしまうため分けた。
- **本人が書けるのは `locale` と `notificationSettings` だけ。** `premium` / `storage` はサーバー（Cloud Functions）だけが書く。削除も禁止（`docId` は `state` に限定）。
- **以前は `email` / `locale` / `notificationSettings` を `users/{uid}` の直下に置いていた**が、他人に見えていたため 2026-08-11 にここへ移した（`PREMIUM-DESIGN.md` 7.1）。
- `notificationSettings` の形（プッシュは 12.7 により初期リリースでは画面に出さないが、値は最初から保持する）：

```
notificationSettings: {
  master: true,                                  // 全体のマスタースイッチ
  types: {
    itemAdded:      { inApp: true, push: true },
    commentAdded:   { inApp: true, push: true },
    quotaNotice:    { inApp: true, push: true },
    quotaWarning:   { inApp: true, push: true },
    listRequested:  { inApp: true, push: true },
    joinRequested:  { inApp: true, push: true },
    requestApproved:{ inApp: true, push: true },
  }
}
```

#### `users/{uid}/notifications/{notificationId}` — アプリ内通知

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `type` | string | 通知種別（上記 `types` のキー） |
| `listId` / `itemId` / `commentId` | string? | 遷移先の特定に使う |
| `requestId` | string? | 申請に関する通知のときの申請 ID |
| `actorUid` | string? | 通知のきっかけを作った人 |
| `isRead` | bool | 既読フラグ（未読件数の集計に使う） |
| `createdAt` | timestamp | |

- 通知は Cloud Functions が受信者ごとに 1 件ずつ作成する（まとめ通知は行わない／12.7）。

#### `lists/{listId}` — リスト（公開可能な情報のみ）

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `name` | string | リスト名 |
| `nameLower` | string | 重複チェック用の正規化名。前後の空白を落とし、小文字にし、**スラッシュを `_` に置き換える**（スラッシュはドキュメント ID の区切りになるため） |
| `createdBy` | string | 作成者（＝承認時のリスト管理者）の uid |
| `createdAt` / `updatedAt` | timestamp | |
| `adminCount` | number | リスト管理者の人数。**0 なら管理者不在**（5.6）。サイト管理画面での抽出に使う |
| `memberCount` | number | メンバー数 |

#### `lists/{listId}/meta/stats` — リストの内部情報（メンバーのみ）

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `nextSeq` | number | 次に採番する連番（6.2）。初期値 1 |
| `usedBytes` | number | 使用容量（7.2） |
| `quotaBytes` | number | 容量上限。初期値 1GB（`1073741824`） |
| `notifiedNotice80` | bool | 80% 通知の送信済みフラグ（重複通知の防止） |
| `notifiedWarning90` | bool | 90% 通知の送信済みフラグ |
| `itemCount` | number | 削除済みを除いた項目数（14.2 ホームの件数表示）。Cloud Functions が増減させる |

- **クライアントが書けるのは `nextSeq` を 1 進めることだけ**（項目の追加と同じトランザクションで行う／6.2）。
  容量・件数・通知フラグは Cloud Functions だけが更新する。
  - 以前はここを全面禁止にしており、**項目の追加が一度も成功しない**状態だった。
    ルールのコメントは「連番はトランザクション」と書いていたのに、その下は `allow write: if false` だった。
- 使用量が各しきい値を下回ったら、対応するフラグを false に戻す（再び超えたときに改めて通知するため）。

#### `lists/{listId}/members/{uid}` — メンバーと役割

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `role` | string | `listAdmin` / `superUser` / `readOnly` |
| `joinedAt` | timestamp | |
| `addedBy` | string? | 招待・承認を行った人の uid |
| `via` | string | `invite`（招待）/ `request`（参加申請）/ `founder`（作成者）/ `assigned`（サイト管理者による指名・5.6／リストへの追加・5.7） |

- **サイト管理者はここに含めない**。サイト管理者は全リストへの権限をカスタムクレームで持つため（13.5）、メンバー登録は不要。
- 「自分の参加リスト一覧」は、`members` に対する **collectionGroup クエリ**で取得する。
  - **ドキュメント ID では引けない。** `documentId()` に渡す値は完全なドキュメントパスでなければならず、素の uid では失敗する。そのため `members` と `joinRequests` には**中身にも `uid` を持たせ**、その項目で絞る。
  - 必要なのは複合インデックスではなく、**コレクショングループ範囲の単一フィールド索引**（`firestore.indexes.json` の `fieldOverrides`）。単一フィールドの索引はコレクション範囲しか自動作成されないため、明示が要る。
- **メンバーを除外したとき／本人が抜けたときは、このドキュメントを削除する**。投稿自体は残るため（5.4）、表示は次のルールになる。

> **「退会したユーザー」と表示する条件**
> 1. `users/{uid}.isWithdrawn` が true（＝アカウント退会／3.5）
> 2. または、その uid が**そのリストの `members` に存在しない**（＝除外された／自分で抜けた／5.4）
>
> どちらの場合も元の表示名は出さず、「退会したユーザー」と表示する。

#### `lists/{listId}/items/{itemId}` — リスト項目

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `seq` | number | 連番（6.2）。振り直しなし |
| `date` | string | 録音日想定。`YYYY-MM-DD` 形式の**文字列**。タイムゾーンを持たせないため、あえてタイムスタンプ型を使わない（6.2） |
| `kind` | string | `file` または `url`（どちらか一方のみ／6.1） |
| `file` | map? | `kind == 'file'` のとき。下記参照 |
| `url` | string? | `kind == 'url'` のとき |
| `title` | string? | 曲名（任意） |
| `artist` | string? | アーティスト名（任意） |
| `createdBy` | string | 登録者の uid（自動記録） |
| `createdAt` | timestamp | |
| `updatedBy` / `updatedAt` | string / timestamp | 最終更新者・更新日時 |
| `status` | string | `active` / `deleted`（ソフト削除） |
| `deletedBy` / `deletedAt` | string / timestamp | 削除者・削除日時 |
| `purgeAt` | timestamp? | ファイル本体の完全削除予定日時（13.4） |
| `purgedAt` | timestamp? | 完全削除を終えた日時。次回以降の対象から外すための印 |
| `previousFiles` | array? | 差し替え前のファイル。**`functions/src/callable/items.ts` の `replaceItemFile` が書きます**（クライアントからは書けません／13.4） |

`file` マップの内容：

```
file: {
  storagePath: 'lists/{listId}/items/{itemId}/{fileName}',
  fileName:    'take01.mp3',
  sizeBytes:   5242880,
  contentType: 'audio/mpeg',
}
```

- 項目の初回コメント（6.2）は、独立したコメントドキュメントとして `comments` に作成する。項目内には持たない。
- **`updatedAt` は同時編集の検出にも使う**（6.3）。編集画面を開いたときの `updatedAt` を保持し、保存時にトランザクション内で現在値と突き合わせる。一致しなければ保存を中止して警告を出す。コメントも同じ方式。

#### `lists/{listId}/items/{itemId}/comments/{commentId}` — コメント

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `body` | string | 本文 |
| `parentId` | string? | 返信先コメントの ID。ルートコメントは `null` |
| `path` | array&lt;string&gt; | ルートから親までの ID を順に並べた配列。ルートコメントは `[]` |
| `depth` | number | 階層の深さ。ルートは 0 |
| `createdBy` | string | 投稿者の uid |
| `createdAt` / `updatedAt` | timestamp | |
| `status` | string | `active` / `deleted` |

- **項目のコメントは 1 回のクエリで全件取得し、アプリ側でツリーに組み直す**。`path` を持たせているのは、スレッド順（親の直下に子が並ぶ順序）でソートするため。
- 返信がぶら下がっているコメントを削除した場合、`status` を `deleted` にして「削除されました」と表示し、**子の返信は残す**（親を物理削除するとツリーが切れるため）。

#### `listNames/{nameLower}` — リスト名の重複チェック

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `listId` | string? | 確定済みリストの ID |
| `requestId` | string? | 申請中の場合の申請 ID |
| `reservedAt` | timestamp | |

- 5.1 の重複チェックを、**ドキュメント ID の存在確認だけで行う**ための仕組み。
- `lists` コレクションを名前で検索する方式にすると、未参加者が全リスト名を列挙できてしまい、5.3（全リスト一覧は公開しない）に反する。ID 直接指定なら「その名前があるか」しか分からない。

#### `listRequests/{requestId}` — リスト作成申請（5.1）

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `listName` / `nameLower` | string | 申請するリスト名 |
| `estimatedTrackCount` | number | 概算の登録曲数 |
| `expectedUserCount` | number | 使用者数 |
| `purpose` | string | 作成目的 |
| `requestedBy` / `requestedAt` | string / timestamp | 申請者・申請日時 |
| `status` | string | `pending` / `approved` / `rejected` |
| `decidedBy` / `decidedAt` | string / timestamp | 承認・却下したサイト管理者と日時 |
| `createdListId` | string? | 承認時に作成されたリストの ID |

- 承認処理は Cloud Functions で行い、**リスト作成・`listNames` の確定・申請者を `listAdmin` として `members` に登録・申請者への承認通知**までを一括で実行する。
- **却下時は `listNames` の予約を解放**する。その名前を他の人が申請できるようにするため。
- 却下された申請は、申請者の申請一覧に「却下」として残す（5.2.1）。**再申請は新しいドキュメントとして作成**する。

#### `lists/{listId}/joinRequests/{uid}` — 参加申請（5.2）

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `requestedAt` | timestamp | |
| `status` | string | `pending` / `approved` / `rejected` |
| `assignedRole` | string? | 承認時にリスト管理者が決めた役割 |
| `decidedBy` / `decidedAt` | string / timestamp | |

- ドキュメント ID を申請者の uid にすることで、**同じ人が二重に申請することを構造的に防ぐ**。
- 申請者は役割を選べない（5.2）。`assignedRole` は承認側だけが書き込める。
- **却下後の再申請**（5.2.1）は、同じドキュメントを `pending` で上書きして行う。`decidedBy` / `decidedAt` / `assignedRole` はクリアする。過去の却下履歴は保持しない。
- 承認されるとメンバー登録され、この申請ドキュメントは削除する。除外・離脱した人が再申請する場合（5.4）も、同じ経路で新たに作成される。

#### `shareLinks/{linkId}` — 共有リンク（3.3）

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `listId` | string | 共有先のリスト |
| `itemId` | string? | 曲を指すリンクなら、その項目 |
| `createdBy` / `createdAt` | string / timestamp | 発行者・発行日時 |
| `revoked` / `revokedAt` | bool / timestamp? | 取り消し |

- **役割の欄は持たない。** URL は「どのリスト（どの曲）か」以外の意味を持ってはいけない。
  参加した人の初期役割は `domain/roles.ts` の `INITIAL_JOIN_ROLE`（Read Only）で、リンクとは無関係に決まる。
- `linkId` は**推測できないランダムな文字列**（256 ビット相当）とし、これがそのまま URL に載る。
  **期限が無いぶん、ID の推測されにくさがそのまま守りになる。**
- **期限も使用回数の上限も持たない。** 何人が何度使ってもよい。
- 一覧としての取得は禁じる。許すと、すべてのリンクを集められてしまう。
- トップレベルに置いているのは、**まだそのリストのメンバーでない人が読む必要がある**ため。

#### `lists/{listId}/viewers/{uid}` — 参加せずに見るだけの人（3.3）

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `uid` | string | 本人 |
| `viaLink` | string | どのリンクから来たか |
| `firstSeenAt` | timestamp | 最初に選んだ日時 |

- **メンバーとは別に持つ。** メンバー一覧にも `memberCount` にも通知の宛先にも入らない。
- **書けるのは Cloud Functions だけ。** クライアントから書けると、
  リンクを持っていない人が自分で閲覧権を作れてしまう。
- 読めるのは本人とリスト管理者。**誰が見ているかは、リストを預かる人には分かるようにする。**
- 本人は自分から削除できる（見るのをやめる）。

#### `siteConfig/global` — サイト設定（11.1）

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `defaultQuotaBytes` | number | 新規リストの容量上限の初期値。`1073741824`（1GB） |
| `itemPurgeGraceDays` | number | 削除項目のファイル保持日数（13.4）。初期値 30 |
| `orphanFileGraceHours` | number | 行き場を失ったファイルを削除するまでの猶予時間（7.5）。初期値 24 |
| `siteAdminCount` | number | サイト管理者の人数。**1 のときは降格・退会をブロック**する（4.5） |

- 読み取りは全ログインユーザー、書き込みはサイト管理者のみ（`siteAdminCount` は Cloud Functions のみ）。
- `orphanFileGraceHours` は**サイト設定画面に入力欄がある**（`lib/ui/screens/site_admin_screens.dart`。`itemPurgeGraceDays` と並ぶ）。サイト管理者が変更できる。

#### `siteConfig/internal` — サーバーだけが使う値

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `siteAdminUids` | array | サイト管理者の uid 一覧。通知の宛先を集めるために使う |
| `orphanScanPageToken` | string? | 孤児ファイルの走査を次回どこから始めるか（13.4） |

- **読み書きとも一切許可しない。** Cloud Functions だけが触る。
- `siteConfig/global` は利用者も読めるため、これらを混ぜない。
  - `siteAdminUids` を控えるようにしたのは、通知のたびに Auth の全ユーザーを走査していたため。
    コメントは 1 件付くだけで利用者数に比例した往復が発生していた（監査 第2回）。

### 13.4 サーバー側で行う処理（Cloud Functions）

| 契機 | 処理 |
| --- | --- |
| Storage へのファイル保存 | `meta/stats.usedBytes` に加算し、80%／90% のしきい値を超えたらリスト管理者へ通知（7.3） |
| Storage からのファイル削除 | `meta/stats.usedBytes` から減算し、しきい値を下回ったら通知済みフラグをリセット |
| 項目の作成 | そのリストの**メンバー全員**へ通知（10.2） |
| 項目の作成・削除（増減） | `meta/stats.itemCount` を増減する（13.3。ホームの件数表示に使う／14.2） |
| コメントの作成 | リスト管理者・サイト管理者、および親コメント／項目の投稿者本人へ通知 |
| リスト作成申請の承認 | リスト・`listNames`・`members`・通知をまとめて作成 |
| 共有リンクの受け入れ | 有効性の検証と、`members` または `viewers` への登録をトランザクションで実行 |
| メンバーの追加・削除 | `lists/{listId}` の `memberCount` / `adminCount` を更新 |
| サイト管理者の昇格・降格・退会 | カスタムクレームを付け外しし、`siteConfig.siteAdminCount` を更新。**残り 1 人のときの降格・退会は拒否**（4.5） |
| 新規ユーザーの作成 | **クライアント側で初期化する**（`lib/data/repositories/auth_repository.dart`）。firebase-functions v2 には Auth の作成トリガーが無く、blocking function は Identity Platform の有効化が要るため |
| 定期実行（1 日 1 回） | ①猶予期間を過ぎた削除項目のファイルを Storage から完全削除（下記）／②行き場を失ったファイルの削除（7.5）。②は 1 回あたりの走査量に上限を置き、**続きの位置を `siteConfig/internal` に持ち越す** |

#### 削除項目のファイル保持と完全削除

- 項目を削除すると、`status` を `deleted` にしたうえで **`purgeAt` に「削除日時＋`itemPurgeGraceDays`（初期値 30 日）」を設定**する。
- 猶予期間中は、**リスト管理者・サイト管理者が項目を復元できる**（`status` を `active` に戻し、`purgeAt` を消す）。
- 猶予期間を過ぎると、定期実行の Cloud Functions が Storage のファイルを削除する。これに連動して `usedBytes` が減る。
- **猶予期間中は容量を消費し続ける**点に注意。上限に近いリストでは、削除してもすぐには空きが増えない。
- 項目のドキュメント自体は完全削除後も残す（連番の欠番を維持し「削除されました」と表示するため／6.2）。

> **ファイル差し替え時の扱い（6.3）— 実装済み（2026-08-15）**
>
> 登録済みファイルを差し替えると、**旧ファイルは同じ猶予期間（初期値 30 日）を置いてから削除**される。
> クライアントが**別名**でアップロードし、`replaceItemFile`（`functions/src/callable/items.ts`）が
> `file` を差し替えたうえで旧 `file` を `previousFiles` に `arrayUnion` する（`replacedAt` と `purgeAt` 付き）。
> 掃除は `purgeDeletedFiles` が `purgeAt` を過ぎたものから行う。
>
> **この注記は長らく「未実装」のままでした**（2026-08-16 に修正）。
> **「未実装」の記述は書いた瞬間から腐ります**——実装した人は、
> そう書かれた場所を知らないので消す動機を持ちません（共有ドキュメント S-9）。

#### 行き場を失ったファイルの削除（7.5）

- アップロードは完了したが項目の作成に至らなかったファイルは、Storage 上に取り残される。
- 定期実行の Cloud Functions が、**対応する項目が存在せず、かつアップロードから `orphanFileGraceHours`（初期値 24 時間）以上経過した**ファイルを削除する。
- 猶予時間を置いているのは、**アップロード完了から項目作成までの短い間に消してしまわないため**。

#### 連番の採番はクライアントが行う（6.2）

`lists/{listId}/meta/stats` の `nextSeq` を、**項目の追加と同じトランザクションで
1 進める**。サーバー側で採番すると、追加のたびに関数の起動を待つことになり、
体感が落ちるため。

そのためルールは、この 1 点だけをクライアントに許す。

```
allow update: if docId == 'stats'
  && canWrite(listId)
  && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['nextSeq'])
  && request.resource.data.nextSeq == resource.data.nextSeq + 1;
```

**戻すことも飛ばすこともできない**ので、「連番は振り直さない・欠番は残す」（6.2）は
ここで守られる。容量（`usedBytes`）や通知フラグは Functions だけが書く。

> **`allow write: if false` にしてはいけない。** 実際にそう書いており、
> 「連番はトランザクション」というコメントと食い違ったまま、
> **項目の追加が一度も成功しない状態**になっていた。

#### コレクショングループのクエリ（横断的な取得）

「自分が参加しているリスト」「自分が出した参加申請」のように、**リストをまたいで
自分の行を集める**場面がある。ここには制約が 2 つあり、どちらも見落としやすい。

**1. ドキュメント ID では引けない。**

```
Invalid query. When querying a collection group by documentId(),
the value provided must result in a valid document path,
but 'xxx' is not because it has an odd number of segments (1).
```

コレクショングループを `documentId()` で引く場合、値は**完全なドキュメントパス**で
なければならない。素の uid は「セグメント数が奇数」として拒否される。
クライアント（Dart）でもサーバー（Admin SDK）でも同じ。

→ **ドキュメントに `uid` 項目を持たせ、その項目で引く。**
`members` と `joinRequests` がこれに当たる。

**2. 通常の `match` ではクエリが許可されない。**

`/lists/{listId}/members/{uid}` に `read` を書いても、それは**そのパスを直接指した
取得にしか効かない**。横断的に引くには、再帰ワイルドカードの `match` を別に書く。

```
match /{path=**}/members/{memberUid} {
  allow list: if isVerified() && resource.data.uid == uid();
}
```

**この `match` ではドキュメント ID の変数が束縛されない**（`Null value error` になる）。
判定はドキュメントの中身（`uid` 項目）で行う。クエリ側も同じ項目で絞るため、
返るのは自分の行だけになる。

**3. 索引は自動で作られない。**

単一フィールドの索引は自動で作られるが、それは**コレクション範囲だけ**。
コレクショングループ範囲の索引は `firestore.indexes.json` の `fieldOverrides` に
明示する必要がある。

> **この 3 つが揃わないと、リストを作ってもホームに出ない。**
> 実際に 2026-08-06 の配信後まで気づけなかった（`docs/AUDIT-2026-08-06.md`）。

### 13.5 権限判定とセキュリティルール

#### サイト管理者の判定

- **Firebase Authentication のカスタムクレーム**（`siteAdmin: true`）で保持する。
- セキュリティルールから追加の読み取りなしに判定できるため、高速かつ課金が発生しない。
- 付与・剥奪は Cloud Functions（サイト管理者のみ実行可）で行う。
- **注意**：カスタムクレームは認証トークンに埋め込まれるため、**変更が反映されるのはトークン更新後**（再ログイン、またはアプリ側でのトークン強制リフレッシュ）。権限を変更したら、対象ユーザーに再ログインを促す。

#### ルールの基本構造

```
// 判定用のヘルパー
isSiteAdmin()      : request.auth.token.siteAdmin == true
memberRole(listId) : get(lists/{listId}/members/{uid}).role
isListAdmin(listId): isSiteAdmin() || memberRole(listId) == 'listAdmin'
canWrite(listId)   : isListAdmin(listId) || memberRole(listId) == 'superUser'
isMember(listId)   : isSiteAdmin() || members ドキュメントが存在する
```

| パス | 読み取り | 書き込み |
| --- | --- | --- |
| `lists/{listId}` | ログイン済みなら誰でも（5.3 の最低限の情報） | サイト管理者・リスト管理者のみ（統計フィールドは Functions のみ） |
| `lists/{listId}/meta/stats` | メンバーのみ | **不可**（Functions とトランザクションのみ） |
| `lists/{listId}/members/{uid}` | メンバーのみ／自分の行は本人も可 | サイト管理者・リスト管理者。ただし本人による削除（離脱）は可 |
| `lists/{listId}/items/**` | メンバーのみ | Super User 以上。編集・削除は本人＋リスト管理者以上（6.3） |
| `lists/{listId}/items/*/comments/**` | メンバーのみ | Super User 以上。編集・削除は本人＋リスト管理者以上（9 章） |
| `lists/{listId}/joinRequests/{uid}` | リスト管理者以上／自分の行は本人も可 | 作成は本人のみ、承認・却下はリスト管理者以上 |
| `listNames/{nameLower}` | ログイン済みなら誰でも（ID 直接指定のみ／一覧取得は禁止） | **不可**（Functions のみ） |
| `listRequests/{requestId}` | サイト管理者／申請者本人 | 作成は本人、承認・却下はサイト管理者 |
| `shareLinks/{linkId}` | ログイン済みなら誰でも（ID を知っている人だけ到達できる） | **不可**（発行・受諾とも Functions のみ） |
| `users/{uid}` | ログイン済みなら誰でも（表示名の解決に必要。**公開情報のみ**） | 本人のみ。ただし `premium`・`storage` は Functions のみ |
| `users/{uid}/private/state` | **本人のみ**（email・locale・通知設定・premium・storage） | 本人（`locale`・`notificationSettings` のみ）。`premium`・`storage` は Functions のみ |
| `users/{uid}/notifications/**` | 本人のみ | 本人のみ（既読の更新）。作成は Functions のみ |
| `coupons/{couponId}`（＋ `redemptions`） | **不可**（コード一覧の漏洩防止／Functions のみ） | **不可**（Functions のみ） |
| `siteConfig/global` | ログイン済みなら誰でも | サイト管理者のみ |

- Storage のルールも同様に、`lists/{listId}/items/**` へのアクセスを**そのリストのメンバーに限定**する。

### 13.6 検索・並び替えの実現方法

- **並び替え**（6.4／連番・日付・登録者）は、`items` を読み込んだうえで**アプリ側で並べ替える**。登録者名での並び替えは uid ではなく解決後の表示名で行う。
- **検索**（6.4）は、**リストを開いた時点で項目を読み込んでおき、アプリのメモリ上で部分一致**させる。
  - Firestore は部分一致検索に対応していないため、この方式を採る。
  - 検索対象は、**曲名・アーティスト名。両方とも未記入の項目はファイル名**（6.4）。実装上は「曲名／アーティスト名／ファイル名のいずれかに含まれれば一致」とする。
  - 大文字小文字は区別しない。
  - **削除済み項目（`status == 'deleted'`）は検索の対象外**（6.4）。
- **制約**：項目数が数千件規模になると、リストを開いたときの読み込みが重くなる。その段階に達したら、ページングの導入や検索用キーワードの保持を改めて検討する。

### 13.7 Storage のファイル配置

```
lists/{listId}/items/{itemId}/{元のファイル名}
```

- パスにリスト ID を含めることで、Storage 側のセキュリティルールをリスト単位で書ける。
- 同一項目内でファイルを差し替えた場合は、**新しいファイルを別名で保存**し、旧ファイルは猶予期間後に削除する（13.4）。

### 14.4 項目の追加・編集画面

**1 つの画面で、上部のタブで「ファイル」「URL」を切り替える**形とする。

#### 保存できる条件と、失敗したときの見え方（v1.7）

| タブ | 保存に要るもの |
| --- | --- |
| ファイル | 選んだファイル。**編集中は、元のファイルがあればそれでよい** |
| URL | 空でない URL |

曲名・アーティスト名・コメントは任意。日付は初期値が入る。

- **要るものが揃うまで、保存ボタンは押せない。** 何が足りないかは
  ボタンのそばに書く。ボタンが灰色なだけでは、何をすればよいか分からない。
- **保存に失敗しても画面を閉じない。** 理由をポップアップで知らせ、
  画面にとどまる。入力した内容は残っているので、直して押し直せる。
  一覧へ戻してしまうと、書いた内容ごと失われる。
- ポップアップを閉じたあとも、同じ文言を画面の中に残す。
  何が起きたのかを見返せるようにするため。

> **2026-08-09 の指摘から。** ファイルを選ばずに保存を押すと、一瞬エラーが
> 出たあと曲の一覧へ戻っていた。原因は 2 つ重なっており、**足りないまま
> 押せたこと**と、**保存処理が「入力が足りない」ときに例外ではなく普通に
> 戻り、呼び出し側が成功と見分けられなかったこと**である。
> 成否は返り値で受け取る。`test/ui/item_form_test.dart` が固定している。

```
┌──────────────────────────────┐
│  [ ファイル ] [ URL ]         │  ← タブで切替
├──────────────────────────────┤
│  ファイル選択 ／ URL 入力欄   │  ← タブによって変わる
├──────────────────────────────┤
│  日付        （初期値：当日） │
│  曲名        （任意）         │  ← 共通
│  アーティスト名（任意）       │
│  コメント    （任意）         │
└──────────────────────────────┘
```

- **日付・曲名・アーティスト名・コメントの入力欄は共通**。タブを切り替えても入力済みの内容は保持され、やり直しが不要。
- ファイルタブでは、選択後に**ファイル名とサイズ**を表示し、**そのリストの残り容量**も併せて示す。
- 上限を超える場合は、この時点で警告し**アップロードを開始しない**（7.5）。
- アップロード中は**進捗を表示し、キャンセルできる**（7.5）。
- 編集時も同じ画面を使う。**タブを切り替えればファイル ↔ URL の変更もできる**（6.3）。

### 14.5 権限による表示の差

画面自体を出し分けるのではなく、**権限のない操作はボタンごと表示しない**方針とする。

| 役割 | 見え方 |
| --- | --- |
| Read Only | 一覧・詳細・コメントの閲覧、再生・ダウンロードのみ。「追加」「コメント入力欄」「編集」「削除」は表示しない |
| Super User | 上記に加え、項目の追加とコメント投稿。**自分が登録した項目・コメント**にのみ編集・削除ボタンが出る |
| リスト管理者 | 上記に加え、リスト内の全項目・全コメントの編集・削除、リスト管理への導線 |
| サイト管理者 | 全リストでリスト管理者と同等。加えてサイト管理へのナビゲーション項目が出る |

- 表示を消すだけでなく、**セキュリティルールでも同じ制限をかける**（13.5）。画面上の出し分けは利便性のためであり、権限の担保はルール側で行う。

## 15. プレミアム機能・クーポン・オフライン保存

**2026-08-11 に依頼者と決め、実装済み。** 課金が絡む機能なので、**詳細は設計文書が事実上の詳細仕様**として機能する（[PREMIUM-DESIGN.md](PREMIUM-DESIGN.md) / [DOWNLOAD-DESIGN.md](DOWNLOAD-DESIGN.md)）。ここでは全体像だけを示し、細部はそれらを参照する。

### 15.1 プレミアム（課金）

- 課金の単位は**人ごと**。契約は利用者に付く。解約しても既存のデータは消さず、**追加だけ止める**。
- **決済サービスは入れない。クーポンコードで付与する**（集金はアプリの外）。
- プレミアムが与えるもの（現時点の 3 つ）：
  1. **申請なしのリスト作成**（`createListDirectly`／`functions/src/callable/list_requests.ts`）。通常はサイト管理者の承認が要る（5.1）が、それを飛ばして名前を入れるだけで作れる。作れる数は無制限。
  2. **容量の自動拡張**。上限は**人ごとの合計**で、初期 2GB。90% を超えると 2GB ずつ、最大 10GB まで自動で増える。無償の人も上限 2GB だが**自動拡張だけが無い**（`functions/src/domain/quota.ts`）。
  3. **オフライン保存（ダウンロード）**（15.3）。
- 状態は `users/{uid}/private/state.premium.until`（本人だけが読める／13.3）に持ち、**真偽値は持たず期限だけ**で表す。切れると上記が使えなくなるだけで、リストもアップロード済みファイルも残る。判定は `functions/src/domain/premium.ts` の `isPremiumActive`。書き込みはサーバーのみ。
- サイト管理者は `extendPremium` で任意の利用者の期限を延ばせる。容量上限の個別調整は `setUserQuota`。

### 15.2 クーポン

- サイト管理画面の「クーポン管理」で**発行・一覧・使用人数の上限変更・停止・使用者の確認**ができる（`createCoupon` / `listCoupons` ほか／`site_admin_screens.dart`）。
- コードは**自動生成（既定・24 文字。読み違えやすい文字は使わない）と、文字列の指定**の両方を選べる。
- 利用者は設定画面の**「クーポンを入力」**で引き換える（`redeemCoupon`／`settings_screen.dart`）。**2 枚目のクーポンは月数を足す**（上書きしない）。同じ人が同じクーポンを二度使うことは、`coupons/{couponId}/redemptions/{uid}` で構造的に防ぐ。
- **`coupons` はルールで全面禁止**（クライアントから読めない。読めるとコードの一覧が漏れる）。発行・一覧・引き換えはすべて呼び出し可能関数を通す。

### 15.3 オフライン保存（ダウンロード）

- **プレミアム限定・モバイル（iOS / Android）限定**の機能。落とした曲は端末のサンドボックスに保存し、ほかのアプリからは見えない。アンインストール、およびプレミアム失効で端末から削除される。詳細は [DOWNLOAD-DESIGN.md](DOWNLOAD-DESIGN.md)。
- 使えるのは**メンバー（Read Only を含む）だけ**。閲覧者（viewer）は不可。サイト管理者もそのリストのメンバーでなければ不可（判定を「メンバーかつプレミアム」の 1 つに揃えるため）。
- 権限確認はサーバーの `verifyDownloadAccess`（`functions/src/callable/downloads.ts`。起動時に問い合わせる）。端末内の曲は「ダウンロード済み」画面（`/downloads`／`lib/ui/screens/downloads_screen.dart`）で管理する。
- **Web からは音源のダウンロードを外す**方針。ただし外す引き金は **Android の一般公開**で、それまでは従来どおり動く（音源以外のファイルと URL は外さない／`DOWNLOAD-DESIGN.md` 7）。この撤去はまだ実施していない。
