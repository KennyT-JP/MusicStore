## 1. 概要・目的

メンバーが個々に録音した音源や、YouTube 等で見つけた楽曲を、1 つのリストに集約して共有するためのアプリです。まず Web 版を開発し、将来的に Android / iOS アプリへの展開も見据えます。リストは複数作成でき、管理者がメンバーのアクセスを承認・管理します。

---

## 2. 対象プラットフォーム・技術スタック

| 区分 | 採用技術 | 備考 |
| --- | --- | --- |
| フロントエンド | **Flutter** | 1 つのコードで Web・Android・iOS に対応。まず Web、将来モバイル |
| バックエンド | **Firebase** | 下記の各サービスを利用 |
| データベース | Firestore | リスト・項目・コメント・ユーザー等の情報を保存 |
| 認証 | Firebase Authentication | Google 連携／メール＋パスワード |
| ファイル保存 | Firebase Storage（Cloud Storage） | 音源・動画などのファイル本体を保存 |
| プッシュ通知 | Firebase Cloud Messaging（FCM） | 将来のモバイル含むプッシュ通知 |

- **表示言語**：多言語対応とし、初期対応は **日本語・英語**。後から言語を追加しやすい設計にする。

## 3. アカウント・認証

### 3.1 ログイン方法
- Google アカウント連携
- メールアドレス＋パスワード
- **ログイン状態を保持**する（次回以降、自動でログインした状態を維持）
- メール＋パスワード登録者向けに、**パスワード再設定機能**（登録メールにリセット用リンクを送付）を用意

#### メールアドレスの確認（本人確認）

- **メール＋パスワードで登録した場合、メールアドレスの確認を必須**とする。
  - 登録すると確認メールが送られ、**リンクを押すまでアプリを利用できない**（ログインはできるが、「確認メールを送りました」の案内画面で止まる）。
  - 確認メールの再送ができるようにする。
- **Google アカウント連携での登録は確認不要**（Google 側で確認済みのため）。
- 未確認のまま招待 URL を受け取った場合も、**確認を済ませてからリストへ参加**する（3.3）。

### 3.1.1 未ログイン状態で URL を開いた場合

- 共有 URL・招待 URL のいずれも、**未ログインでは内容を一切表示しない**（リスト名も出さない）。
- まずログイン／サインアップ画面を表示し、**完了後に元の URL へ自動的に戻す**。戻った先で、共有 URL ならリスト名と参加申請ボタン（5.3）、招待 URL なら参加処理（3.3）が動く。
- URL を偶然拾っただけの第三者に、リスト名が漏れないようにするための扱い。

### 3.2 アカウント取得の 2 経路（両方対応）
1. **自己登録**：誰でも Google／メールでサインアップ可能。その後、リスト作成やリスト参加を申請できる。
2. **招待による登録**：サイト管理者・リスト管理者が招待 URL を発行して招く。

### 3.3 招待 URL の仕様
- 招待操作を行うと、**ワンタイムの招待 URL** が発行される。
- 管理者が任意の手段（メール等）でその URL を相手に伝え、受け取った人が URL をクリックすると参加できる。
- **有効期限あり**。初期値 **24 時間**。サイト管理者がサイト管理画面で変更可能。
- 発行時に、**対象リスト**と**付与する役割（Super User / Read Only）**をあらかじめ指定する。
- 発行できる人：**サイト管理者は誰に対しても**発行可／**リスト管理者は自分のリストへの招待のみ**発行可。

#### 招待 URL を受け取ってから参加するまでの流れ

招待された人がアカウントを持っているかどうかで分岐せず、**どちらの場合も URL を 1 回開くだけで参加が完了する**ようにする。

| 状態 | 流れ |
| --- | --- |
| ログイン済み | URL を開く → 確認画面 → 参加完了 |
| ログアウト中（アカウントあり） | URL を開く → ログイン → **元の URL へ自動で戻る** → 参加完了 |
| アカウント未取得 | URL を開く → サインアップ → （メール登録の場合はメール確認／3.1）→ **完了と同時に自動で参加** |

- **有効期限は「受諾した時点」で判定**する。URL を開いた時点ではなく、サインアップ・メール確認を終えて実際に参加処理が走る瞬間に期限内であればよい。
  - サインアップやメール確認に手間取ると期限切れになり得るため、期限切れの場合は「招待の有効期限が切れています。招待した方に再発行を依頼してください」と表示する。
- ワンタイム性の担保方法は 13.3（`invites`）を参照。同じ URL を複数人が同時に開いても、参加できるのは 1 人だけ。

### 3.4 表示名
- 初期値は Google の表示名（またはメール名）。
- ユーザーが後から自由に変更可能。

### 3.5 退会（アカウント削除）
- ユーザーは自分のアカウントを自分で削除（退会）できる。
- 退会後も、その人が登録した項目・コメント等の**投稿・履歴は残す**。表示名は「**退会したユーザー**」と表示（元の名前は出さない）。
- **例外**：自分が**最後のサイト管理者**である場合は退会できない（4.4 参照）。

## 4. 権限・役割

### 4.1 権限階層
```
サイト管理者 ＞ リスト管理者 ＞ Super User ＞ Read Only
```
- 上位の役割は、下位の役割の権限を**すべて包含**する。
- 役割は**リストごとに個別**に決まる（例：あるユーザーがリスト A では Super User、リスト B では Read Only、も可能）。

### 4.2 各役割の主な権限
| 役割 | 主な権限 |
| --- | --- |
| サイト管理者 | サイト全体の全権限。全リストの項目・コメントの編集・削除、全リストの削除、権限変更、リスト作成申請の承認、各種サイト設定 |
| リスト管理者 | 自分が管理するリスト内の全権限（項目・コメントの編集・削除、リスト削除、メンバー招待・承認・役割割当・除外、容量把握 等） |
| Super User | リストへの項目追加・アップロード、コメント・返信 |
| Read Only | 閲覧のみ（全項目・全コメントの閲覧、音源再生・URL アクセス可）。追加・コメントは一切不可 |

### 4.3 権限の管理
- 各ユーザーの役割変更は、**サイト管理者・リスト管理者**が行う。
- 管理者自身もアップロード・コメントができる（上位は下位の権限を包含するため）。

### 4.4 サイト管理者の初期設定
- 最初のサイト管理者は、**システムを立ち上げた人**を初期サイト管理者として登録する。
- 以後、サイト管理者は他の人をサイト管理者に昇格できる。

### 4.5 サイト管理者が 0 人になることの防止

サイト管理者が 0 人になると、リスト作成申請の承認も権限変更もできなくなり、**アプリ内からは誰も復旧できない**。これを構造的に防ぐ。

- **サイト管理者が 1 人しかいない場合、その人は自分を降格できず、退会もできない**。
- 該当する操作をしようとした場合は、次のように案内してブロックする。
  > 「あなたは現在ただ 1 人のサイト管理者です。先に別の方をサイト管理者に指名してください。」
- 判定はサーバー側（Cloud Functions）で行う。画面上でボタンを無効化するだけでは、他の経路からの操作を防げないため。
- サイト管理者の人数は `siteConfig/global` に保持し、昇格・降格・退会のたびに更新する（13.3）。

> **補足**：リスト管理者については、0 人（管理者不在）になることを許容し、サイト管理者が後から指名する運用としている（5.6）。サイト管理者だけは上位の救済先が存在しないため、扱いを分けている。

## 5. リスト管理

### 5.1 リスト作成（申請制）
- 新規リストは**サイト管理者への申請制**。
- 申請に必要な情報：
  - **リスト名**（申請時に、既存の全リストと**重複チェック**を行う）
  - 概算の**登録曲数**
  - **使用者数**
  - **作成目的**
- サイト管理者が申請を確認して承認する。
- 承認されると、**申請者がそのリストのリスト管理者**になる。
- 申請は**初期ユーザーを含め、誰でも**可能。

### 5.2 既存リストへの参加（2 経路）
1. **招待 URL 経由**（3.3 参照）。
2. **参加申請**：リストの共有 URL から参加を申請する。
   - 申請者は役割を選べない（**アクセス申請のみ**）。
   - **リスト管理者が承認時に役割（Super User / Read Only）を決定**する。

### 5.2.1 申請の状態確認と却下後の扱い（リスト作成申請・参加申請の共通ルール）

- ユーザーは**自分が出した申請の一覧と状態**（申請中／承認／却下）を、いつでも画面で確認できる。
- **却下されても通知は送らない**（10.2 のとおり）。ただし申請一覧を見に行けば「却下」と分かる。
- **却下された後は、同じ申請をやり直せる**。回数の制限は設けない。
- 却下理由は入力させない（管理者の負担と気まずさを避けるため）。

> **意図**：通知を送らないのは「わざわざ知らせない」ためであり、「隠す」ためではない。申請者が永遠に待ち続ける状態や、管理者への問い合わせが発生する状態を避ける。

### 5.3 リストの見え方・発見方法
- 全リストの一覧を公開する画面は**作らない**。
- リストは、**既存参加者から共有 URL をもらって**発見・申請する。
- 未参加者が共有 URL を開いた場合：**リスト名など最低限の情報＋「参加申請」ボタンのみ**を表示。中身（曲・コメント）は承認されるまで見えない。

### 5.4 メンバーの除外・離脱
- **リスト管理者（以上）**は、メンバーをそのリストから外す（アクセス権を取り消す）ことができる。
- **メンバー自身**も、自分からリストを抜けることができる。
- 外された／抜けた後も、その人の投稿・履歴は残す。表示名は「**退会したユーザー**」と表示。
- **除外・離脱した人は、あらためて参加申請できる**（5.2）。除外された人と自分で抜けた人を区別せず、どちらも同じ扱いとする。
  - 入れ直すかどうかはリスト管理者がその都度判断する。ブロックリストのような仕組みは設けない。
  - 誤って外してしまった場合も、招待 URL を送るか申請を承認すればすぐ戻せる。
- **リスト管理者自身が抜ける場合**、そのリストのリスト管理者が自分ひとりであれば、抜けた時点で**管理者不在のリスト**になる（5.6）。サイト管理者が別の人を指名するまでその状態が続く。

### 5.5 リスト削除
- **リスト管理者**は自分のリストを削除できる。
- **サイト管理者**は全リストに対して全権限を持つ（どのリストでも削除可）。
- リストを削除すると、そのリストのファイル・コメントも**すべて削除**される。

### 5.6 管理者不在時の扱い
- リスト管理者が 1 人だけの状態でその人が退会した場合、そのリストは**管理者不在のまま保持**する。
- **サイト管理者が新しいリスト管理者を指名する**まで、その状態を維持する。
- サイト管理画面で「管理者不在のリスト」を確認・指名できるようにする。

## 6. リスト項目

### 6.1 項目の単位
- 1 項目 ＝ **音源ファイル 1 つ**、または **URL 1 つ**（両方の混在・複数登録は不可）。

### 6.2 項目が持つ情報
| 項目 | 内容 |
| --- | --- |
| 連番 | リストごとに 1 から採番。**振り直しなし**。削除時は欠番を残し、リスト上に「**削除されました**」と表示（ソフト削除） |
| 日付 | 録音日を想定（ただし厳密な意味は持たせない）。初期値は当日、**自由に変更可**。**時刻もタイムゾーンも持たない「年月日」だけの値**（下記） |
| ファイル または URL | 音源ファイル、または URL のいずれか |
| 曲名 | **任意** |
| アーティスト名 | **任意** |
| 登録者 | **ログインユーザーを自動記録** |
| コメント | **任意**（追加・アップロード時に記入できる） |

#### 日付の扱い（タイムゾーン）

- 項目の「日付」は、**時刻もタイムゾーンも持たない年月日の値**として保存する（`2026-08-04` のような文字列相当）。
- **どの国・どの端末から見ても、登録した人が入力したとおりの日付が表示される**。時差による 1 日のずれは発生しない。
- 初期値の「当日」は、**入力する人の端末のローカル日付**を用いる。
- これはユーザーが意味を持たせる日付（録音日）に限った扱い。**投稿日時・更新日時などのシステムが記録する日時は、通常のタイムスタンプとして保存し、見る人の現地時刻で表示**する。

### 6.3 編集・削除

- 項目の**全フィールドを編集可能**（登録済みの**ファイル／URL そのものの差し替え**も含む）。
- 編集・削除できる人：**登録した本人**、および自リストのリスト管理者、サイト管理者（4.2 参照）。
- **削除には猶予期間がある**。削除した項目は一覧上「削除されました」と表示されるが、ファイル本体は**一定期間（初期値 30 日）Storage に保持**され、その間はリスト管理者以上が**復元できる**。猶予期間を過ぎるとファイルは完全に削除され、使用容量が減る（詳細は 13.4）。
- **ファイルを差し替えた場合も、旧ファイルは同じ猶予期間だけ保持**される。
- 猶予期間中は**容量を消費し続ける**ため、上限に近いリストでは削除してもすぐには空きが増えない点に注意（7.2）。

#### 同時編集の扱い

2 人が同じ項目（またはコメント）を同時に編集していた場合、**後から保存した人が、先に保存された内容を知らないまま上書きしてしまう**ことがある。バックアップを持たない方針（12.3）のため、これを防ぐ。

- 編集画面を開いた時点の更新日時を保持しておき、**保存時に「開いてから他の人が更新していないか」を確認**する。
- 更新されていた場合は**保存を中止**し、次のように表示する。
  > 「ほかの方がこの項目を更新しました。最新の内容を読み込み直してください。」
- ユーザーは最新内容を読み込み直したうえで、編集をやり直す。
- **編集中のロックは行わない**（ブラウザを閉じられたときにロックが残るため）。
- この確認はサーバー側（Firestore のトランザクション）で行い、画面上のチェックだけに頼らない。

### 6.4 表示・並び替え・検索
- **並び替え**：連番／日付／登録者 で並び替え可能。
- **検索**：曲名・アーティスト名で検索。曲名・アーティスト名が未記入の項目は、**ファイル名で検索**できるようにする。
- リスト上は、URL やファイル名を**そのまま表示**し、**リンク**を付ける。

#### 削除済み項目の見え方

- **既定では削除済み項目も一覧に表示**し、欠番の位置に「削除されました」と出す。連番が飛んでいる理由が誰にでも分かる状態にする。
- 一覧上の**切り替えで、削除済み項目を非表示にできる**。削除が積み上がっても一覧が見づらくならないようにするため。
  - 切り替えは全メンバー（Read Only 含む）が使える。設定は端末側に保持し、次に開いたときも維持する。
- **削除済み項目は検索の対象に含めない**。検索は「今ある曲を探す」ための機能と位置づける。
- 削除済み項目には、曲名・アーティスト名・ファイル名・URL を表示しない（「削除されました」とだけ表示する）。**復元操作はリスト管理者以上のみ**が行える（6.3）。

## 7. ファイル・容量

### 7.1 アップロード対象
- 主に mp3・mp4 を想定するが、**ファイル種別は制限しない**（他形式も可）。
- ファイル本体は **Firebase Storage** に保存し、Firestore には「どのファイルがどこにあるか」等のメタ情報のみを持たせる。

### 7.2 容量上限（クォータ）
- **リスト単位の合計容量に上限**を設ける。
- 初期値 **1GB**。**サイト管理者がリストごとに個別**に上限を設定できる（サイト管理画面）。
- **ファイル単位の上限は設けない**。

### 7.3 容量に関する通知・挙動
- 使用量が **80% を超えたら「Notice」**、**90% を超えたら「警告」**を、**リスト管理者**へ通知する。
- 上限を超えた状態でアップロードしようとした場合：「**上限を超えました。リスト管理者にご連絡ください**」と表示し、アップロードをブロックする。

### 7.4 使用量の可視化
- **サイト管理画面**：全リストの容量使用量を表示。
- **リスト管理者**：自分のリストの容量使用量を把握できる。

### 7.5 アップロードの手順と、失敗・中断時の扱い

**基本方針：ファイルのアップロードが完全に終わってから、項目を作成する。**

#### 手順

1. ユーザーがファイルを選び、曲名・日付などを入力して「追加」を実行する。
2. **先に Storage へファイルをアップロード**する。この間、進捗を表示し、**キャンセルできる**ようにする。
3. アップロードが完了したら、**項目を作成する**（このときに連番が採番される／13.3）。
4. 項目の作成まで終わって、はじめて一覧に表示される。

#### 失敗・中断したとき

- 通信が切れた／ブラウザを閉じた／キャンセルした場合、**項目は作成されない**。
  - 一覧に中途半端な項目が残らない。
  - **連番も消費しない**（欠番が無駄に増えない）。
- Storage 側に**行き場を失ったファイル**が残ることがある。これは**定期実行（1 日 1 回）で自動削除**する（13.4）。
  - 判定条件：Storage 上にあるが、**対応する項目が存在せず、かつアップロードから 24 時間以上経過**しているファイル。
  - 削除に連動して使用容量も戻る。
- ユーザーには「アップロードに失敗しました。もう一度お試しください」と表示し、**やり直しを促す**。中断したところからの再開機能は設けない。

#### 容量チェックのタイミング

- **アップロードを始める前**に、そのファイルのサイズを加えても上限を超えないかを確認する。超える場合は 7.3 のメッセージを表示し、**アップロード自体を開始しない**（無駄な通信と課金を避けるため）。
- 同時アップロードなどで、開始時のチェックをすり抜けて上限を超えることがあり得る。その場合も**アップロード済みのファイルは削除せず受け入れ**、以後のアップロードをブロックする。

## 12. 運用・非機能に関する方針

### 12.1 Firebase の料金プラン

- **Blaze プラン（従量課金）を採用**する。Cloud Functions・Storage・FCM を本格利用するため、無料の Spark プランでは要件を満たせない。
- ただし、**Google Cloud の予算アラートを必ず設定**し、想定月額を超えた場合はメール通知が届くようにする。
  - 予算アラートのしきい値は、想定月額に対して **50% / 90% / 100%** の 3 段階で設定する。
  - 通知先はサイト管理者のメールアドレス。
- Blaze プランには各サービスの無料枠がそのまま適用されるため、**小規模利用のうちは実質無償**で運用できる見込み。無料枠を超えた分のみ課金される。
- **予算超過時の自動停止（課金の自動無効化）は実装しない**。サービスが止まる影響のほうが大きいため、アラートによる検知と手動対応で運用する。
- 想定利用量に応じた概算見積もりは別途整理する。

### 12.2 デプロイ・ホスティング・環境構成

- Web 版は **Firebase Hosting** にデプロイする。
- **本番環境と検証（ステージング）環境を、別々の Firebase プロジェクトとして分離**する。

| 環境 | 用途 | Firebase プロジェクト |
| --- | --- | --- |
| 本番（production） | 実際の利用者が使う環境 | 本番用プロジェクト |
| 検証（staging） | 新機能の動作確認・リハーサル | 検証用プロジェクト |

- 環境を分ける理由：Firestore のデータ・Storage のファイル・認証ユーザーがプロジェクト単位で完全に独立するため、**検証作業が本番データを壊す事故を構造的に防げる**。
- Flutter 側は **ビルド時に接続先の Firebase 設定を切り替える**構成にする（環境ごとの設定ファイルを用意し、ビルドフレーバー／`--dart-define` 等で切り替え）。
- 予算アラート（12.1）は**本番・検証の両プロジェクトに設定**する。検証環境の想定額は本番より低く設定する。
- 公開 URL は当面 Firebase Hosting の既定ドメイン（`*.web.app` / `*.firebaseapp.com`）を使用し、独自ドメインの割り当ては将来の検討事項とする。

### 12.3 バックアップ・エクスポート方針

- **定期自動バックアップは組まない**。バックアップ保管にかかるストレージ課金を抑えることを優先する。
- 必要が生じたときに、**サイト管理者が手動でエクスポート**する運用とする。
  - Firestore：`gcloud firestore export` によるデータのエクスポート。
  - Storage：`gsutil` / `gcloud storage` によるファイルの一括ダウンロードまたは別バケットへのコピー。
- **アプリ側にバックアップ／エクスポート用の画面は作らない**（初期リリースでは対象外）。
- 手動エクスポートの具体的な手順は、**運用手順書として別途整備**する。

> **留意事項（リスクの明示）**
> 定期バックアップを持たないため、**誤操作や不具合でデータが失われた場合、直前の状態には戻せない**。特に以下の操作は復旧手段がないことを前提に扱う。
> - リストの削除（5.5：ファイル・コメントもすべて削除される）
> - 項目のファイル／URL の差し替え（6.3：元のファイルは残らない）
>
> 実運用の負荷が見えてきた段階で、定期自動バックアップの導入を改めて検討する。

### 12.4 利用規約・プライバシーポリシー

- **初期リリースでは作成しない**。身内・少人数での限定利用を前提とし、規約への同意フローも実装しない。
- **外部に広く公開する段階になった時点で、改めて整備する**。その際に検討すべき主な論点は以下のとおり。
  - アップロードされた音源・動画の**著作権・権利処理**（誰の責任で投稿するか）
  - 権利侵害の申し立てがあった場合の**削除対応の手順**
  - 収集する個人情報の範囲（メールアドレス・表示名・Google アカウント情報）と利用目的
  - 退会後もデータが残る仕様（3.5）の明示

> **留意事項**
> 規約がなくても、**サイト管理者は全リストの項目・コメントを削除できる**（4.2）ため、問題のある投稿への対処手段は仕様上確保されている。

### 12.5 UI デザインの方針

- **Flutter 標準の Material Design をそのまま使う**。独自のデザインシステム・テーマは作らない。実用性とスピードを優先する。
- **レスポンシブ対応は初期リリースから行う**。PC ブラウザとスマートフォンのブラウザの両方で、破綻せず使えることを最低ラインとする。
  - 画面幅に応じてレイアウトを切り替える（広い幅＝表形式に近い一覧、狭い幅＝1 行ずつのカード／リスト表示）。
- リスト項目の一覧は、**行形式のシンプルな表示**とする（連番・日付・曲名／ファイル名・登録者が一目で分かる並び）。
- 詳細なレイアウトは実装しながら詰める方針とし、**事前のモックアップ作成やデザイントーンの決定は行わない**。
- 多言語対応（2 章）に伴い、**文言は日本語・英語で長さが変わる**ため、テキストが固定幅で溢れない作りにする。

### 12.6 テスト・品質保証の方針

**方針：壊れると影響が大きいロジックは自動テストで守り、画面操作はステージング環境での手動確認でカバーする。**

#### 自動テストを書く対象（必須）

| 対象 | 理由 |
| --- | --- |
| 権限判定ロジック（4 章） | 役割ごとの可否を間違えると、見えてはいけない情報が見えてしまう |
| Firestore セキュリティルール | クライアントを信用しない最後の防波堤。ルール単体で検証する必要がある |
| 容量上限の判定（7.2・7.3） | 80%／90% の通知境界、上限超過時のアップロードブロック |
| 連番の採番（6.1・6.2） | 振り直しなし・欠番維持という仕様が崩れると復旧できない |
| 招待 URL の検証 | ワンタイム性・有効期限切れの判定 |

- Firestore セキュリティルールは **Firebase Emulator Suite** 上でテストする（本番・検証プロジェクトに触れずに検証できる）。
- ロジックのテストは Flutter の単体テスト（`flutter test`）で記述する。

#### 手動確認でカバーする対象

- 画面のレイアウト・レスポンシブ表示（PC／スマートフォン）
- 認証フロー（Google 連携・メール＋パスワード・パスワード再設定）
- ファイルのアップロード／ダウンロード／外部アプリでの再生
- 通知の到達（アプリ内通知・プッシュ通知）
- 日本語・英語の表示切り替え

- 手動確認は**検証（ステージング）環境**で行う（12.2）。本番反映前の確認手順は、確認観点リストとして別途整備する。

#### 今回は行わないこと

- **E2E テスト（自動）は作らない**。作成・維持のコストが見合わないため、上記の手動確認で代替する。
- **CI（GitHub Actions 等）での自動実行は初期リリースでは組まない**。テストはローカルで実行する。開発が続き手動実行の負担が増えてきた段階で、改めて導入を検討する。

### 12.7 通知の実装範囲（10 章の細部）

- **初期リリースでは、アプリ内通知（ベルアイコン）のみを実装する。**
- **プッシュ通知（FCM）は初期リリースの対象外**とし、モバイル版（Android / iOS）の開発時にまとめて対応する。Web プッシュはブラウザごとの差が大きく、通知許可の取得も必要になるため、Web 単独での先行実装は行わない。
- **まとめ通知（集約表示）は行わない**。通知は 1 件ずつ、発生の都度リアルタイムに積む。
- **メールでの通知は行わない**（12.1 の予算アラートは Google Cloud 側の機能であり、これとは別）。

#### 通知設定への影響（10.3 の補足）

- 通知設定画面には、**種別ごとのアプリ内通知の On/Off と、全体のマスタースイッチ**を用意する。
- **プッシュ通知の On/Off 項目は、初期リリースでは画面に表示しない**。ただし将来の追加を見越し、**データ構造としてはプッシュ通知の設定値を最初から保持できる形**にしておく（既定値はオン）。

#### アプリ内通知の扱い

- 未読／既読の状態を持ち、ベルアイコンに**未読件数**を表示する。
- 通知をタップすると、対象のリスト・項目・コメントへ遷移する。
- 通知の保持期間・上限件数は、運用しながら決める（初期は無制限に保持し、問題が出たら見直す）。

## 13. データモデル（Firestore / Storage）

### 13.1 設計の基本方針

| 方針 | 内容 |
| --- | --- |
| 入れ子構成 | `lists/{listId}` の配下に項目・メンバー・コメントをぶら下げる。セキュリティルールをパス単位で書けるため、未参加者に中身を見せない要件（5.3）を構造で担保できる |
| メンバー情報は一元管理 | 役割は `lists/{listId}/members/{uid}` の 1 か所のみに持つ。ユーザー側へのミラーは行わない |
| コメントはフラット | 無制限の入れ子（9 章）を、親 ID とパス配列で表現する |
| 表示名は参照で解決 | 項目・コメントには uid のみを持ち、名前は表示時に `users` から引く |
| サーバー側で守る値 | 連番・使用容量など、狂うと困る値はトランザクションまたは Cloud Functions で更新し、クライアントからは書けないようにする |

### 13.2 コレクション全体像

```
users/{uid}
  └ notifications/{notificationId}

lists/{listId}                       ← 公開可能な最小情報のみ
  ├ meta/stats                       ← 容量・連番などの内部情報（メンバーのみ）
  ├ members/{uid}
  ├ joinRequests/{uid}
  └ items/{itemId}
      └ comments/{commentId}

listNames/{nameLower}                ← リスト名の重複チェック用
listRequests/{requestId}             ← リスト作成申請
invites/{inviteId}                   ← 招待 URL
siteConfig/global                    ← サイト全体の設定
```

#### `lists/{listId}` を 2 段に分けている理由

Firestore の読み取り権限は**ドキュメント単位**で、「このフィールドだけ見せる」ということができない。5.3 で「未参加者が共有 URL を開いたらリスト名など最低限の情報だけ見える」と決めているため、**公開してよい情報**と**メンバーにしか見せたくない情報**を別ドキュメントに分ける必要がある。

- `lists/{listId}` … リスト名・作成日時など。ログイン済みユーザーなら誰でも読める。
- `lists/{listId}/meta/stats` … 使用容量・連番カウンタなど。そのリストのメンバーのみ読める。

### 13.3 各ドキュメントの構造

#### `users/{uid}` — ユーザー

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `displayName` | string | 表示名（3.4）。初期値は Google の表示名またはメール名 |
| `email` | string | メールアドレス |
| `photoURL` | string? | アイコン画像 |
| `locale` | string | 表示言語（`ja` / `en`） |
| `isWithdrawn` | bool | 退会済みかどうか（3.5） |
| `withdrawnAt` | timestamp? | 退会日時 |
| `notificationSettings` | map | 通知設定（10.3）。下記参照 |
| `createdAt` / `updatedAt` | timestamp | |

- **退会時は `users/{uid}` を削除せず、`isWithdrawn` を true にする**。過去の投稿は uid 参照のままなので、この 1 か所を変えるだけで全投稿の表示が「退会したユーザー」に切り替わる。
- `notificationSettings` の形（プッシュは 12.7 により初期リリースでは画面に出さないが、値は最初から保持する）：

```
notificationSettings: {
  master: true,                                  // 全体のマスタースイッチ
  types: {
    itemAdded:      { inApp: true, push: true },
    commentAdded:   { inApp: true, push: true },
    quotaNotice:    { inApp: true, push: true },
    quotaWarning:   { inApp: true, push: true },
    listRequested:  { inApp: true, push: true },
    joinRequested:  { inApp: true, push: true },
    requestApproved:{ inApp: true, push: true },
  }
}
```

#### `users/{uid}/notifications/{notificationId}` — アプリ内通知

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `type` | string | 通知種別（上記 `types` のキー） |
| `listId` / `itemId` / `commentId` | string? | 遷移先の特定に使う |
| `actorUid` | string? | 通知のきっかけを作った人 |
| `isRead` | bool | 既読フラグ（未読件数の集計に使う） |
| `createdAt` | timestamp | |

- 通知は Cloud Functions が受信者ごとに 1 件ずつ作成する（まとめ通知は行わない／12.7）。

#### `lists/{listId}` — リスト（公開可能な情報のみ）

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `name` | string | リスト名 |
| `nameLower` | string | 重複チェック用の正規化名 |
| `createdBy` | string | 作成者（＝承認時のリスト管理者）の uid |
| `createdAt` / `updatedAt` | timestamp | |
| `adminCount` | number | リスト管理者の人数。**0 なら管理者不在**（5.6）。サイト管理画面での抽出に使う |
| `memberCount` | number | メンバー数 |

#### `lists/{listId}/meta/stats` — リストの内部情報（メンバーのみ）

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `nextSeq` | number | 次に採番する連番（6.2）。初期値 1 |
| `usedBytes` | number | 使用容量（7.2） |
| `quotaBytes` | number | 容量上限。初期値 1GB（`1073741824`） |
| `notifiedNotice80` | bool | 80% 通知の送信済みフラグ（重複通知の防止） |
| `notifiedWarning90` | bool | 90% 通知の送信済みフラグ |

- **クライアントからの書き込みは一切禁止**。連番はトランザクション、容量は Cloud Functions が更新する。
- 使用量が各しきい値を下回ったら、対応するフラグを false に戻す（再び超えたときに改めて通知するため）。

#### `lists/{listId}/members/{uid}` — メンバーと役割

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `role` | string | `listAdmin` / `superUser` / `readOnly` |
| `joinedAt` | timestamp | |
| `addedBy` | string? | 招待・承認を行った人の uid |
| `via` | string | `invite` / `request` / `founder`（作成者） |

- **サイト管理者はここに含めない**。サイト管理者は全リストへの権限をカスタムクレームで持つため（13.5）、メンバー登録は不要。
- 「自分の参加リスト一覧」は、`members` に対する **collectionGroup クエリ**（ドキュメント ID＝自分の uid で絞り込み）で取得する。この用途で複合インデックスを 1 つ作成する。
- **メンバーを除外したとき／本人が抜けたときは、このドキュメントを削除する**。投稿自体は残るため（5.4）、表示は次のルールになる。

> **「退会したユーザー」と表示する条件**
> 1. `users/{uid}.isWithdrawn` が true（＝アカウント退会／3.5）
> 2. または、その uid が**そのリストの `members` に存在しない**（＝除外された／自分で抜けた／5.4）
>
> どちらの場合も元の表示名は出さず、「退会したユーザー」と表示する。

#### `lists/{listId}/items/{itemId}` — リスト項目

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `seq` | number | 連番（6.2）。振り直しなし |
| `date` | string | 録音日想定。`YYYY-MM-DD` 形式の**文字列**。タイムゾーンを持たせないため、あえてタイムスタンプ型を使わない（6.2） |
| `kind` | string | `file` または `url`（どちらか一方のみ／6.1） |
| `file` | map? | `kind == 'file'` のとき。下記参照 |
| `url` | string? | `kind == 'url'` のとき |
| `title` | string? | 曲名（任意） |
| `artist` | string? | アーティスト名（任意） |
| `createdBy` | string | 登録者の uid（自動記録） |
| `createdAt` | timestamp | |
| `updatedBy` / `updatedAt` | string / timestamp | 最終更新者・更新日時 |
| `status` | string | `active` / `deleted`（ソフト削除） |
| `deletedBy` / `deletedAt` | string / timestamp | 削除者・削除日時 |
| `purgeAt` | timestamp? | ファイル本体の完全削除予定日時（13.4） |

`file` マップの内容：

```
file: {
  storagePath: 'lists/{listId}/items/{itemId}/{fileName}',
  fileName:    'take01.mp3',
  sizeBytes:   5242880,
  contentType: 'audio/mpeg',
}
```

- 項目の初回コメント（6.2）は、独立したコメントドキュメントとして `comments` に作成する。項目内には持たない。
- **`updatedAt` は同時編集の検出にも使う**（6.3）。編集画面を開いたときの `updatedAt` を保持し、保存時にトランザクション内で現在値と突き合わせる。一致しなければ保存を中止して警告を出す。コメントも同じ方式。

#### `lists/{listId}/items/{itemId}/comments/{commentId}` — コメント

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `body` | string | 本文 |
| `parentId` | string? | 返信先コメントの ID。ルートコメントは `null` |
| `path` | array&lt;string&gt; | ルートから親までの ID を順に並べた配列。ルートコメントは `[]` |
| `depth` | number | 階層の深さ。ルートは 0 |
| `createdBy` | string | 投稿者の uid |
| `createdAt` / `updatedAt` | timestamp | |
| `status` | string | `active` / `deleted` |

- **項目のコメントは 1 回のクエリで全件取得し、アプリ側でツリーに組み直す**。`path` を持たせているのは、スレッド順（親の直下に子が並ぶ順序）でソートするため。
- 返信がぶら下がっているコメントを削除した場合、`status` を `deleted` にして「削除されました」と表示し、**子の返信は残す**（親を物理削除するとツリーが切れるため）。

#### `listNames/{nameLower}` — リスト名の重複チェック

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `listId` | string? | 確定済みリストの ID |
| `requestId` | string? | 申請中の場合の申請 ID |
| `reservedAt` | timestamp | |

- 5.1 の重複チェックを、**ドキュメント ID の存在確認だけで行う**ための仕組み。
- `lists` コレクションを名前で検索する方式にすると、未参加者が全リスト名を列挙できてしまい、5.3（全リスト一覧は公開しない）に反する。ID 直接指定なら「その名前があるか」しか分からない。

#### `listRequests/{requestId}` — リスト作成申請（5.1）

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `listName` / `nameLower` | string | 申請するリスト名 |
| `estimatedTrackCount` | number | 概算の登録曲数 |
| `expectedUserCount` | number | 使用者数 |
| `purpose` | string | 作成目的 |
| `requestedBy` / `requestedAt` | string / timestamp | 申請者・申請日時 |
| `status` | string | `pending` / `approved` / `rejected` |
| `decidedBy` / `decidedAt` | string / timestamp | 承認・却下したサイト管理者と日時 |
| `createdListId` | string? | 承認時に作成されたリストの ID |

- 承認処理は Cloud Functions で行い、**リスト作成・`listNames` の確定・申請者を `listAdmin` として `members` に登録・申請者への承認通知**までを一括で実行する。
- **却下時は `listNames` の予約を解放**する。その名前を他の人が申請できるようにするため。
- 却下された申請は、申請者の申請一覧に「却下」として残す（5.2.1）。**再申請は新しいドキュメントとして作成**する。

#### `lists/{listId}/joinRequests/{uid}` — 参加申請（5.2）

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `requestedAt` | timestamp | |
| `status` | string | `pending` / `approved` / `rejected` |
| `assignedRole` | string? | 承認時にリスト管理者が決めた役割 |
| `decidedBy` / `decidedAt` | string / timestamp | |

- ドキュメント ID を申請者の uid にすることで、**同じ人が二重に申請することを構造的に防ぐ**。
- 申請者は役割を選べない（5.2）。`assignedRole` は承認側だけが書き込める。
- **却下後の再申請**（5.2.1）は、同じドキュメントを `pending` で上書きして行う。`decidedBy` / `decidedAt` / `assignedRole` はクリアする。過去の却下履歴は保持しない。
- 承認されるとメンバー登録され、この申請ドキュメントは削除する。除外・離脱した人が再申請する場合（5.4）も、同じ経路で新たに作成される。

#### `invites/{inviteId}` — 招待 URL（3.3）

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `listId` | string | 招待先のリスト |
| `role` | string | 付与する役割（`superUser` / `readOnly`） |
| `createdBy` / `createdAt` | string / timestamp | 発行者・発行日時 |
| `expiresAt` | timestamp | 有効期限。発行時点＋`siteConfig.inviteExpiryHours` |
| `status` | string | `active` / `used` / `revoked` |
| `usedBy` / `usedAt` | string? / timestamp? | 使用者・使用日時 |

- `inviteId` は**推測できないランダムな文字列**とし、これがそのまま招待 URL に載る。
- ワンタイム性の担保：招待の受諾は Cloud Functions で行い、**「有効期限内かつ `status == 'active'` であること」の確認と、`members` への登録・`status` の `used` への更新を 1 つのトランザクションで実行**する。同じ URL を同時に複数人が開いても、成立するのは 1 人だけになる。
- トップレベルに置いているのは、**まだそのリストのメンバーでない人が読む必要がある**ため。

#### `siteConfig/global` — サイト設定（11.1）

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `inviteExpiryHours` | number | 招待 URL の有効期限。初期値 24 |
| `defaultQuotaBytes` | number | 新規リストの容量上限の初期値。`1073741824`（1GB） |
| `itemPurgeGraceDays` | number | 削除項目のファイル保持日数（13.4）。初期値 30 |
| `orphanFileGraceHours` | number | 行き場を失ったファイルを削除するまでの猶予時間（7.5）。初期値 24 |
| `siteAdminCount` | number | サイト管理者の人数。**1 のときは降格・退会をブロック**する（4.5） |

- 読み取りは全ログインユーザー、書き込みはサイト管理者のみ（`siteAdminCount` は Cloud Functions のみ）。

### 13.4 サーバー側で行う処理（Cloud Functions）

| 契機 | 処理 |
| --- | --- |
| Storage へのファイル保存 | `meta/stats.usedBytes` に加算し、80%／90% のしきい値を超えたらリスト管理者へ通知（7.3） |
| Storage からのファイル削除 | `meta/stats.usedBytes` から減算し、しきい値を下回ったら通知済みフラグをリセット |
| 項目の作成 | リスト管理者・サイト管理者へ通知（10.2） |
| コメントの作成 | リスト管理者・サイト管理者、および親コメント／項目の投稿者本人へ通知 |
| リスト作成申請の承認 | リスト・`listNames`・`members`・通知をまとめて作成 |
| 招待 URL の受諾 | 有効性の検証と `members` 登録をトランザクションで実行 |
| メンバーの追加・削除 | `lists/{listId}` の `memberCount` / `adminCount` を更新 |
| サイト管理者の昇格・降格・退会 | カスタムクレームを付け外しし、`siteConfig.siteAdminCount` を更新。**残り 1 人のときの降格・退会は拒否**（4.5） |
| 新規ユーザーの作成 | `users/{uid}` を初期化（表示名・通知設定の既定値） |
| 定期実行（1 日 1 回） | ①猶予期間を過ぎた削除項目のファイルを Storage から完全削除（下記）／②行き場を失ったファイルの削除（7.5） |

#### 削除項目のファイル保持と完全削除

- 項目を削除すると、`status` を `deleted` にしたうえで **`purgeAt` に「削除日時＋`itemPurgeGraceDays`（初期値 30 日）」を設定**する。
- 猶予期間中は、**リスト管理者・サイト管理者が項目を復元できる**（`status` を `active` に戻し、`purgeAt` を消す）。
- 猶予期間を過ぎると、定期実行の Cloud Functions が Storage のファイルを削除する。これに連動して `usedBytes` が減る。
- **猶予期間中は容量を消費し続ける**点に注意。上限に近いリストでは、削除してもすぐには空きが増えない。
- 項目のドキュメント自体は完全削除後も残す（連番の欠番を維持し「削除されました」と表示するため／6.2）。

> **ファイル差し替え時の扱い（6.3）**
> 登録済みファイルを差し替えた場合も、**旧ファイルは同じ猶予期間（初期値 30 日）を置いてから削除**する。誤って差し替えたときに戻せる余地を残す。

#### 行き場を失ったファイルの削除（7.5）

- アップロードは完了したが項目の作成に至らなかったファイルは、Storage 上に取り残される。
- 定期実行の Cloud Functions が、**対応する項目が存在せず、かつアップロードから `orphanFileGraceHours`（初期値 24 時間）以上経過した**ファイルを削除する。
- 猶予時間を置いているのは、**アップロード完了から項目作成までの短い間に消してしまわないため**。

### 13.5 権限判定とセキュリティルール

#### サイト管理者の判定

- **Firebase Authentication のカスタムクレーム**（`siteAdmin: true`）で保持する。
- セキュリティルールから追加の読み取りなしに判定できるため、高速かつ課金が発生しない。
- 付与・剥奪は Cloud Functions（サイト管理者のみ実行可）で行う。
- **注意**：カスタムクレームは認証トークンに埋め込まれるため、**変更が反映されるのはトークン更新後**（再ログイン、またはアプリ側でのトークン強制リフレッシュ）。権限を変更したら、対象ユーザーに再ログインを促す。

#### ルールの基本構造

```
// 判定用のヘルパー
isSiteAdmin()      : request.auth.token.siteAdmin == true
memberRole(listId) : get(lists/{listId}/members/{uid}).role
isListAdmin(listId): isSiteAdmin() || memberRole(listId) == 'listAdmin'
canWrite(listId)   : isListAdmin(listId) || memberRole(listId) == 'superUser'
isMember(listId)   : isSiteAdmin() || members ドキュメントが存在する
```

| パス | 読み取り | 書き込み |
| --- | --- | --- |
| `lists/{listId}` | ログイン済みなら誰でも（5.3 の最低限の情報） | サイト管理者・リスト管理者のみ（統計フィールドは Functions のみ） |
| `lists/{listId}/meta/stats` | メンバーのみ | **不可**（Functions とトランザクションのみ） |
| `lists/{listId}/members/{uid}` | メンバーのみ／自分の行は本人も可 | サイト管理者・リスト管理者。ただし本人による削除（離脱）は可 |
| `lists/{listId}/items/**` | メンバーのみ | Super User 以上。編集・削除は本人＋リスト管理者以上（6.3） |
| `lists/{listId}/items/*/comments/**` | メンバーのみ | Super User 以上。編集・削除は本人＋リスト管理者以上（9 章） |
| `lists/{listId}/joinRequests/{uid}` | リスト管理者以上／自分の行は本人も可 | 作成は本人のみ、承認・却下はリスト管理者以上 |
| `listNames/{nameLower}` | ログイン済みなら誰でも（ID 直接指定のみ／一覧取得は禁止） | **不可**（Functions のみ） |
| `listRequests/{requestId}` | サイト管理者／申請者本人 | 作成は本人、承認・却下はサイト管理者 |
| `invites/{inviteId}` | ログイン済みなら誰でも（ID を知っている人だけ到達できる） | **不可**（発行・受諾とも Functions のみ） |
| `users/{uid}` | ログイン済みなら誰でも（表示名の解決に必要） | 本人のみ |
| `users/{uid}/notifications/**` | 本人のみ | 本人のみ（既読の更新）。作成は Functions のみ |
| `siteConfig/global` | ログイン済みなら誰でも | サイト管理者のみ |

- Storage のルールも同様に、`lists/{listId}/items/**` へのアクセスを**そのリストのメンバーに限定**する。

### 13.6 検索・並び替えの実現方法

- **並び替え**（6.4／連番・日付・登録者）は、`items` を読み込んだうえで**アプリ側で並べ替える**。登録者名での並び替えは uid ではなく解決後の表示名で行う。
- **検索**（6.4）は、**リストを開いた時点で項目を読み込んでおき、アプリのメモリ上で部分一致**させる。
  - Firestore は部分一致検索に対応していないため、この方式を採る。
  - 検索対象は、**曲名・アーティスト名。両方とも未記入の項目はファイル名**（6.4）。実装上は「曲名／アーティスト名／ファイル名のいずれかに含まれれば一致」とする。
  - 大文字小文字は区別しない。
  - **削除済み項目（`status == 'deleted'`）は検索の対象外**（6.4）。
- **制約**：項目数が数千件規模になると、リストを開いたときの読み込みが重くなる。その段階に達したら、ページングの導入や検索用キーワードの保持を改めて検討する。

### 13.7 Storage のファイル配置

```
lists/{listId}/items/{itemId}/{元のファイル名}
```

- パスにリスト ID を含めることで、Storage 側のセキュリティルールをリスト単位で書ける。
- 同一項目内でファイルを差し替えた場合は、**新しいファイルを別名で保存**し、旧ファイルは猶予期間後に削除する（13.4）。
