## 2026-08-04 — 仕様確定から初期構築まで

- 仕様書を v0.5 まで詰め、要件を確定（12 章 運用方針 → 13 章 データモデル → 14 章 画面）。
- Flutter 3.44.8 / Dart 3.12.2 でプロジェクトを作成。画面 20 件、Cloud Functions 22 件を実装。
- ローカルのエミュレータで動く状態にした。**Firebase プロジェクトを作らなくても試せる**ことを優先している。

### 決めたこと

| 決定 | 理由 |
| --- | --- |
| 権限・容量の判定を `domain/` に切り出す | Firebase に依存させなければ通信なしでテストできる。間違えると見えてはいけない情報が見える箇所なので、確実に検証したい |
| 同じ規則を Dart と TypeScript の両方に持つ | 画面の出し分けは Flutter 側、最終判断は Functions 側が行う。片方だけでは守れない |
| リストの一覧取得（`list`）をサイト管理者のみに制限 | ID 直接指定の取得を許すだけでは、未参加者が全リスト名を列挙できてしまう。「全リストの一覧を公開する画面は作らない」（5.3）に反する |
| 日本語フォントを同梱する | Flutter Web は既定でグリフを Google Fonts から取りに行く。社内ネットワークで遮断されていると日本語が出ない |

### つまずき

- **Storage のセキュリティルールは自動テストで検証しきれない。** `storage.rules` はメンバー判定に Firestore を参照するが、Storage エミュレータがこれに対応していない（本番では動く）。A/B の切り分けで確認済み。該当箇所は手動確認のチェックリストで補っている（SETUP.md）。
- **日本語の名前は五十音順に並ばない。** Dart の文字列比較は文字コード順のため（佐藤 < 田中 < 鈴木）。読み仮名を持たない限り解決できないため、制限として受け入れる。

## 2026-08-05 — Windows 対応

手元の環境が Windows だったため、開発環境まわりで連続して止まった。**どれもアプリの不具合ではなく、手順書とスクリプトが Windows を想定していなかった**もの。

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| `'.' は…認識されていません` | `.sh` は macOS / Linux 用 | `.cmd` を追加 |
| `'ebase' は…認識されていません`（文字化け） | cmd.exe はバッチファイルをコードページ（CP932）で読む。UTF-8 の日本語が別の文字として解釈され、**コマンド行そのものが壊れる** | 処理の本体を `.mjs` に移し、`.cmd` は英数字だけの入り口にした。Node は Windows でもコンソールへ直接書き込むためコードページに関係ない |
| `'flutterfire' は…認識されていません` | `dart pub global activate` の入れ先が PATH に入っていない | `dart pub global run` 経由で起動するスクリプトを用意（PATH を直す必要をなくした） |
| `version solving failed` | Flutter が古い（Dart 3.9.2） | `flutter upgrade`。診断がバージョンまで見るようにした |
| Java の診断が通ってしまう | 存在確認しかしていなかった。実際は Java 8 で、Firestore エミュレータは 11 以上が必要 | メジャーバージョンを判定。Java 8 以前は `1.8` 表記なので先頭が 1 のときは 2 つ目を見る |

**副産物として、`.sh` と `.cmd` に同じ処理を二重に書く状態を解消した。** 本体は `.mjs` 1 本で、両者はそれを呼ぶだけ。

### `127.0.0.1` が開けない

「エミュレータの管理画面は `http://127.0.0.1:4000`」という手順書の書き方が不正確だった。`127.0.0.1` は**ブラウザを開いているマシン自身**を指すため、エミュレータを起動したのと同じマシンでなければ開けない。WSL・Dev Container・SSH 先で起動した場合はポート転送が要る。手順書に明記した。

## 2026-08-05 — 検証環境への配信

初回のデプロイは 6 回失敗した。**すべて初回特有の事情**で、以後は起きない。

### 1. リージョンの不一致

```
A function in region asia-northeast1 cannot listen to a bucket in region us-east1
```

Storage のバケットが `us-east1` にあった（無料枠がそこにしかないため、意図して選んだもの）。トリガーは対象と同じリージョンでしか動かせず、**バケットのリージョンは作成後に変更できない**。

関数側を合わせられるよう、`FUNCTIONS_REGION` / `STORAGE_REGION` で上書きできるようにした。

**ただし最初の実装は効かなかった。** `process.env` で読んでいたが、Firebase CLI は「どの関数をどこに配置するか」を決める解析の段階で、子プロセスに `HOME` / `PATH` などごく一部の環境変数しか渡さない（firebase-tools の `spawnFunctionsProcess`）。`.env` の中身が渡るのはその後なので、解析時には常に未設定だった。「.env を読み込んだ」というログは出るため紛らわしい。

`defineString`（パラメータ）に変えて解決。パラメータは解析時には未解決の式として運ばれ、配置を決める直前に `.env` の値で解決される。

**さらに、`default` を指定しても入力を求められた。** `default` は「入力を求めるときの初期値」であって、入力を省く指定ではない。しかも答えた内容が `.env.<プロジェクト ID>` に**書き込まれる**（リポジトリのファイルが勝手に書き換わる）。共通の既定値を `functions/.env` に明示して解決。

### 2. 不要な複合インデックス

```
400, this index is not necessary, configure using single field index controls
```

`members` に `[joinedAt DESC, __name__ DESC]` を定義していたが、実際のクエリはドキュメント ID の一致だけで並び替えを伴わない。単一フィールドの索引は Firestore が自動で作るため、どのクエリにも使われていなかった。削除。

### 3. IAM ポリシーの変更に失敗

```
We failed to modify the IAM policy for the project.
```

必要な API（Cloud Scheduler / Eventarc / Cloud Run）の有効化と同時に走ったため。**API を有効化すると Google 側がサービスアカウントを追加する＝権限設定が書き換わる。** 書き換え前の内容をもとに更新をかけたため拒否された。API はすでに有効になっているので、**再実行で解消**。

（このとき Compute Engine の既定サービスアカウントが存在しない可能性を疑ったが、IAM の画面で存在を確認できたため外れだった。）

### 4. Cloud Build が 22 個中 21 個失敗

```
Build failed with status: FAILURE and message: An unexpected error occurred.
```

コンテナの置き場所（Artifact Registry のリポジトリ）が同じデプロイの中で作られるため、用意が整う前に始まったビルドが巻き添えで落ちた。**1 個だけ成功していた**ことが、コードではなく競合であることを示していた。置き場所ができたあとの再実行で全 22 個成功。

`--only=functions` を追加し、成功済みのルールや Web の配信を省いてやり直せるようにした。

### 5. 呼び出し可能関数が `internal` を返す

アプリから申請すると `internal` とだけ表示される。ログを見ると：

```
W submitlistrequest: The request was not authenticated.
Empty Authorization header value.
```

**関数のコードは 1 行も実行されていなかった。** 手前の Cloud Run が門前払いしていた。

`onCall` の関数は Cloud Run のレベルでは誰でも呼べる状態にしておく必要がある（Firebase のログイン情報は Google のアクセストークンではないため Cloud Run には読めない。利用者の確認は関数の中で行う）。Firebase CLI はこの設定を**新規作成時**に行うが、4 の Cloud Build 失敗で作成が途中終了し、その後の設定だけが飛ばされていた。再実行は更新扱いになるため直らない。

**削除してから配信し直す**ことで解決。

> **教訓：`internal` は Firebase が例外を包み隠した結果でしかない。** 推測を重ねるより `firebase functions:log` を見るほうが速い。実際、通知処理を疑って手を入れたが外れだった（その修正自体は残す価値があるので残している）。

### この過程で入れた予防策

| 対策 | 狙い |
| --- | --- |
| `deploy.mjs` の事前検査 | 接続設定が未生成のまま配信すると、**起動と同時にエラーで止まるアプリが公開される**。ログイン状態と併せて先に弾く |
| `--no-build` / `--only=` / `--debug` | 失敗のたびに 5 分の Web ビルドを繰り返さない。原因が見えないときは詳細ログを出す |
| `notifySafely` | 通知の失敗が本処理を巻き込まないようにする。トリガーでも例外を投げると再試行が延々と繰り返される |
| `grant-site-admin.js` の `--email` / `--list` | UID を調べるために Firebase コンソールを開く手順にしていたが、ブラウザが別の Google アカウントだと開けず、そこで詰む |
| 同スクリプトのエラー切り分け | すべての失敗を「ユーザーが見つかりません」と表示していた。鍵の指定漏れもプロジェクト名の誤りも同じ文言になり、原因にたどり着けなかった |

**「サイト管理者だから」という理由では送らないことにした。** 全リストの曲が
届くと、本当に見るべき通知（作成申請など）が埋もれる。サイト管理者も、
そのリストのメンバーであれば受け取る。リスト管理者を兼任できるように
してあるので（4.1）、見たいリストには入ればよい。

切り替えの仕組みは以前からあり、種別ごとの On/Off も設定画面に出ていた。
ただし**種別の名前しか書いていなかった**ため、「これは自分に届く通知なのか」が

### この環境では動かせなかったテスト（※ のちに誤りと判明）

**開発コンテナのプロキシの都合で、以下は手元では実行できていない。**
`firebase-tools` は `NO_PROXY` を見ずに**すべての通信をプロキシへ流す**ため、
`127.0.0.1` 宛の呼び出しまでプロキシに拒否される
（`403 denied by policy: no rule matched`）。影響を受けるのは 2 か所。

- Functions エミュレータの Firestore トリガー登録（→ `integration.mjs` が動かせない）
- Storage ルールの `firestore.exists()`（→ メンバー判定を伴う 3 件が失敗する）

> **【訂正】この「動かせない」は誤りだった。**
>
> 第 2 回のゼロベース監査で、観点 2 と観点 4 の担当が**実際に試して動かした**。
> プロキシの環境変数を外すだけで `rules-test` 105/105、統合テスト 47/47 が通る。
>
> 原因の分析（firebase-tools が NO_PROXY を見ない）は正しかったが、
> **「だから実行できない」は推測であって事実ではなかった。**
> この記述が、統合テストが手元で一度も通されないまま作業が進む原因になった。
>
> 第 1 回の申し送りは「**『〜できない』と書かれた箇所こそ、まず試すこと**」。
> **その記述を作ったのが自分だと、いちばん疑いにくい。**
> 詳細は [AUDIT-2026-08-06-2.md](AUDIT-2026-08-06-2.md) の 4.1。

なお `rules-test` の起動を `run.mjs` に移した。`JAVA_TOOL_OPTIONS` は
**空にするのでは足りず変数ごと消す**必要があり（値が空でも JVM が
`Picked up JAVA_TOOL_OPTIONS: ` を出力し、Storage のルールランタイムが落ちる）、
その書き方が OS で違うため。

その移し替えでもう 1 つ Windows 特有の落とし穴を踏んだ。

引用符が付かない。** `vitest run` が 2 つの引数として渡り

shell は外せない。**空白を含む引数があるときは、こちらで引用符まで含めた
1 本の文字列を組み立てて渡す。** 配列と shell を併用しないので、
Node の DEP0190 警告も出なくなる。

`scripts/` の他の .mjs も見直したが、空白を含む引数を渡している箇所は
無かったため、影響はこの 1 か所だけだった。

## 2026-08-06 — 意味の無い PASS が混ざっていた

統合テストを実行したところ、31 件中 24 件が FAIL した。原因は
`functions` の `npm run serve` に `--project demo-musiclist` が無かったこと。
`.firebaserc` の既定は検証環境の `music-storage-dev` なので、エミュレータは
実在のプロジェクト ID で立ち上がり、統合テストが呼ぶ
`http://127.0.0.1:5001/demo-musiclist/...` とは噛み合わなかった。

**問題は FAIL の数ではなく、その裏で 4 件が PASS していたこと。**

- 「追加した本人には届かない」
- 「参加していない人には届かない」
- 「サイト管理者でも参加していなければ届かない」

いずれも「通知が無いこと」を確かめる形なので、**そもそも何も起きて
いなければ必ず PASS になる**。土台が崩れているほど緑が増えるという、
いちばん質の悪い出方をしていた。緑は「確かめた」という意味でなければ
ならない。

対処は 3 つ。

| 対処 | ねらい |
| --- | --- |
| `npm run serve` に `--project demo-musiclist` を付ける | 原因そのものを断つ |
| テストの冒頭で相手を確かめて、違えば理由を出して止まる | 噛み合わないまま走らせない |
| クレーム付与とリスト作成に失敗したらその場で止まる | 土台が無い状態で先へ進ませない |

**「〜が無いこと」を確かめる項目は、前提が崩れると自動的に通る。**
そういう項目を書いたら、前提そのものを別に確かめること。

## 2026-08-06 — Windows でスクリプトが動かなかった一連の失敗

`rules-test` の起動スクリプトだけで 4 回続けて失敗した。すべて
**Linux では起きず Windows でだけ起きる**もので、こちらの環境では
気づけなかった。同種の失敗を繰り返さないために並べておく。

| 症状 | 原因 |
| --- | --- |
| `'JAVA_TOOL_OPTIONS' は認識されていません` | `VAR= コマンド` は POSIX シェルの書き方。cmd.exe では動かない |
| `Too many arguments` | `spawn` に引数の配列と `shell: true` を併用すると、引数は連結されるだけで引用符が付かない。`vitest run` が 2 つの引数になった |
| `'vitest' は認識されていません` | `npm install` を飛ばすと、エミュレータ起動後に落ちる。原因が見えにくい |
| `'firebase' は認識されていません` | **Windows の環境変数名は `Path` で `PATH` ではない。** `env.PATH = ...` と書くと項目が二重になり、中身が `node_modules/.bin` だけの方が採用された |
