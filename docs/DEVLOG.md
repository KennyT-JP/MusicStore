### 外し方 1：エラーが挙げた条件を、原因だと読んだ（**共有ドキュメント AP-72 の実物**）

## 2026-08-16（4） — Android のビルドを通し、Firebase へ登録した

依頼者が署名鍵を作り、そこから先を CLI で進めた。
**「依頼者しかできない」と見積もっていた作業のうち、2 件は CLI でできた。**

### 「CLI に無い」と言ったものが、あった

こちらは当初こう案内していた。

> SHA-1 の登録は Firebase コンソールの操作です。**スクリプトはやってくれません。**

**誤りだった。** `firebase apps:android:sha:create <appId> <sha>` がある。
`apps:create` / `apps:sdkconfig` も揃っており、**登録から設定ファイルの取得まで
全部 CLI で完結した。**

さらに「Authentication の Google 有効化だけは CLI に無い」と言ったが、
**そもそも既に有効だった**（Web の Google ログインが本番で動いている以上、
当然のことだった）。生成された `google-services.json` に `oauth_client` が
2 件入っていることで確認できた。

**Session Concierge が踏んだ落とし穴**——「Google を有効化する**前**に
ダウンロードしたファイルは `oauth_client` が 0 件」——は、この確認で回避した。

### AGP 9 では、このアプリはビルドできない

**初回の release ビルドが落ちた。**

```
GeneratedPluginRegistrant.java:39: シンボルを見つけられません
  new com.mr.flutter.plugin.filepicker.FilePickerPlugin()
```

原因は `file_picker` の `android/build.gradle` にあった。

```groovy
def isAgp9OrAbove = com.android.Version.ANDROID_GRADLE_PLUGIN_VERSION
    .tokenize('.')[0].toInteger() >= 9
if (!isAgp9OrAbove) {
    apply plugin: 'org.jetbrains.kotlin.android'
}
```

**AGP 9 では Kotlin プラグインを適用しない。** 実装は全部 Kotlin なので、
**1 行もコンパイルされずクラスが生成されない。**

`android.builtInKotlin=true` にすると、今度は `audio_session`（`just_audio` の
依存）が落ちる——

```
The 'org.jetbrains.kotlin.android' plugin is no longer required for Kotlin support since AGP 9.0.
```

**このフラグはプロジェクト全体に効く 1 つのスイッチで、どちらに倒しても
片方が壊れる。** 生態系が AGP 9 を境に割れている。

**Session Concierge と同じ構成に下げた**（AGP 8.11.1 / Kotlin 2.2.20 /
Gradle 8.14）。**推測ではなく、Play へ出荷している実物に合わせた。**

> **次に触る人へ。** これは「古い版に留めている」のではなく、
> **上げると必ず壊れる**状態です。`file_picker` と `audio_session` の**両方**が
> AGP 9 に揃うまで上げられません。`test/domain/android_platform_test.dart` が
> 版を見張っています。

### 27 分を無駄にしないための確かめ方

版を下げたあと、**ビルドを回す前に設定段階だけで確かめた。**

```
./gradlew :file_picker:tasks --all -q | grep compile.*Kotlin
```

`compileReleaseKotlin` が現れるかどうかで、**Kotlin が適用されたかが
数秒で分かる。** 落ちた原因がまさに「Kotlin のコンパイル作業が存在しない」
ことだったので、そこだけを見れば足りた。

**フルビルドは 27 分かかる。** 直したつもりで回して落ちると、
1 回の試行が 27 分になる。

### 鍵・署名・登録が繋がっていることの確かめ方

`keytool -printcert -jarfile` は「**署名付き JAR ファイルではありません**」と
返した。**v1（JAR）署名しか読めない**ためで、最近の Android は v2 で署名する。
`apksigner verify --print-certs` に切り替えて確認した。

| 見たもの | 一致した先 |
| --- | --- |
| 証明書の DN | **`CN=Android Debug` ではない** ＝ `key.properties` が効いている |
| SHA-1 | Firebase に登録した値 |
| SHA-256 | `web/.well-known/assetlinks.json` に入れた値 |

**道具が「読めない」と言ったとき、それを「無い」と読まないこと**（AP-41 の形）。

## 2026-08-16（3） — ダウンロード機能を実装した

サーバー・純ロジック・データ層・画面の 4 層。**認証のモバイル対応だけが、
依頼者の作業（署名鍵・Firebase 登録）待ちで止まっている。**

### 見張りが、実装の分割の仕方を否定した

最初、**「純ロジックを先に固めれば、実機が無くてもテストで確かめられる」**
と考えて `lib/domain/` だけを先に実装した。結果、
`test/domain/no_dead_code_test.dart` が赤になった。

> 判定ロジックを `lib/domain/` に切り出してテストを厚く書いたのに、
> **画面やリポジトリはそれを呼ばず、同じ判定を直接書いていた**。
> テストは緑のまま、本番では別のコードが動いている状態が続いた（監査 第2回）。

**この見張りには除外の仕組みが無い。** 過去 2 回の監査で同じ指摘を受けた結果、
「呼ぶ人のいない判定ロジックを置いてはいけない」という規律として固めてある。

**黙らせずに、繋ぐところまでを 1 つの塊として扱い直した。** 分割の単位が
間違っていたのであって、見張りが厳しすぎたのではない。

### 仕様の穴を 2 つ塞いだ

**① 任意のドキュメントの存在を試せる入口になっていた。**

仕様 5.1 の骨格は、`listIds` の要素が文字列であることしか見ていなかった。
`['abc/items/xyz']` を渡すと `lists/{listId}/members/{uid}` が
**6 セグメントの別ドキュメント**を指す。パス区切り・`.` `..`・`__…__`・
空・200 文字超を弾き、重複も上限を数えたあとでまとめるようにした
（**重複での水増しを通さないため**）。

**② 物理削除の経路が拾えていなかった。**

`deleteSiteUser` は項目を `doc.ref.delete()` で**物理削除**する。
消えたドキュメントは `where('updatedAt', isGreaterThan:)` に**一生上がってこない**。
取得を 2 本立て（更新クエリ＋存在確認）にした。
**存在確認を省くと、変わっていない曲まで「消えた」と読まれて全曲消える。**

### 「例外にしない」を、本文を読んで見張った

`verifyDownloadAccess` は、プレミアムが切れていても**例外を投げない**。

> 例外にすると**通信失敗と区別が付かず**、その判定結果が「端末のファイル削除」
> なので、**電波の悪い場所で 1 回失敗しただけで全曲消える。**

判定のテストだけでは、あとから `throw` を書き足されても緑のままになる。
**ソースそのものを読む見張りを 4 本**置き、実際に `premiumRequired` を投げる
実装に書き換えて 3 件が落ちることを確認した。加えて**純関数の引数から
`ListAccess` も `isSiteAdmin` も外した**——例外を足そうにも材料が無い。

### 「数を数える見張り」で 2 回すり抜けた

- **iOS**: `IPHONEOS_DEPLOYMENT_TARGET` を「全部 15.0 以上」で見張ると、
  **0 件でも成り立つ。** 件数を数えてから中身を見る形にした
- **Swift の受け口**: `FlutterError` の総数で「握りつぶしていない」を見張ったが、
  この受け口には 4 か所あるので、**catch を 1 つ空にしても閾値を超えたまま**だった。
  catch ブロックごとに中身を見る形に直した

**どちらも、壊して赤を確かめる工程で見つかった。** 書いた本人が「効いていない
見張り」に気づける唯一の方法がこれだった。

### autoDispose で、コメントが黙って 0 件になっていた

`ref.read(itemCommentsProvider(...).future)` は、**その曲のコメントを誰も
購読していないと値が届く前に破棄される**（`The provider … was disposed during
loading state`）。項目詳細からは効くが、**一覧からの単曲と一括が該当**した。

**別の担当が見つけ、作った本人が再現して直した。** 伝聞のまま直させず、
「まず自分で再現し、再現しなければその旨を報告せよ」と伝えている。

### Web からの削除は、引き金を用意して引かなかった

`kWebAudioDownloadRemoved = false`。コードは全部書き、**両方の状態を
テストで固定**したうえで、引かずに置いた。引き金は
**「Google Play の一般公開」で、日付ではない**（依頼者の判断・期限は切らない）。

**それまで、Web から誰でも無料で音源を落とせる状態が続く。**
承知のうえの判断で、不具合ではない（[BACKLOG.md](BACKLOG.md) の「高」に起票）。

## 2026-08-16（2） — モバイル化の土台を実装した

### 前提が 1 つ崩れた

依頼者から「**Session Concierge でアンドロイドも iOS アプリも作っている**」と
教わり、`C:\Codes\SessionConcierge` を調べた。

**Mac が要るという前提が崩れた。** あちらは **Windows だけで App Store まで
出している**（Codemagic の `mac_mini_m2`）。初回成功時のビルドは 8 分 28 秒。

あわせて、**こちらが「危ない」と書いた 2 点が事実に反していた**ことも分かった。

| 取り下げたもの | 根拠 |
| --- | --- |
| 「`INTERNET` が `main/` に無いので release だけ通信できない」 | あちらも書いていない。**それで出て動いている** |
| 「`<queries>` が無いと Android 11+ で `url_launcher` が動かない」 | あちらも `PROCESS_TEXT` だけで 3 箇所開けている |

**どちらも「そう言われている」を確かめずに書いた。** 同じ構成で動いている実物が

### 3 回目も同じ間違い方をした

実装中、`firebase.json` の `ignore` に `**/.*` があるのを見て
「**`.well-known` はドット始まりだから配信されない**」と担当に警告した。

**これも誤りだった。** 担当は firebase-tools 15.24.0 の `listFiles.js`（配信が
実際に呼ぶ関数）へ、この `firebase.json` の `ignore` をそのまま渡して数えた。

```
total files = 105
well-known  = [".well-known/assetlinks.json", ".well-known/apple-app-site-association"]
```

glob の `ignore` は、**パターンが `/**` で終わらない限り、一致した
ディレクトリの中身までは除外しない。** 担当は `ignore` を変更せず、
**この前提をテストで固定**した（`.well-known/**` を足すと赤になる）。

**1 日に 3 回、同じ形で間違えた。** 一般論から「危ない」を書き、実物を確かめない。
共有ドキュメント AP-72 の「**『無い』と言われたら、まず対象が存在するかを数える**」は、
自分が言う側でも同じだった。

### 見つかっていた不具合

**`buildShareUrl` がモバイルで落ちる。** `Uri.base` はネイティブで `file:` 形式に
なり、`.origin` を読むと `StateError` が投げられる。**モバイルでは招待リンクを
1 本も作れない。**

**同じファイルのコメントが、すでにこの事実を書いていた**——ただし
「テストでは」という文脈でだけ。**本番のモバイルでも同じことが起きる**という
認識に至っていなかった。

### 見張りを 41 本足し、全部壊して赤を確かめた

4 人の担当が、合計 **37 パターン**で「壊すと赤・戻すと緑」を実測した。

**2 つは AP-54 の実証だった。** 今回のファイルは説明コメントが本文より長く、
「なぜ書かないか」を書いてある。素の文字列検索だと**説明文の中の

## 2026-08-12 — 「本人だけが読める」と書いた項目が、全員に見えていた

プレミアムの実装中に見つかった。**4 回の監査が一度も挙げなかった露出**である。

### どうやって見つかったか

[PREMIUM-DESIGN.md](PREMIUM-DESIGN.md) に「プレミアムの状態は書き込みを
禁じ、**読めるのは本人だけ**」と書いていた。ルール側の担当が
**「その保証を確かめるテストは書けない。書けば嘘になる」**と報告してきた。

**Firestore のルールに、項目単位の読み取り制限は無い。**
読み取りの許可はドキュメント単位でしか書けない。そして `users/{uid}` は
**表示名を引くためにログイン済みなら誰でも取得できる**設計だった
（コメントや曲の投稿者名の解決に要る）。

つまり、そのドキュメントに入っている項目は**全部見えている**。
中身を並べたら、`premium` と `storage` の前に**メールアドレス**があった。
プレミアムを足したから漏れたのではなく、**最初から漏れていた**。

**保証を願望のまま書いた文書は、矛盾していても動く。**
だから誰も気づかない。**気づいたのは「テストが書けない」と言われたときだけ**
だった（共有ドキュメントの AP-58 に一般化して追記した）。

### 直し方

**`users/{uid}/private/state` へ移した。** 移した項目は 5 つ。

| 項目 | 移した理由 |
| --- | --- |
| `email` | 他の利用者に見せる理由が無い |
| `premium` | 誰が有料かは他人に関係ない |
| `storage` | 使用量は他人に関係ない |
| `locale` `notificationSettings` | **同居させたままにすると、次に同じことが起きる** |

最後の 2 つを一緒に運んだのは、[AUDIT-CHECKLIST.md](AUDIT-CHECKLIST.md)
「**片側だけ塞ぐと、もう片側で同じことが起きる**」に従った判断である。
メールだけ移して他を残せば、残した側が育つ。

親に残したのは**表示名・写真・退会したか**の 3 つだけ。
「このドキュメントを読めるのは誰か」を 1 行で言えるようになった。

### 自分の指示が間違っていた

ルール側の担当に「**私的な項目は書き込み禁止**」と指示した。
**`locale` と `notificationSettings` は利用者が変える項目**なので、
そのまま入れたら**設定画面の保存が丸ごと拒否される**（監査 3 回目で
同じ形を踏んでいる。AUDIT-CHECKLIST 観点 1・6「直したことが新しい欠陥を
持ち込んでいないか」）。

**担当が「その項目は利用者が変えるのでは」と指摘して、配信前に気づいた。**
指示を出した側は、自分の指示の矛盾をいちばん見つけにくい。

直した形はこうなった。

```
match /users/{userId}/private/{docId} {
  allow read:   isSignedIn() && uid() == userId
  allow create: ... && docId == 'state'
                && !request.resource.data.keys().hasAny(serverOwnedUserFields())
  allow update: ... && docId == 'state'
                && !request.resource.data.diff(resource.data)
                     .affectedKeys().hasAny(serverOwnedUserFields())
  allow delete: false
}
```

- **禁止は項目名の列挙で、許可は所有の確認で表す。** 本人が変える項目と
  サーバー専用の項目が同居するので、この形しかない
- **`create` にも同じ禁止を課す。** update だけ塞ぐと、**作るときに混ぜられる**
- **`delete` は禁止。** 消して作り直せると、**サーバー専用の項目を捨てられる**
- **`docId` は `state` の 1 つに限る。** 任意の ID を作らせない

### 移行の順序

`scripts/backfill.mjs` に 1 つ足した。**手順の中の順序が効いた。**

**私的な項目を移す処理（6）を、容量の集計（5）より先に実行する。**
集計は移した先を読むので、逆にすると空を読む。番号の順ではなく
**依存の順**で走らせている。

配信と移行の順序も決めた：**影響を数える → 配信 → 移行**。

## 2026-08-09 — テストを速くした。「遅い」の正体は測るまで分からなかった

外部の調査（テスト所要時間の調査 2026-08-09）の提案 1〜4 を入れ、5〜6 を
実測で調べた。検証全体（scripts/check.mjs）は **7〜8 分 → 約 3 分**になった。

### 入れたもの

- **ルールテストの種まきを 1 往復に**（batch 化）と、**汚していなければ
  まき直さない**仕組み（74 秒 → 43 秒）。テストは `allow` / `deny` /
  `mutateAsAdmin` を通す約束にし、破ると discipline.test.js が落とす。
- **ルールテスト専用のエミュレータ設定**（firebase.rules-test.json、
  別ポート）。これで統合テストと同時に走れて、check.mjs は 5 本全部並列。
- **固定の待ち時間 2 か所を waitUntil に**（統合テスト）。

調査の原案は「エミュレータを 1 つに相乗り」だったが、**採らなかった**。
ルールテストの種まきが functions のトリガーを何百回も撃ってしまい、
互いの結果を汚す。分けてポートをずらすほうが単純で安全。

### 「遅い」の正体（提案 5 の調査）

統合テストに時間の内訳を仕込んで測った。単独実行 102 秒のうち、
**96 秒が関数呼び出しの往復の中**にあった。ところがエミュレータのログで
関数の実行時間を合計すると **17 秒**しかない。差はどこか。

呼び出し 51 回の分布を取ると、**関数の数と同じ 19 回だけがきれいに
約 5 秒**で、残り 29 回は 0.3 秒未満だった。つまり**各関数の最初の
1 回だけ、エミュレータがワーカー（node プロセス）を立ち上げる分の
約 5 秒を払っている**。直列に払うと 95 秒。

対策として、テストの頭で全関数へトークン無しの呼び出しを**同時に**投げ、
立ち上げを重ねて払うようにした（102 秒 → 83 秒）。同時でも 32 秒かかる
（プロセス起動が CPU を食い合う）ので、消えはしない。残りの内訳は
エミュレータの起動 + functions のビルドで、テストの外側にある。

**教訓：遅さの調査は、まず「どこで」を測る。** 外部調査は「1 呼び出し
平均 3.3 秒」を関数の遅さと読んでいたが、実体は初回だけの起動代だった。
平均は分布を隠す。

### 並列と直列（提案 6 の調査）

check.mjs のコメントに「直列だと遅い」と書いてあったが、実測が無かった。
測った：**全部並列 = 189 秒**、単独実行の合計（直列の見積もり）≈ 300 秒、
「統合だけ後回し」の 2 段構え ≈ 230 秒。全部並列が最速。取り合いで
統合テストは伸びる（単独なら約 135 秒 → 並列中 189 秒）が、重ねて
隠れる時間のほうが大きい。

数字は check.mjs のコメントにも残した。**次に構成を変えるときも、
言葉ではなく測って比べること。**

入れたものは仕様書の更新履歴（v1.3〜v1.8）にある。ここには**つまずいた点**だけを残す。

### 失敗が呼び出し元に伝わっていなかった

曲の追加でファイルを選ばずに保存すると、一瞬エラーが出たあと一覧へ戻り、
**入力した内容ごと失われて**いた。原因は 2 つ重なっていた。

```dart
await _saveNew(...);   // 入力が足りないと、例外ではなく普通に戻る
_close();              // なので必ず閉じる
```

**戻り値も例外も無い関数は、成功と失敗を区別できない。**
型の上では正しく、解析でもテストでも捕まらない。しかも
**押せてはいけないボタンが押せた**ことと重なって、あの出方になった。

成否を返り値で受け取り、成功したときだけ閉じる形にした。
必須が揃うまで押せないようにもした。**押す前に分かれば、そもそも通らない。**

### 時間制限を 1 か所だけ直して、もう 1 か所で落ちた

検証を並列にした副作用で、統合テストの呼び出しが時間切れになり配信が止まった。
上限を延ばして再実行したら、**今度はルールテストの起動（20 秒）で落ちた。**

1 回目の対処のときに「時間制限がほかにも無いか」を数えていれば、
2 回目は起きなかった。**この文書の観点 4 に自分で書いてあることをやらなかった**
（AUDIT-CHECKLIST「片側だけ塞ぐと、もう片側で同じことが起きる」）。

このとき機械では依頼者の動画編集ソフトが CPU を占めており、
`dart analyze` が 72 秒 → 229 秒、統合テストが 280 秒 → 1111 秒に伸びていた。
**どちらもコードは正しく、ただ遅かっただけ**である。
時間制限は**速さの基準ではなく、止まったまま戻らない事故の歯止め**として置き直した。

### 先読みの種類が合っておらず、転送量を倍にしていた

表示を速くするつもりで Firebase SDK を先読みしたが、`as="script"`
（クラシックスクリプト）で指定していた。firebase_core は SDK を
**動的な `import()`（モジュール）**で読み込むので種類が合わず、
**先読みした分が使われないまま、同じものをもう一度取りに行っていた。**

ブラウザは警告で知らせていたが、**依頼者に指摘されるまで気づかなかった。**
`modulepreload` に直した。**先読みを足したら、開発者ツールで警告が
出ていないか見ること。**

### コミットが main に直接入った（2 回）

| --- | --- | --- |

## 2026-08-05 — 検証環境への配信

初回のデプロイは 6 回失敗した。**すべて初回特有の事情**で、以後は起きない。

### 1. リージョンの不一致

```
A function in region asia-northeast1 cannot listen to a bucket in region us-east1
```

Storage のバケットが `us-east1` にあった（無料枠がそこにしかないため、意図して選んだもの）。トリガーは対象と同じリージョンでしか動かせず、**バケットのリージョンは作成後に変更できない**。

関数側を合わせられるよう、`FUNCTIONS_REGION` / `STORAGE_REGION` で上書きできるようにした。

**ただし最初の実装は効かなかった。** `process.env` で読んでいたが、Firebase CLI は「どの関数をどこに配置するか」を決める解析の段階で、子プロセスに `HOME` / `PATH` などごく一部の環境変数しか渡さない（firebase-tools の `spawnFunctionsProcess`）。`.env` の中身が渡るのはその後なので、解析時には常に未設定だった。「.env を読み込んだ」というログは出るため紛らわしい。

`defineString`（パラメータ）に変えて解決。パラメータは解析時には未解決の式として運ばれ、配置を決める直前に `.env` の値で解決される。

**さらに、`default` を指定しても入力を求められた。** `default` は「入力を求めるときの初期値」であって、入力を省く指定ではない。しかも答えた内容が `.env.<プロジェクト ID>` に**書き込まれる**（リポジトリのファイルが勝手に書き換わる）。共通の既定値を `functions/.env` に明示して解決。

### 2. 不要な複合インデックス

```
400, this index is not necessary, configure using single field index controls
```

`members` に `[joinedAt DESC, __name__ DESC]` を定義していたが、実際のクエリはドキュメント ID の一致だけで並び替えを伴わない。単一フィールドの索引は Firestore が自動で作るため、どのクエリにも使われていなかった。削除。

### 3. IAM ポリシーの変更に失敗

```
We failed to modify the IAM policy for the project.
```

必要な API（Cloud Scheduler / Eventarc / Cloud Run）の有効化と同時に走ったため。**API を有効化すると Google 側がサービスアカウントを追加する＝権限設定が書き換わる。** 書き換え前の内容をもとに更新をかけたため拒否された。API はすでに有効になっているので、**再実行で解消**。

（このとき Compute Engine の既定サービスアカウントが存在しない可能性を疑ったが、IAM の画面で存在を確認できたため外れだった。）

### 4. Cloud Build が 22 個中 21 個失敗

```
Build failed with status: FAILURE and message: An unexpected error occurred.
```

コンテナの置き場所（Artifact Registry のリポジトリ）が同じデプロイの中で作られるため、用意が整う前に始まったビルドが巻き添えで落ちた。**1 個だけ成功していた**ことが、コードではなく競合であることを示していた。置き場所ができたあとの再実行で全 22 個成功。

`--only=functions` を追加し、成功済みのルールや Web の配信を省いてやり直せるようにした。

### 5. 呼び出し可能関数が `internal` を返す

アプリから申請すると `internal` とだけ表示される。ログを見ると：

```
W submitlistrequest: The request was not authenticated.
Empty Authorization header value.
```

**関数のコードは 1 行も実行されていなかった。** 手前の Cloud Run が門前払いしていた。

`onCall` の関数は Cloud Run のレベルでは誰でも呼べる状態にしておく必要がある（Firebase のログイン情報は Google のアクセストークンではないため Cloud Run には読めない。利用者の確認は関数の中で行う）。Firebase CLI はこの設定を**新規作成時**に行うが、4 の Cloud Build 失敗で作成が途中終了し、その後の設定だけが飛ばされていた。再実行は更新扱いになるため直らない。

**削除してから配信し直す**ことで解決。

> **教訓：`internal` は Firebase が例外を包み隠した結果でしかない。** 推測を重ねるより `firebase functions:log` を見るほうが速い。実際、通知処理を疑って手を入れたが外れだった（その修正自体は残す価値があるので残している）。

### この過程で入れた予防策

| 対策 | 狙い |
| --- | --- |
| `deploy.mjs` の事前検査 | 接続設定が未生成のまま配信すると、**起動と同時にエラーで止まるアプリが公開される**。ログイン状態と併せて先に弾く |
| `--no-build` / `--only=` / `--debug` | 失敗のたびに 5 分の Web ビルドを繰り返さない。原因が見えないときは詳細ログを出す |
| `notifySafely` | 通知の失敗が本処理を巻き込まないようにする。トリガーでも例外を投げると再試行が延々と繰り返される |
| `grant-site-admin.js` の `--email` / `--list` | UID を調べるために Firebase コンソールを開く手順にしていたが、ブラウザが別の Google アカウントだと開けず、そこで詰む |
| 同スクリプトのエラー切り分け | すべての失敗を「ユーザーが見つかりません」と表示していた。鍵の指定漏れもプロジェクト名の誤りも同じ文言になり、原因にたどり着けなかった |

## 2026-08-07 — 招待 URL を共有リンクに作り直した

依頼は 4 点。

1. リストもしくは曲から、**単純にリンクで**送れるようにする
2. 受け取った人が、**登録するか登録せずに閲覧するだけか**を決める
3. リンク先のページに**その旨を書く**
4. リンクは**無期限**で、**複数人が何度でも**使える

### 「登録しないで閲覧」の範囲だけ、先に確かめた

ここだけは前提が変わるので、実装前に依頼者に確認した。
いまはリストの曲を見るのに「ログイン済み＋メール確認済み＋メンバー」
が必要で、これを崩すとセキュリティの土台が変わる。

| 選択肢 | 判断 |
| --- | --- |
| ログインは必要（参加はしない） | **これを選んだ** |
| ログインも不要（リンクを知る全員が見られる） | 選ばれず |
| 曲名だけ見せて、音は登録者のみ | 選ばれず |

**推測で進めなかったのが正しかった。** 2 番目を選んでいたら、
無期限・何度でも使えるリンクと組み合わさって、そのリストは
実質公開になっていた。取り返しがつかない種類の違いだった。

### 判断から消えたもの

以前の招待は「一度きり・24 時間」だったので、受諾の判断に
4 つの理由があった。無期限・何度でも・複数人にしたことで、
**残ったのは取り消しだけ**になった。

| 以前 | いま |
| --- | --- |
| 期限切れ | 無い |
| 使用済み | 無い |
| 取り消し済み | **残す** |
| すでにメンバー | **拒否しない** |

「すでにメンバー」を拒否しないのが要点である。何度でも使えるリンクでは
同じ人が二度開くことが普通に起きる。以前は一度きりだったので
「使用済みです」と伝える意味があったが、いまはそのままリストを開けばよい。
エラーにすると、参加済みの人がリンクから入れなくなる。

### 期限を無くすと、取り消しの重みが増す

**期限切れが事実上の歯止めになっていた**ことに、途中で気づいた。
無期限にした以上、一度配ったリンクを止める手段は取り消ししか無い。

そこで次のようにした。

- 発行時の案内を「期限は 24 時間」から
  **「期限は無い。何人でも何度でも使える。止めるときは取り消す」**に変えた
- 取り消しの導線は既にあったので、そのまま活かした
- **取り消し済みと「リンクが違う」を別の文言にした。**
  受け取った人が次に取る行動が違う
  （取り消し → 新しいリンクを依頼／見つからない → URL を確かめる）
- ID を 256 ビット相当のままにした。
  **期限が無いぶん、推測されにくさがそのまま守りになる**

### 閲覧だけの人を、メンバーと混ぜない

`lists/{listId}/viewers/{uid}` を新設した。メンバーとは別に持つ。

- メンバー一覧にも `memberCount` にも通知の宛先にも入らない
- **書けるのは Cloud Functions だけ。** クライアントから書けると、
  リンクを持っていない人が自分で閲覧権を作れてしまう
- 読めるのは本人とリスト管理者。誰が見ているかは、リストを預かる人に分かる

**対照実験で確かめた。** viewers への書き込みをわざと許すルールに
差し替えると、「自分で閲覧権を作れない」が失敗する。

### サイト設定から「招待 URL の有効期限」を消した

期限を持たなくなったので、この設定は何も効かない。
**効かない設定を画面に残すと、触った人が「効いている」と思う。**

## 2026-08-08（続き） — リンクから役割を取り除いた

依頼者の言葉。

> URLは単なるリスト、曲へのリンクでしかなく、それ以上の意味を
> 持たせてはいけません

### 何をやってしまったか

同じ日の午前に「発行する側に役割を選ばせるのをやめる」と直した。
そのとき、**選ばせるのをやめた代わりに `JOIN_ROLE = 'superUser'` を
置き、リンクの側に役割を書き込んでいた。**

依頼者が消したかったのは「選ぶ操作」ではなく、
**リンクが役割を持っていること**だった。

### なぜ持たせてはいけないのか

URL は転送される。メールでも、チャットでも、そのまま貼られる。

リンクに「参加したら Super User」と書いてあると、
**その URL を渡すこと自体が書き込み権限を配ること**になる。
渡した相手が別の人へ回せば、そのまま広がる。
配った人は、誰が書けるようになったかを知らない。

期限も回数の上限も無くしたリンクなので、この性質はいっそう重い。

### どう直したか

| 前 | いま |
| --- | --- |
| `shareLinks/{linkId}` に `role` を書く | **欄そのものを持たない** |
| 参加時に `data.role` を読んで付ける | リンクを読まない |
| `JOIN_ROLE = 'superUser'` | `INITIAL_JOIN_ROLE = 'readOnly'` |
| `via: 'invite'` | `via: 'shareLink'` |

**一番低い役割で入る。** こうするとリンクが与える範囲は
「参加せずに見る」と同じになり、URL は入口以上のものにならない。
書けるようにするかどうかは、リスト管理者が後から決める（5.4）。

`ShareLinkSnapshot` からも `role` を外した。**型に残っていると、
また誰かが読む。** 代わりに「ここに役割は無い」と書いた。

### 統合テストで見るようにしたこと

役割が「効かない」ことだけを見ても足りない。
**リンクのドキュメントを実際に読んで、`role` の欄が無いことを見る。**

- 発行したリンクは役割を持たない
- 役割を渡しても、リンクには載らない
- 参加すると Read Only で入る
- 役割を渡して作ったリンクでも、Read Only より上にならない

`role` が無いことを確かめる 2 件には、**先に `listId` が読めることを
確かめる 1 件を添えた。** 読めていないときも `role` は
`undefined` になるので、そのままでは何も確かめずに緑になる。

### 3 回言われて、ようやく直った

同じ依頼を 3 回、言い方を変えて言われている。

| 回 | 依頼者の言葉 | こちらの受け取り方 |
| --- | --- | --- |
| 1 | 「ユーザーの種類でわけないでください」 | 発行画面の選択肢を消した |
| 2 | 「URLを受け取った人自身が選択する」 | 画面はもうあります、と答えた |
| 3 | 「URLは単なるリンクでしかない」 | **リンクから役割を取り除いた** |

1 回目で「選択肢を消す」までしか読まなかったのが始まりである。
消した判断を別の場所へ移せば済むと考えたが、依頼者が問題にしていたのは
**判断がどこにあるか**ではなく、**リンクが何を持っているか**だった。

**選択肢を消すときは、その判断がどこへ行ったかを見ること。**
消えていないなら、消したことにはならない。

## 2026-08-16 — **「最初の Android リリースビルド成功」は成立していなかった**

**42.4 MB の `app-release.apk`（`flutter clean` の前に作ったもの）には、
アプリが 1 行も入っていなかった。** ビルドは通り、署名も付き、サイズも
それらしく、**端末に入れて起動すると真っ白のまま何も出ない**。
`flutter clean` 後に作り直した 61.0 MB のほうが正しい成果物。

**この APK を「最初のリリースビルド成功」として数えないこと。**

### 何が起きていたか

APK を展開して中身を突き合わせた。**違うのは 551 件中 7 件だけで、
`libflutter.so` はバイト単位で同一。** つまり梱包や strip の差ではなく、
**Dart の AOT スナップショット（`libapp.so`）だけが別物**だった。

| | 42.4 MB 版 | 61.0 MB 版 |
| --- | --- | --- |
| `libapp.so`（arm64） | 1,966,992 B | 8,192,912 B |
| **入っているアプリのファイル** | **6 本** | **87 本** |
| アプリのクラス（全 229 件中） | **2 件** | 226 件 |
| `firebase_core` / `firestore` / `auth` / `riverpod` / `go_router` | **無し** | 有り |
| `runApp` / `MaterialApp` / `ProviderScope` / `MusicListApp` | **無し** | 有り |
| Flutter 本体のライブラリ | 145 本 | 422 本 |

**42.4 MB 版に入っていた 6 本は `lib/main.dart` と `lib/env/` の 5 本だけ。**
`main()` は 32 行目の `DefaultFirebaseOptions.assertConfigured()` までで
途切れていて、**34 行目の `Firebase.initializeApp` も 52 行目の `runApp` も
入っていない。** ウィジェットツリーを作る処理がまるごと無いので、
**起動しても画面は出ない。**

### 難読化や梱包の差ではないことの確認

- **難読化ではない。** `RenderBox` `StatefulWidget` `BuildContext` といった
  **Flutter 本体の名前は 42.4 MB 版にも残っている**。加えて、難読化は
  **文字列リテラルを消さない**が、`プレミアム`（UTF-16LE）は
  61.0 MB 版に 12 件、42.4 MB 版に **0 件**
- **分割 AOT でもデバッグ／プロファイルでもない。** 追加の `libapp-*.so` は無く、
  ファイル件数は同じ 551 件。`kernel_blob.bin` はどちらにも無い
- **フレーバーの差でもない。** 差分は `libapp.so` 3 つと
  `classes.dex` / `resources.arsc` / `baseline.prof` /
  `MaterialIcons-Regular.otf` のみ

### **原因として潰した仮説**（同じ調査を繰り返さないために）

- **接続設定の `REPLACE_ME` は無関係。** リポジトリ状態（プレースホルダーのまま）で
  この commit を一から AOT し直したところ、**87 本すべて入った 11.96 MB
  （strip 前）**が出た。`AppEnvironment.current` が `static final` で
  定数畳み込みされないため、未設定でもアプリは削られない
- **古い commit のコードでもない。** **全ブランチの `lib/main.dart` 全リビジョンが
  例外なく `app.dart` を import して `runApp` を呼んでいる。**
  6 本しか入らない状態は、**リポジトリのどの履歴にも存在しない**

つまり **AOT が食べたカーネル（`.dill`）が、ソースのどの状態とも一致しない
「途中まで」のものだった。** `.dart_tool` に残っていた中途半端な生成物を
使ってしまったと考えるのが自然だが、**引き金までは特定できていない。**
`flutter clean` で直っている。

### ここから引く教訓

**ビルドが通ったこととアプリが入っていることは別。** 今回は
「署名付き APK が出た」「サイズも 42 MB ある」で成功と判断していた。
**`libapp.so` のサイズを見ていれば 5 秒で気づけた。**

**リリース APK を作ったら、`libapp.so` の中身を必ず確かめる。**

```
unzip -p <APK> lib/arm64-v8a/libapp.so | wc -c
```

**この数字が 5 MB を大きく下回ったら、アプリは入っていない。**
中身で確かめるならこちら（0 件なら失敗）。

```
unzip -p <APK> lib/arm64-v8a/libapp.so | grep -ac MusicListApp
```

**`scripts/check.mjs` の対象外**（あちらは APK を作らない）なので、
**当面は手で見る。** 自動化は `docs/BACKLOG.md` に積んだ。
