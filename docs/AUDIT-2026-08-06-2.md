## 3. 主な発見と対処

### 重大

| # | 内容 | 対処 |
| --- | --- | --- |
| **A1** | **メール＋パスワードの新規登録が失敗し、確認メールが送られない。** 登録処理は「読んで、無ければ作る」順だが、`users` の get がメール確認済みを要求していた。登録直後は当然未確認なので拒否され、例外で止まって `sendEmailVerification` に到達しない。利用者には「エラーが発生しました」とだけ出る。**第 1 回の S3 対応で持ち込み、検証環境に配信済みだった** | 自分の行だけは未確認でも読めるようにした。ルールテスト 3 件（作れる／読める を並べる） |
| **A2** | **`assignListAdmin` がメンバーに `uid` を書かない。** 横断クエリに載らないため、指名されたリスト管理者はホームにリストが出ず、リスト詳細では参加申請画面へ振り替えられ、退会してもメンバーから外れない。仕様 5.6 が機能しない | `uid` を書く。既存メンバーの昇格時にも入れ直す |
| **A3** | **`purgeOrphanFiles` がバケットの先頭 2000 件しか見ない。** `pageToken` を持ち越しておらず、総ファイル数が上限を超えると後ろのリストの孤児は永久に消えない。ログには「残りは次回に持ち越します」と出るため監視していても気づけない | 続きの位置を保存し、一巡したら先頭へ戻す |
| **A4** | **`normalizeListName` が Dart と TS で食い違う。** Dart 側だけスラッシュを置き換えておらず、`a/b` という名前で不正なドキュメント参照になる。しかも**「揃っていることを確かめる」テストがスラッシュを含まない入力しか渡しておらず、食い違いを隠していた** | Dart 側を揃え、対応表を両言語に置く |

## 4. 今回分かったこと（次回への申し送り）

### 4.1 「〜できない」と書いたのは、今回は監査の主宰者だった

第 1 回の申し送りは「**『〜できない』と書かれた箇所こそ、まず試すこと**」だった。

今回、その記述を作ったのは**私（監査の主宰者）**である。開発コンテナのプロキシ制約に従ったまま
「この環境では統合テストと Storage ルール 3 件を実行できない」と断定し、
`docs/DEVLOG.md` に転記した。

観点 2 と観点 4 の担当が**実際に試して動かし**、`rules-test` 105/105・統合テスト 47/47 を実測した。

**前提を作る側が、その前提をいちばん疑いにくい。**
「動かせない」と書くときは、根拠と、試した手順を必ず添えること。

### 4.2 「環境のせいで赤」は、それ自体が抜け道になる

私は「Storage の 3 件の赤はこの環境のプロキシ由来です」と繰り返し説明していた。

観点 4 の担当が、ルールの上書き禁止をわざと壊す対照実験を行った結果：

| 条件 | 「既存ファイルを上書きできない」 |
| --- | --- |
| 変異あり・Firestore 参照が生きている | **失敗（検出できた）** |
| 変異あり・Firestore 参照が壊れている | **成功（見逃す）** |

**「環境のせいで 3 件赤」と「環境のせいで 3 件赤＋本物のセキュリティ後退」が、出力から見分けられない。**
常に赤が出ている状態は、赤に慣れることを通じて検出能力そのものを削る。

対処として、前提が壊れていたら**その場で理由を出して止まる**ようにした。
以降、否定側のテストは前提が生きているときだけ実行される。

### 4.3 「テストがあること」と「守られていること」は別（第 1 回と同じ指摘）

第 1 回でも指摘され、**コードも README も直っていなかった**。

| 死蔵 | テスト件数 | 実際に動いていたもの |
| --- | --- | --- |
| `SequenceCounter` | 9 | リポジトリのインライン実装 |
| `InvitePolicy` | 13 | Functions のインライン実装（無テスト） |
| `Permissions` の 6 メソッド | 15 | 画面のインライン判定 |

**指摘を記録しただけでは直らない。** 今回は、
死蔵の有無そのものを `test/domain/no_dead_code_test.dart` で機械的に確かめるようにした。
このテストは、**監査でも挙がっていなかった `watchMyMembership` を新たに検出した。**

### 4.4 前回の対応が、新しい欠陥を持ち込んでいた

A1（新規登録が失敗する）は、**第 1 回の S3 対応（メール確認をサーバー側で強制する）で持ち込んだもの**。
S3 の修正自体は正しかったが、「作れるのに読めない」という食い違いを生んだ。

既存のルールテストは「未確認でも自分のユーザードキュメントは**作れる**」だけを見ており、
**読む側を一度も試していなかった**。

**修正の対になる操作を、必ず並べて確かめること。**
書けるなら読めるか。読めるなら書けるか。片方だけのテストは、片方だけの保証しかしない。

### 4.5 否定を確かめる項目は、単独では意味を持たない

第 2 回の途中、私が追加した通知のテストでも同じことが起きた。
エミュレータのプロジェクト ID が噛み合っていないとき、
「本人には届かない」「参加していない人には届かない」が**すべて緑になった**。

土台が崩れているほど緑が増える。前提の確認を最初にまとめて行い、
崩れていればその場で止めるようにした。
