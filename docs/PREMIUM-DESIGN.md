## 1. 依頼者が決めたこと（2026-08-11）

| 論点 | 決定 |
| --- | --- |
| 課金の単位 | **人ごと**。契約は利用者に付く |
| 解約したとき | **追加だけ止める。既存のデータは消さない** |
| 初回に出す範囲 | **申請なしのリスト作成だけ**（容量拡張とオフライン保存は後） |
| 支払い | **決済サービスは入れない。クーポンコードで付与する** |

**この 4 つが、以下すべての土台です。**

### 決済を入れないことで、要らなくなったもの

初回に限っては、次を作らなくて済みます。**あとで決済を足すときに要る
ようになる**ので、消えたのではなく先送りだと考えてください。

- 決済サービスとの繋ぎ込み、その結果を受け取る口（Webhook）
- 返金・請求の失敗・カードの期限切れの扱い
- 自動更新と、その停止
- 特定商取引法に基づく表記、適格請求書（インボイス）

> **お金を受け取る方法をアプリの外に置く**という判断です。
> 実際にどう集金するか（振込・現金・別サービス）は運用側の話になり、
> アプリは「クーポンを配る」ところだけを持ちます。

## 2. 細部の決定（2026-08-11・依頼者に 1 件ずつ確認）

| # | 決めたこと | 内容 |
| --- | --- | --- |
| D1 | クーポン 1 枚を使える人数 | **発行時に決める。あとから変更できる** |
| D2 | プレミアムが続く期間 | **クーポンごとに月数を決める。延長できる** |
| D3 | 期間が切れたら | **新しいリストを作れなくなるだけ。既存はすべて残る** |
| D4 | 期間の延ばし方 | **2 枚目のクーポンでも、管理画面からでも延ばせる** |
| D5 | 作れるリストの数 | **無制限** |
| D6 | 上限に達したときの導線 | — （D5 が無制限のため不要） |
| D7 | 消したら枠が戻るか | — （同上） |
| D8 | コードの作り方 | **自動生成と、文字列の指定の両方を選べる** |

### D1 の補足：上限を下げたとき

すでに使われた人数を**下回る値**にできます。そのときは
**それ以上使えなくなるだけ**で、すでに使った人のプレミアムは消えません。
（「配りすぎたので止めたい」に、停止とは別の粒度で応えるため。）

### D5 の補足：容量は「人ごとの合計」で囲む（2026-08-11 に追加で決定）

**リストは無制限。ただし容量に上限を置きます。** リストが無制限だと
1 人が持てる総容量にも上限が無くなるため、費用の裏口が開きます。
そこを塞ぐ判断です。

| 決めたこと | 内容 |
| --- | --- |
| 上限の単位 | **人ごとの合計だけ**（リストごとの上限は使わない） |
| 誰の枠を使うか | **リストを作った人**。誰がアップロードしても、作った人の枠から引く |

**「自分の場所に人を招いて集める」という使い方と揃います。** 誰が
入っても、費用の上限が読めます。アップロードした本人の枠にすると、
**無償の人は枠を持たない**ため、その分をどう数えるかを別に決める
必要が出ます。いまの管理者の枠にすると、**管理者を交代した瞬間に
使用量が付け替わり、新しい管理者がいきなり上限超過**になります。

### 容量の数字（2026-08-11 に決定）

| | 初期 | 自動拡張 |
| --- | --- | --- |
| プレミアム | **2GB** | **90% を超えたら 2GB ずつ、最大 10GB まで**（2→4→6→8→10） |
| それ以外 | **2GB** | **無し** |

**上限は人ごとの合計です。** リストごとの上限は使いません。
無償の人も同じ仕組みで、**自動拡張だけが無い**という違いになります。
2 通りの仕組みが並ぶことを避けられました。

#### 自動拡張の作り

- **90% の通知（7.3）に繋げます。** すでに 80%／90% で通知しており、
  判定はそこにあります。**新しい判定を別に作らないこと**
- 増やしたことを**通知で伝えます。** 黙って増えると、
  請求が増える理由が利用者にも運営にも分かりません
- 10GB に達したら、それ以上は増えません。**アップロードが止まります**

#### プレミアムが切れたとき

**上限は 2GB に戻します。** すでに保存したものは消えません
（D3 の「追加だけ止める」と同じ扱い）。

例：10GB まで拡張して 6GB 使っている人の期限が切れると、
**6GB のファイルはすべて残り、新しくアップロードできなくなります。**
使用量が 2GB を下回るまで消せば、また追加できます。

> **画面でそう説明してください。** 「容量が減りました」とだけ出すと、
> ファイルが消されたと誤解されます。**消えていないこと**と、
> **どうすればまた追加できるか**を書きます。

### 着手前に必ず確かめること：既存の利用者への影響

**いまは容量がリストごとに 1GB です。** 人ごとの合計 2GB へ変えると、
持っているリストの数で有利不利が変わります。

| 持っているリスト | いま使える量 | 変更後 |
| --- | --- | --- |
| 1 個 | 1GB | **2GB（増える）** |
| 2 個 | 2GB | 2GB（同じ） |
| 3 個以上 | 3GB 以上 | **2GB（減る）** |

**3 個以上のリストを持つ無償の方は、いまより減ります。**
既存のファイルは消えませんが、**昨日までアップロードできた人が
今日からできなくなる**ことが起こり得ます
（[AUDIT-CHECKLIST.md](AUDIT-CHECKLIST.md) 観点 6「既存利用者が
使えなくなる変更は無いか」）。

**実装に入る前に、本番と検証環境で該当者がいるかを数えてください。**

- いなければ、そのまま進めて構いません
- いれば、**その人たちにだけ上限を個別に足す**（サイト管理から）か、
  **移行のあいだは上限を「合計 2GB か、リスト数×1GB の大きいほう」に
  する**といった手当てが要ります

### この変更が波及するところ

**見た目より広く効きます。着手前に必ず読んでください。**

いまは容量が**リストごと**に付いており、次がその前提で作られています。

| いまの作り | 変更後に必要なこと |
| --- | --- |
| `lists/{listId}/meta/stats.quotaBytes` と `usedBytes` | 使用量は引き続きリストごとに数える（表示に要る）。**上限の判定は人ごとの合計で行う** |
| 容量バー（ホーム・リスト詳細） | 「このリストの使用量」と「作った人の残り」の両方が要る |
| 80%／90% の通知（7.3） | **宛先と判定を人ごとに変える。** いまはリスト管理者へ、リストの割合で送っている |
| サイト管理の容量変更（`setListQuota`） | **人ごとの上限を変える形へ。** リストごとの上限は使わなくなる |
| Storage の保存後の処理（`onFileUploaded`） | リストの使用量に加えて、**作った人の合計**も更新する。超過の判定はそちらで行う |

> **無償の人も同じ仕組みに変わります。** 上限は人ごとの合計 2GB で、
> 自動拡張だけがありません。**2 通りの仕組みが並ばない**ぶん、
> 説明も実装も単純になります。ただし上の「既存の利用者への影響」を
> 必ず先に確かめてください。

## 3. データの持ち方

### 3.1 プレミアムの状態は Firestore に持つ（クレームは使わない）

サイト管理者の判定は Auth のカスタムクレームで行っています（13.5）。
**プレミアムは同じ形にしません。**

| | サイト管理者 | プレミアム |
| --- | --- | --- |
| 置き場所 | Auth のカスタムクレーム | **Firestore の `users/{uid}`** |
| 理由 | **セキュリティルールが判定に使う** | **ルールは使わない**。判定は Functions の中だけ |

リストの作成は、名前の予約・容量の初期化・メンバー登録を**まとめて
行う必要がある**ため、必ず Functions を通ります（下の 4 節）。
つまりルール側でプレミアムを見る場面がありません。

**クレームを避けると、面倒がひとつ消えます。** クレームは付けても
**利用者がトークンを取り直すまで反映されません。** クーポンを入れた
直後に「プレミアムになっていない」と見える問題が起きます。
Firestore なら、書いた瞬間に画面へ流れます。

> **あとで容量拡張（構想 2-3）をやるときは要注意。** 容量の判定は
> Storage のルールにも関わるため、そのときはクレームが要るか
> 改めて検討してください。**いま決め打ちしない。**

```
users/{uid}
  premium: {
    until: Timestamp,        // ここまでプレミアム
    grantedBy: string,       // 使ったクーポンの ID（追跡用）
    updatedAt: Timestamp,
  }
```

**`until` だけで状態を表します。** 「プレミアムかどうか」の真偽値を
別に持つと、期限切れのときに 2 つが食い違います
（[AUDIT-CHECKLIST.md](AUDIT-CHECKLIST.md)「同じ規則を 2 か所に持つな」）。

> **書き込みはクライアントから完全に塞ぎます**（ルールで禁止）。
> **ただし読みは他人にも見えます。** 当初この文書には「本人が読める
> だけ」と書いていましたが、**実装できませんでした。**
> Firestore のルールに項目単位の読み取り制限は無く、
> `users/{uid}` は**表示名の解決のためログイン済みなら誰でも取得できる**
> 設計だからです（そこにはメールアドレスも入っています）。
>
> **詐称には繋がりません**（書けないため）。漏れるのは「誰がプレミアムか」
> と「どれだけ使っているか」で、**既にある露出の延長**です。
> 閉じるには `users/{uid}/private/…` のような別の置き場所へ移す必要があり、
> **メールアドレスの露出とまとめて**判断すべきなので、
> [BACKLOG.md](BACKLOG.md) へ回しました。

### 3.2 クーポン

```
coupons/{couponId}            ← 管理者だけが読み書き（ルールで全面禁止）
  code: string                // 表示用。照合は codeHash で行う
  codeHash: string            // 探すときはこちら（下の注意）
  months: number              // 付与する月数（D2）
  maxUses: number             // 何人まで使えるか（D1。**あとから変更できる**）
  usedCount: number           // 使われた数
  expiresAt: Timestamp | null // クーポン自体の有効期限
  disabled: boolean           // 配ったあとに止めたいとき
  createdBy: string
  createdAt: Timestamp

coupons/{couponId}/redemptions/{uid}   ← 誰がいつ使ったか
  redeemedAt: Timestamp
```

> **同じ人が同じクーポンを二度使えないようにする**ため、使用記録の
> ドキュメント ID を uid にします。トランザクションの中で
> 「無ければ作る」を行えば、二重取りが起きません。

**自動生成のときは推測できない長さにします**（24 文字）。
`0/O` `1/l/I` のような読み違えやすい文字は使いません。
**文字列を指定したときは短く覚えやすくなる**ので、
人数と期限を必ず付け、推測されやすい点を発行画面で伝えます（D8）。

## 4. 申請なしのリスト作成

### 4.1 いまの流れ（承認あり）

`submitListRequest` → サイト管理者が `approveListRequest`。
承認の中で**ひとつのトランザクション**にまとめて次を行っています。

1. `listNames/{nameLower}` を見て、**同じ名前が使われていないか**確かめる
2. `lists/{listId}` を作る
3. `lists/{listId}/meta/stats` を作る（連番 1・容量の初期値）
4. 申請者を `listAdmin` として登録する
5. `listNames/{nameLower}` を確定する
6. 申請を `approved` にする

### 4.2 足すもの

**新しい呼び出し可能関数 `createListDirectly` を作ります。**

上の 1〜5 をそのまま行い、6 だけ行いません。**同じトランザクション、
同じ名前の予約を通します。**

> **名前の予約を飛ばしてはいけません。** 承認の流れに組み込まれて
> いるので、飛ばすと**同じ名前のリストが 2 つできます**（BACKLOG の
> 「承認を飛ばす経路を作るなら、そこも通るようにすること」）。

関数の中で確かめること（**順序も含めて、すべてサーバー側**）。

| 確かめること | 満たさないとき |
| --- | --- |
| ログイン済み・メール確認済み | `signInRequired` / `emailNotVerified` |
| **プレミアムが有効**（`premium.until` が未来） | `premiumRequired` |
| 名前が空でない・長すぎない | `listNameRequired` など |
| 名前が使われていない | `listNameTaken` |

**作れる数に上限はありません**（D5）。数を数える処理も、そのための
索引も要りません。**あとで上限を入れるときは、利用者ごとの合計を
どこかに持つのではなく `lists` を `createdBy` で数え直してください**
——持つと、リストを消したときに食い違います。そのときは
`firestore.indexes.json` への宣言を忘れないこと（2026-08-10 に索引の
宣言漏れでユーザー削除が本番で必ず失敗した件と同じ形です）。

### 4.3 画面

- ホームの「リスト作成を申請」の隣か置き換えで、**プレミアムの人には
  「リストを作る」**を出す。名前だけ入れて即作成
- プレミアムでない人には、いまと同じ申請の導線のみ

## 5. クーポン管理画面（サイト管理）

サイト管理の下に「クーポン」を足します（仕様 11.1 の並び）。

| できること | 備考 |
| --- | --- |
| 発行 | 月数・使える人数・有効期限を決めて作る。**コードは自動生成か、文字列の指定**（D8） |
| 一覧 | 使われた数／上限、期限、止めてあるか |
| 上限を変える | 配りすぎ／足りないときに人数だけ直す（D1） |
| 止める | `disabled` を立てる。**消さない**——誰が使ったかの記録が消える |
| 使った人を見る | 追跡と、問い合わせへの回答用 |

**クーポンはクライアントから直接読めません。** ルールで全面禁止にし、
発行・一覧・停止はすべて呼び出し可能関数を通します。読めると、
**コードの一覧がそのまま漏れます。**

利用者側は、設定画面に**「クーポンを入力」**を置きます。

## 7.1 私的な情報を別の置き場所へ移した（2026-08-11）

**`users/{uid}` は、表示名の解決のためログイン済みなら誰でも読めます。**
Firestore のルールに項目単位の読み取り制限が無いため、そこへ置いた
プレミアムの期限も容量も、**他人に見えていました**。
メールアドレスも同じ理由で以前から見えていました。

分けました。

| 置き場所 | 中身 | 誰が読めるか |
| --- | --- | --- |
| `users/{uid}` | 表示名・写真・退会したか | ログイン済みなら誰でも（表示名の解決に要る） |
| `users/{uid}/private/state` | メール・表示言語・通知設定・プレミアム・容量 | **本人だけ**（サイト管理者も読めない） |

- **書けるのは `locale` と `notificationSettings` だけ。** プレミアムと容量は
  サーバーだけが書きます。ここが緩むと誰でも自分をプレミアムにできます
- **削除も禁止。** 消せると、書けないはずの項目を「消す形で」捨てられます
- `docId` は `state` に限定。無いと、自分の下に好きなだけ書類を作れます
- サイト管理者が必要な情報は、**サーバー経由**（`listSiteUsers` など）で取ります
- **メンバー管理からメールアドレスの表示をやめました**（依頼者の判断）

### 移行（配信の直後に必要）

```
node scripts/backfill.mjs --project <プロジェクト ID>
```

**実行するまで、表示言語と通知設定が既定に戻って見えます。**
容量の集計より先に私的情報を移します（順序が逆だと、管理者が決めた
容量の土台を見失って既定値へ戻してしまう）。何度実行しても同じ結果です。

## 8. 今回やらないこと

**書かないと、あとで「なぜ無いのか」を調べ直すことになります。**

| やらないこと | 理由 |
| --- | --- |
| 決済サービスとの繋ぎ込み | 依頼者の判断。クーポンで配る |
| オフライン保存（構想 2-1） | 初回の範囲外。**端末に降りたものは取り消せない**という別の判断が要る |

## 9. 危ないところ

**着手する人へ。この 3 つは事故の起きやすい順です。**

1. **二重取り。** クーポンの引き換えは、必ずトランザクションの中で
   「使用記録が無いこと」と「上限に達していないこと」を同時に確かめる。
   読んでから書くまでの間に、別の要求が入ります。
2. **名前の予約を飛ばすこと。** 4.2 のとおり。同じ名前のリストが
   できると、あとから直せません。
3. **コードの漏れ。** `coupons` はルールで全面禁止にします。読めると
   **コードの一覧がそのまま漏れ**、誰でもプレミアムになれます。
   ルールテストで「読めないこと」を必ず確かめてください。

> **上限を入れることになったら、索引の宣言を思い出してください。**
> `createdBy` で数えるクエリには索引が要り、**エミュレータは索引を
> 強制しないので統合テストは緑のまま本番だけ落ちます**
> （2026-08-10 に実際に起きました）。
