# プレミアムユーザー 実装検討（2026-08-11）

**まだ実装していません。** これは「作る前に決めること」を並べ、
決まった範囲の作り方をまとめた文書です。

課金が絡むと、間違いが利用者のお金に直結します。**この文書で決めきって
から書き始めてください**（[BACKLOG.md](BACKLOG.md) の構想）。

## 1. 依頼者が決めたこと（2026-08-11）

| 論点 | 決定 |
| --- | --- |
| 課金の単位 | **人ごと**。契約は利用者に付く |
| 解約したとき | **追加だけ止める。既存のデータは消さない** |
| 初回に出す範囲 | **申請なしのリスト作成だけ**（容量拡張とオフライン保存は後） |
| 支払い | **決済サービスは入れない。クーポンコードで付与する** |

**この 4 つが、以下すべての土台です。**

### 決済を入れないことで、要らなくなったもの

初回に限っては、次を作らなくて済みます。**あとで決済を足すときに要る
ようになる**ので、消えたのではなく先送りだと考えてください。

- 決済サービスとの繋ぎ込み、その結果を受け取る口（Webhook）
- 返金・請求の失敗・カードの期限切れの扱い
- 自動更新と、その停止
- 特定商取引法に基づく表記、適格請求書（インボイス）

> **お金を受け取る方法をアプリの外に置く**という判断です。
> 実際にどう集金するか（振込・現金・別サービス）は運用側の話になり、
> アプリは「クーポンを配る」ところだけを持ちます。

## 2. まだ決まっていないこと

**着手前にここを埋めてください。** 空欄のまま作ると、あとで
データを作り直すことになります。推奨を添えてあります。

| # | 決めること | 推奨 | なぜ決めないと進めないか |
| --- | --- | --- | --- |
| D1 | クーポン 1 枚を**何人が使えるか** | 人数上限つき（既定 1） | データの持ち方が変わる。1 人だけなら使用済みフラグで足りるが、複数人なら使用記録を別に持つ必要がある |
| D2 | プレミアムが**続く期間** | クーポンに書く（例 12 か月） | 期限が無いと「解約」という状態が発生しない。D3 の前提 |
| D3 | 期間が切れたら | **追加だけ止める**（決定済みの方針をそのまま適用） | 1 の決定どおり。既存のリストは残り、**新しく作れなくなる**だけ |
| D4 | 同じ人が**2 枚目**を使ったら | 期間を足す | 上書きだと、残りが長いほうを捨てることになり苦情が出る |
| D5 | **作れるリストの上限** | 5 個 | 「上限つき」とだけ決まっている。数を決めないと実装できない |
| D6 | 上限に達したら | 申請の画面へ誘導 | 作れないだけだと行き止まりになる。既存の申請の仕組みへ戻す |
| D7 | 既存のリストを消したら**枠は戻るか** | 戻す | 戻さないと「作っては消す」を防げる代わりに、消す判断を歪める |
| D8 | コードの**作り方** | こちらで自動生成（読み違えにくい文字だけ） | 管理者が決めると、推測されやすい文字列になりやすい |

> **D5 と D6 は、サイト管理者の負担に直結します。** 承認を通らない
> リストが増えるので、一覧で把握できないと管理不能になります（仕様 11.1）。

## 3. データの持ち方

### 3.1 プレミアムの状態は Firestore に持つ（クレームは使わない）

サイト管理者の判定は Auth のカスタムクレームで行っています（13.5）。
**プレミアムは同じ形にしません。**

| | サイト管理者 | プレミアム |
| --- | --- | --- |
| 置き場所 | Auth のカスタムクレーム | **Firestore の `users/{uid}`** |
| 理由 | **セキュリティルールが判定に使う** | **ルールは使わない**。判定は Functions の中だけ |

リストの作成は、名前の予約・容量の初期化・メンバー登録を**まとめて
行う必要がある**ため、必ず Functions を通ります（下の 4 節）。
つまりルール側でプレミアムを見る場面がありません。

**クレームを避けると、面倒がひとつ消えます。** クレームは付けても
**利用者がトークンを取り直すまで反映されません。** クーポンを入れた
直後に「プレミアムになっていない」と見える問題が起きます。
Firestore なら、書いた瞬間に画面へ流れます。

> **あとで容量拡張（構想 2-3）をやるときは要注意。** 容量の判定は
> Storage のルールにも関わるため、そのときはクレームが要るか
> 改めて検討してください。**いま決め打ちしない。**

```
users/{uid}
  premium: {
    until: Timestamp,        // ここまでプレミアム
    grantedBy: string,       // 使ったクーポンの ID（追跡用）
    updatedAt: Timestamp,
  }
```

**`until` だけで状態を表します。** 「プレミアムかどうか」の真偽値を
別に持つと、期限切れのときに 2 つが食い違います
（[AUDIT-CHECKLIST.md](AUDIT-CHECKLIST.md)「同じ規則を 2 か所に持つな」）。

### 3.2 クーポン

```
coupons/{couponId}            ← 管理者だけが読み書き（ルールで全面禁止）
  code: string                // 表示用。照合は codeHash で行う
  codeHash: string            // 探すときはこちら（下の注意）
  months: number              // 付与する月数
  maxUses: number             // 何人まで使えるか（D1）
  usedCount: number           // 使われた数
  expiresAt: Timestamp | null // クーポン自体の有効期限
  disabled: boolean           // 配ったあとに止めたいとき
  createdBy: string
  createdAt: Timestamp

coupons/{couponId}/redemptions/{uid}   ← 誰がいつ使ったか
  redeemedAt: Timestamp
```

> **同じ人が同じクーポンを二度使えないようにする**ため、使用記録の
> ドキュメント ID を uid にします。トランザクションの中で
> 「無ければ作る」を行えば、二重取りが起きません。

**コードは推測できない長さにします**（例：24 文字）。
`0/O` `1/l/I` のような読み違えやすい文字は使いません。

## 4. 申請なしのリスト作成

### 4.1 いまの流れ（承認あり）

`submitListRequest` → サイト管理者が `approveListRequest`。
承認の中で**ひとつのトランザクション**にまとめて次を行っています。

1. `listNames/{nameLower}` を見て、**同じ名前が使われていないか**確かめる
2. `lists/{listId}` を作る
3. `lists/{listId}/meta/stats` を作る（連番 1・容量の初期値）
4. 申請者を `listAdmin` として登録する
5. `listNames/{nameLower}` を確定する
6. 申請を `approved` にする

### 4.2 足すもの

**新しい呼び出し可能関数 `createListDirectly` を作ります。**

上の 1〜5 をそのまま行い、6 だけ行いません。**同じトランザクション、
同じ名前の予約を通します。**

> **名前の予約を飛ばしてはいけません。** 承認の流れに組み込まれて
> いるので、飛ばすと**同じ名前のリストが 2 つできます**（BACKLOG の
> 「承認を飛ばす経路を作るなら、そこも通るようにすること」）。

関数の中で確かめること（**順序も含めて、すべてサーバー側**）。

| 確かめること | 満たさないとき |
| --- | --- |
| ログイン済み・メール確認済み | `signInRequired` / `emailNotVerified` |
| **プレミアムが有効**（`premium.until` が未来） | `premiumRequired` |
| **作った数が上限未満**（D5） | `listLimitReached` |
| 名前が空でない・長すぎない | `listNameRequired` など |
| 名前が使われていない | `listNameTaken` |

**「作った数」は数え直します。** 利用者ごとの合計をどこかに持つと、
リストを消したときの戻し（D7）と食い違います。
`lists` を `createdBy` で数えるため、**コレクションの索引が要ります**
（`firestore.indexes.json`。2026-08-10 に索引の宣言漏れで
ユーザー削除が本番で必ず失敗した件と同じ形なので、忘れないこと）。

### 4.3 画面

- ホームの「リスト作成を申請」の隣か置き換えで、**プレミアムの人には
  「リストを作る」**を出す。名前だけ入れて即作成
- **上限に達したら、その旨と申請への導線**（D6）
- プレミアムでない人には、いまと同じ申請の導線のみ

## 5. クーポン管理画面（サイト管理）

サイト管理の下に「クーポン」を足します（仕様 11.1 の並び）。

| できること | 備考 |
| --- | --- |
| 発行 | 月数・使える人数・有効期限を決めて作る。**コードは自動生成** |
| 一覧 | 使われた数／上限、期限、止めてあるか |
| 止める | `disabled` を立てる。**消さない**——誰が使ったかの記録が消える |
| 使った人を見る | 追跡と、問い合わせへの回答用 |

**クーポンはクライアントから直接読めません。** ルールで全面禁止にし、
発行・一覧・停止はすべて呼び出し可能関数を通します。読めると、
**コードの一覧がそのまま漏れます。**

利用者側は、設定画面に**「クーポンを入力」**を置きます。

**上から順に、1 つずつ緑にしてから次へ進んでください。**

| # | 作るもの | 置き場所 |
| --- | --- | --- |
| 1 | プレミアムの判定（期限を見るだけの純関数） | `functions/src/domain/premium.ts` |
| 2 | クーポンの発行・停止・一覧（サイト管理者のみ） | `functions/src/callable/coupons.ts` |
| 3 | クーポンの引き換え（トランザクション。二重取りを防ぐ） | 同上 |
| 4 | `createListDirectly`（4.2） | `functions/src/callable/list_requests.ts` |
| 5 | ルール：`coupons` を全面禁止。`users.premium` は本人が読めるだけ | `firestore.rules` |
| 6 | 索引：`lists` の `createdBy` | `firestore.indexes.json` |
| 7 | 画面：クーポン入力（設定）、リストを作る（ホーム） | `lib/ui/screens/` |
| 8 | 画面：クーポン管理（サイト管理） | 同上 |
| 9 | 文言（日英）、使い方への追記 | `lib/l10n/`、`web/help/` |

**テストで守るもの**（仕様 12.6 の「必須」に当たります）。

- 期限の境界（ちょうど・1 秒前・1 秒後）
- **二重取りができないこと**（同じ人が同じクーポンを 2 回）
- 使用人数の上限を超えないこと
- **プレミアムでない人が `createListDirectly` を呼べないこと**
  ——符号まで確かめる（`permissionDenied` であって未ログインではない）
- 上限に達した人が作れないこと。**消したら作れるようになること**（D7）
- 同じ名前のリストが 2 つ作れないこと（申請経由と直接作成を混ぜて）

## 7. 既存の利用者への影響

**移行の作業はありません。**

- `users/{uid}.premium` が無い人は「プレミアムでない」と読みます
  （`isWithdrawn` と同じ扱い方。読み取り時に既定へ倒す）
- 既存のリスト、申請、承認の流れは**何も変わりません**
- プレミアムでない人から見て、画面の見え方も変わりません

**書かないと、あとで「なぜ無いのか」を調べ直すことになります。**

| やらないこと | 理由 |

## 9. 危ないところ

**着手する人へ。この 3 つは事故の起きやすい順です。**

1. **二重取り。** クーポンの引き換えは、必ずトランザクションの中で
   「使用記録が無いこと」と「上限に達していないこと」を同時に確かめる。
   読んでから書くまでの間に、別の要求が入ります。
2. **名前の予約を飛ばすこと。** 4.2 のとおり。同じ名前のリストが
   できると、あとから直せません。
3. **索引の宣言漏れ。** `createdBy` で数えるクエリには索引が要ります。
   **エミュレータは索引を強制しないので、統合テストは緑のまま
   本番だけ落ちます**（2026-08-10 に実際に起きました）。
